# TaskLoom「织序」开发路线与 OpenClaw 对照方案

> 自研调度核心与轻量执行框架，采用 OpenClaw 的成熟机制建立对照，并保留真实系统接入路径。

**日期** 2026-10-14 · **状态** 当前开发建议 · **读者** 项目成员与指导教师

本文依次说明路线选择及报告取舍、系统设计与 OS 方法、对照实验、实施与验证条件。TaskLoom 延续个人端 L1—L3 与平台端 L4 的四层模型，比较中固定模型能力、资源与额度，并评价完整任务的交付质量。

证据分为两类：附加报告记录了作者在 OpenClaw 2026.10.3 环境中的 mock 模型服务接入；仓库调研记录了固定版本的接口、源码和问题状态。自研框架的功能、调度收益与 OpenClaw 兼容性属于后续实施和验证内容。

**完整方案入口（2026-10-15）** 系统范围、两端架构、技术与首版验收见[当前完整项目说明书](TaskLoom_项目说明书_当前完整方案.md)。本文作为路线选择与对照原则的专题依据。

## 1. 路线选择与报告取舍

### 1.1 当前开发建议

建议将首版主线调整为：**独立开发 TaskLoom 调度核心与轻量 Agent 执行框架，以 OpenClaw 的相关机制作为方法对照，以真实 OpenClaw 作为后续集成和应用验证对象。**

这项调整改变的是实现载体，保留原有问题和目标：在个人电脑上协调工具资源与模型请求，在平台上分配多用户的共享请求机会，使相同资源和额度支持更多及时、合格完成的任务。

自研的直接价值是控制任务进入、等待、许可释放和续接的完整过程，使实验能够逐项切换策略。系统首先需要实现可靠的执行底座，再比较不同调度方案。

### 1.2 为什么调整 OpenClaw 的角色

OpenClaw 已经具备会话串行化、并发限制、容量组、优先级与老化、父子任务交接和进程清理等能力。项目的主要贡献应围绕根任务份额、工具资源成本、请求额度与跨阶段等待展开。[OC-D06](../research/agent-orchestrate/materials/L2_harness_tasks/OC-D06/queue.md)、[OC-S02](../research/agent-orchestrate/materials/L2_harness_tasks/OC-S02/command-queue.types.ts)

原生队列的 `taskIdentity` 用于诊断，相关准入字段主要描述容量、类别和等待。按完整任务计量成本和分配服务份额，仍具有可检验的机制空间。

下表比较三种实现路线，重点考虑课程展示、控制范围和工程投入。

| 路线 | 主要收益 | 主要投入与适用定位 |
|---|---|---|
| 基于 OpenClaw 插件与外部服务开发。 | 能复用真实 Agent 循环、工具和已有生命周期。 | 需要衔接外部队列与原生运行许可，适合作为接入路线。 |
| 自研调度核心与轻量执行框架。 | 能直接管理步骤状态、资源许可和续接，便于策略对照与 OS 展示。 | 需要实现最小可靠执行底座，建议作为首版主线。 |
| 重建完整 Agent 成品平台。 | 产品形态可以全面自定义。 | 渠道、插件生态和多运行时会显著扩大范围，首版投入集中在执行与调度能力。 |

独立开发带来的是控制与验证条件。课设价值来自明确场景下的机制设计和量化改善，性能研究需要与合理配置的成熟方案比较。

### 1.3 附加报告中可采用的部分

附加报告《TaskLoom 是否修改 OpenClaw 源码利弊分析》提供了接入经验和工程取舍。以下四组内容进入本方案；原报告保存在[工作输入目录](../agent-workspace/inputs/reports/TaskLoom_是否修改OpenClaw源码_利弊分析.md)，引用使用同一份文件。

| 内容 | 采用方式 | 证据与设计处理 |
|---|---|---|
| 自定义 Provider 与 `baseUrl` 接入。 | 作为真实 OpenClaw 对照的模型请求入口。 | 报告 E5 记录了一条 mock 请求与流式返回链路；其他调用路径在接入阶段逐项验证。 |
| 官方插件、工具 gate 与调用事件。 | 用于任务映射、执行观察和必要的调用前控制。 | 区分 Observe、Gate 与传输接口；实际派发由拥有发送权的组件控制。 |
| 请求与用量观察。 | 登记模型调用、实际 HTTP 尝试与用量，贯通任务账本。 | 任务身份采用结构化上下文与传输元数据，prompt 中的 Runtime 文本用于辅助核对。 |
| 配置、插件、局部源码适配的演进路线。 | 接入时优先使用公开接口，按具体能力缺口决定补丁。 | 固定版本、明确补丁范围，通过同底座对照和消融评价影响。 |

报告中的接口数量说明扩展面丰富，接口是否覆盖任务调度由调用位置、权限、返回语义和生命周期决定。SDK 子路径数量与运行时控制能力分别核验。

模型路由、改写提示或合成回复属于可用产品能力。当前性能主实验保持模型能力和任务质量要求一致，收益主要由服务次序、资源安排、等待和恢复解释。

### 1.4 版本与证据范围

报告中的运行环境为 OpenClaw 2026.10.3。仓库核查同时保留稳定版 `59cb44796b0f1f0daa0e37af8b1495abb45d9bc1` 与 main 快照 `6a64431a10b638958cdeccc782f2b36074274776`，版本记录见[OC-M01](../research/agent-orchestrate/materials/L2_harness_tasks/OC-M01/pin.json)。

已核查稳定版采用严格类别优先；main 快照增加有界优先超越与老化。因此，机制对照建议采用固定的 main 快照，稳定版保留作接入和版本对照。真实运行的代码、配置与修复集合在实验前登记。

## 2. 系统设计与 OS 方法

### 2.1 两个部署场景与四层职责

个人端运行轻量执行框架和调度核心，承载 L1—L3；平台端承载 L4。四层是职责划分，首版可以在客户端服务内组合个人端模块，将统一模型服务平台作为独立部署边界。

下表规定各层管理对象和执行责任。

| 层次 | 管理对象 | 首版职责 |
|---|---|---|
| L1：本地资源与工具执行。 | 工具进程、实例、CPU、内存、文件和产物。 | 判断资源可行性，启动受控工具，核实实际结束并回收。 |
| L2：任务管理与推进。 | 根任务、子 Agent、动态步骤、执行尝试和成果。 | 登记已揭示的依赖，选择就绪步骤，维护等待、唤醒、取消与续接。 |
| L3：个人模型请求。 | 本人的就绪请求、任务份额、私有预算与重试。 | 安排发送顺序，检查个人约束，记录在途请求和实际消费。 |
| L4：平台多用户请求。 | 用户、根任务队列、共享额度与派发许可。 | 分层分配服务机会，保护共享额度，反馈平台压力。 |

个人端使用本平台注册账号的 API Key。平台维护账户额度与统一模型池的最终分配，个人端维护自身任务排序和私有预算。单机开发将两端放在同一机器的独立进程中，模型请求仍经过平台。

### 2.2 轻量执行框架的范围

首版实现模型调用、工具注册、任务分支、动态依赖、状态保存和调度接口。模型 SDK、数据库和子进程管理库可以复用成熟组件，TaskLoom 自行定义任务推进和资源许可协议。

一次任务按以下过程运行，每一步都产生可追踪的状态和事件。

1. **建立根任务。** 用户提交目标、期限及预算，系统登记 Task。子 Agent 继承根任务的份额和预算归属。
2. **揭示就绪步骤。** Agent 循环根据当前上下文提出模型或工具操作。L2 登记已知依赖，以当前满足的条件判断就绪。
3. **取得执行许可。** 工具步骤进入 L1，模型步骤进入 L3，随后由 L4 安排平台模型池派发。等待原因、许可和实际开始分别记录。
4. **接收结果并推进。** 结果保存后解锁后续步骤；失败、取消与恢复按具体尝试处理。根任务按成果验收确认交付。

Task、Agent、Step 与 Attempt 的含义沿用[项目说明书](TaskLoom_项目说明书_分层清晰版.md)。完整未来依赖由执行逐步揭示，所有策略获得相同的已知信息。

### 2.3 等待、许可释放与可靠续接

暂停与续接首先发生在受控步骤边界。模型请求尚未派发时可以排队和撤销预留；已经派发的请求单独记录真实在途状态。工具停止以进程和实例的实际退出事实为依据。

缺少额度或工具资源时，L2 登记等待条件，让出能够安全释放的执行许可。仍驻留的内存、实例和锁继续记账。资源释放、额度恢复或依赖完成产生唤醒事件，调度器重新检查条件，再原子取得许可并启动。

这个机制处理一个重要场景：两个长任务已经进入执行循环，随后等待模型额度，新的短任务仍应能够获得执行机会。等待状态与正在执行的状态分开管理，使空闲 CPU 和可用工具资源能够继续服务其他任务。

许可申请还需要处理迟到授权。申请取消或失效后，即使调度服务稍后返回授权，执行器也要核验当前状态与代次，撤销失效预留。OpenClaw 的 hook 超时规则同样说明：结束等待后，handler 可能继续运行。[OC-D18](../research/agent-orchestrate/materials/L2_harness_tasks/OC-D18/reference.md)

### 2.4 OS 方法与核心研究机制

核心组合为工具成本准入、根任务公平和跨阶段等待协调。各种 OS 方法分别承担排序、安全、保护和通信职责，避免把优先级当作全部资源问题的解法。

| 机制组 | 算法与技术 | 对应作用 |
|---|---|---|
| 资源选择与保护。 | 资源约束列表调度、信号量、进程组、cgroup、产物预算。 | 选择当前可行的轻重工具，限制真实占用并收敛后代进程。 |
| 公平与额度分配。 | 根任务成本 DRR、令牌桶、分层公平、Aging。 | 按成本分配服务机会，满足速率约束并保护后台任务活性。 |
| 安全分配与共享访问。 | 原子预留、统一锁顺序、读写锁、阶段银行家检查。 | 避免部分预留和冲突访问，在受控资源阶段检查分配安全。 |
| 状态、通信与恢复。 | 条件唤醒、IPC、短事务、持久状态、幂等与代次检查、守护进程。 | 可靠交接等待和完成，处理重复事件、失效执行器和取消回收。 |

银行家检查用于最大需求可信、申请可拦截、能够归还的受控阶段，例如实例名额。已消耗 token、费用和速率窗口按各自合同管理；物理内存保护与逻辑安全检查分别实现。条件和数值例子见[OS 算法补充说明](TaskLoom_OS算法补充说明.md)。

## 3. 对照实验与效果评价

### 3.1 三类对照的用途

算法贡献与真实产品效果使用不同对照。方法实验共用执行框架和工作负载，真实 OpenClaw 实验评价同类任务的实际体验与交付。

| 对照类型 | 设置 | 可评价的结论 |
|---|---|---|
| OpenClaw 机制对照。 | 在同一执行框架中复现所选版本的会话顺序、并发、优先级、老化和相关容量机制。 | 任务份额、成本准入和步骤等待协调，相比该机制组合的增量收益。 |
| 成熟调度方法对照。 | 使用合理配置的公平队列、限流、重试、资源限制与基本清理。 | 跨层协调是否在已有公平与保护后仍能改善完整任务交付。 |
| 真实 OpenClaw 对照。 | 固定原版版本，运行同类真实任务，统一模型、资源、额度和验收要求。 | TaskLoom 的系统效果以及后续接入的适用性。 |

机制复现标注为“OpenClaw 策略复现”，记录原生规则、复现范围与简化条件。原生 Run 粒度与 TaskLoom 步骤粒度的差异应显式记录，再通过消融判断收益。

### 3.2 控制工作量与调度变量

先通过固定调用轨迹和逐步揭示的依赖事件比较策略，再使用真实模型与工具验证结果。轨迹中的请求、工具、成本和到达负载保持一致，调度器在相应事件发生后才获得步骤信息。

方法实验固定模型及推理配置、提示与结果验收要求、资源容量、额度、身份信息和基础可靠性。预计成本来自实际画像，实际用量用于校准；同时记录排序与记账开销。

真实 OpenClaw 与轻量框架的系统提示、工具表面和调用次数可能不同，端到端比较同时报告这些差异及结果质量。耗时变化结合实际工作量解释，算法收益以同底座实验识别。

个人端、平台端与反馈贡献沿用[五组对照设计](../research/agent-orchestrate/reports/03_os_design_and_validation.md#43-五组对照与统一验收)：B00、B10、B01、B11、B11+FB。各组共用正确依赖、合理限流重试、基本取消清理和持久化，分别切换个人端优化、平台端优化与动态反馈。

### 3.3 负载与指标

工作负载覆盖交互问答、资料解析与总结、代码修改与测试等不同成本和紧迫程度的任务，并分别设置资源宽松、仅工具紧张、仅 API 紧张和两者紧张的条件。

主要指标是按时且通过验收的根任务比例。辅助指标按以下四组解释收益及代价。

- **等待体验。** 报告交互任务 P95、分段排队时间和后台最长等待，观察及时性与活性。
- **公平分配。** 报告不同用户、根任务与分支数量下的服务份额，检查派生分支的影响。
- **资源与额度。** 报告内存峰值、工具失败、产物空间、实际费用、无效重试和未结算预留。
- **结束与恢复。** 报告取消收敛时延、后代残留、恢复成功率、重复执行和结果交付状态。

同条件配对运行并报告波动。30 天仿真的成本与耗时分布由真实执行记录校准，用于展示长期累计结果；实测和仿真分别标明。

## 4. 实施路径与接入条件

### 4.1 首版实施顺序

先完成最小真实执行闭环，再逐步增加多任务竞争、平台协同和外部框架接入。各阶段以可检查的运行事实验收。

| 阶段 | 工作重点 | 验收依据 |
|---|---|---|
| 最小执行闭环。 | 单根任务的模型调用、真实工具、结果保存、取消与基本恢复。 | 任务、步骤、尝试和成果能够关联，真实进程可查询与回收。 |
| 个人端混合调度。 | 多根任务、成本准入、公平请求、等待释放与唤醒。 | 重工具与短任务混合运行，资源和额度约束成立，后台持续推进。 |
| 平台与联合实验。 | 多用户网关、共享额度、根任务份额及有时效反馈。 | 各优化组使用相同负载，能够区分个人、平台与反馈的贡献。 |
| OpenClaw 接入验证。 | 任务映射、模型传输、工具许可和必要的生命周期适配。 | 选定调用路径的身份、派发、取消、回收和结果均有真实记录。 |

### 4.2 OpenClaw 的接入与源码适配

独立调度核心通过适配器连接执行框架。OpenClaw 接入时优先复用自定义 Provider 和官方插件，将请求与事件送入同一任务账本。已有 mock 接入成果继续作为这条路径的起点。

结构化 hook 上下文提供 `runId`、`sessionKey`、`sessionId` 等信息；Provider 的 `resolveTransportTurnState` 支持每轮 headers 和 metadata。适配器据此建立根任务、步骤与尝试关系，并由平台结合认证身份核验归属。[OC-S18](../research/agent-orchestrate/materials/L2_harness_tasks/OC-S18/hook-agent-context.types.ts)、[OC-D21](../research/agent-orchestrate/materials/L3_client_requests/OC-D21/runtime-hooks.md)

源码适配依据三类具体缺口决定。

1. **控制权缺口。** 必须由原生运行时完成的暂停、许可释放、续接或取消，公开接口缺少所需语义。
2. **身份与覆盖缺口。** 某条必要调用路径无法通过公开接口传递身份或纳入统一派发，外部关联也无法可靠完成。
3. **可测量的接入开销。** 同条件测量确认外部路径造成明显瓶颈，局部适配具有明确改善目标。

适配采用固定版本上的小范围补丁，记录修改对象与协议，并设置原版、仅适配及完整调度的对照。源码修改与外挂实现都通过可复现配置和消融确定贡献。

### 4.3 阶段性决策依据

优先验证等待释放、工具成本与请求成本共同准入、根任务公平三个机制，再评估动态反馈。观测显示哪一类约束真正造成任务延迟，后续工作就围绕该瓶颈展开。

OpenClaw 已有能力进入成熟对照。项目的叙事集中在“相同电脑、模型与额度，面对同样任务，怎样减少相互拖累并改善合格交付”，实现与实验共同支撑这一结论。
