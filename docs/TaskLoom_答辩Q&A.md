## 1. 选题与需求：为什么需要 TaskLoom

### 1.1 项目目标与使用场景

#### 1.1.1 Q01｜★必备：用半分钟说明，你们到底要做什么？

**我们要在固定模型能力下，协调 Agent 任务的工具执行和模型请求，让有限资源支持更多及时、合格的任务交付。** 因为一项任务通常要多次切换模型和工具，单次调用快不等于整个任务完成快。个人端管理自己的多个任务，平台端管理多个用户的请求，并通过必要反馈减少不合适的等待。

定位与依据：PPT 第 4、10、13 页；项目说明书第 1.1、2.1—2.2 节。

#### 1.1.2 Q02｜一个人为什么需要同时运行多个 Agent？这个场景是不是人为制造的？

**多任务并发是合理场景，但我们不假定所有用户始终处于高并发。** 例如资料整理在后台运行时，用户仍可能测试代码或临时提问；一个任务也可能派生多个分支。实验会覆盖宽松和拥塞条件，判断何时需要调度、何时简单控制已经足够，不靠无限增加 Agent 数量制造优势。

定位与依据：PPT 第 4、27 页；这是设计场景，不能当作真实用户并发比例的统计。

### 1.2 痛点是否有证据

#### 1.2.1 Q03｜★必备：怎么证明问题真实存在，而不是你们假设出来的？

**我们有工作负载测量、资源约束研究和具体故障案例三类依据，但它们支持的结论不同。** TraceLab 支持工具时长和阶段的异质性；PeakBench 说明依赖可并行不等于资源容量可行；社区报告提供特定退出与交接问题。平台协同能改善多少仍是研究假设，需要本项目的对照实验回答。

定位与依据：PPT 第 5、8 页；文献 [1]、[2]，案例 [9]、[10]。问题单的版本与触发条件不能省略。

#### 1.2.2 Q04｜你们引用“4% 的工具调用占 85% 时间”，是不是意味着能优化掉 85%？

**不能，这个数字说明长尾明显，不代表这些时间都能节省。** TraceLab 统计的是工具调用总时间，其中包含必要计算和等待。TaskLoom 主要减少可避免的排队、重复执行和过度并发损耗。我们会把执行时间与等待时间分开测量，再判断实际可优化的部分。

定位与依据：PPT 第 5、28 页；TraceLab 的工具调用时长分析 [1]。

### 1.3 OS 课设定位与优化边界

#### 1.3.1 Q05｜★必备：操作系统已经会调度进程，你们为什么还要再调度一次？

**操作系统主要按进程、线程和资源控制执行，而 TaskLoom 还知道用户目标、步骤依赖和 API 额度。** 内核通常不知道多个进程属于同一项资料整理任务，也不知道某次模型请求正在等待哪个工具。我们在应用层安排启动与派发，再交给 OS 执行和隔离，两层分工不同。

定位与依据：PPT 第 11—15 页；项目说明书第 2.3、3.1—3.3 节。

#### 1.3.2 Q06｜不优化模型推理，性能提升究竟从哪里来？

**改进空间来自任务组织和资源竞争造成的额外损耗。** 例如避免多个重工具同时拖慢电脑、减少无效重试，让紧迫请求不必排在大量无关工作之后。模型处理同样输入所需的计算没有被我们直接缩短；如果负载没有竞争、耗时几乎全在模型内部，收益可能很小。

定位与依据：PPT 第 8、14、24 页；这是机制上的优化空间，不是已有加速结果。

### 1.4 已有方案与项目价值

#### 1.4.1 Q07｜★必备：这些算法早就存在，AIOS、工作流平台也做过，你们有什么创新？

**我们的候选贡献是把根任务、工具约束和两端反馈放进同一执行闭环，并验证组合的增量。** AIOS、LLMCompiler、Temporal 等已有调度或编排能力，我们不会把使用 DRR、锁和检查点本身说成创新。项目价值需要由具体场景、可靠的接口衔接，以及相对成熟基线的交付改善证明。

定位与依据：PPT 第 8、27、30 页；已有工作 [3]—[8]。开题阶段使用“候选贡献”，不宣称已经证明研究空白。

#### 1.4.2 Q08｜加内存、提高 API 额度，不就解决了吗？

**扩容能缓解容量不足，但不会自动解决依赖、公平和取消交接问题。** 同样的资源，也可能因重复请求或占而不用被浪费。我们固定资源和预算比较策略，研究现有条件下的有效交付；同时承认调度不能凭空增加容量，持续超载时仍需扩容或减少接纳。

定位与依据：PPT 第 6、12、27 页；固定资源是研究条件，不是反对扩容。

## 2. 系统模型与协同：我们具体管理哪一部分

### 2.1 两个场景与四层边界

#### 2.1.1 Q09｜你们是不是假设很多人共用一台电脑、一个 Agent？

**不是；个人端竞争发生在同一用户的多个任务之间，平台竞争发生在多个用户的请求之间。** 每位用户有自己的电脑，管理自己的工具资源。若这些个人端通过同一应用网关共享上游额度，平台再统一分配请求机会。两种竞争通过模型请求链连接起来。

定位与依据：PPT 第 4、10、13 页；项目说明书第 2.1 节。

#### 2.1.2 Q10｜★必备：平台指模型服务商吗？你们能控制它的 GPU 吗？

**平台指我们能够部署和修改的应用 API 网关，控制的是请求接纳、排队和派发。** 它取得许可后调用既有模型服务，不能保证服务商内部按同样顺序执行，也不管理 GPU、KV cache 或推理批处理。比较时模型和服务配置保持一致，外部时延波动需要单独记录。

定位与依据：PPT 第 8、10、15 页；项目控制边界与 API 合同 [17]、[18]。

#### 2.1.3 Q11｜个人端和平台都排队，是否重复设计？只保留一端行不行？

**两端可以独立运行，因为各自管理的范围和信息不同。** 个人端能看到工具压力和自身任务依赖，平台能看到多用户队列与共享额度。两端都有队列不等于一定有收益，也可能造成重复等待。因此我们分别测单端、双端独立和双端反馈；没有反馈增量时就保留更简单的组合。

定位与依据：PPT 第 10、24、27 页；协同价值需要由 B11F 对 B11 验证。

### 2.2 模型、Agent 与任务对象

#### 2.2.1 Q12｜模型、Agent 和 Harness 分别是什么？

**模型产生理解和决策，Agent 是围绕目标持续执行的逻辑角色，Harness 是让它实际运行的软件。** 模型可以提出调用工具，但真正发起请求、执行工具、保存状态和交回结果的是运行时。TaskLoom 主要介入这些执行入口；一个 Agent 不必对应一个操作系统进程。

定位与依据：PPT 第 11、14—15 页；项目说明书第 1.2.2、2.3 节。

#### 2.2.2 Q13｜★必备：为什么以根任务分配份额，而不是每个 Agent 各分一份？

**因为子 Agent 只是完成同一用户目标的分支，多开分支不应自动获得更多服务份额。** 我们保留根任务身份，把分支消耗归到同一个目标。平台再在用户份额内安排根任务，避免用户仅靠多开任务占便宜。合法并行仍然允许，只是不重置公平账目和预算。

定位与依据：PPT 第 11、20、23 页；项目说明书第 2.3.1、2.3.3、3.4.2 节。

#### 2.2.3 Q14｜Agent 的下一步不确定，你们怎么提前建立任务依赖图？

**我们只维护已经揭示的步骤和依赖，不要求提前知道完整任务。** 工具或模型返回结果后，运行时再生成后续步骤。例如测试失败才产生新修复步骤。预测可以辅助排序，但未知步骤不进入真实就绪队列，也不能按预测提前长期占住资源。

定位与依据：PPT 第 11、20 页；项目说明书第 2.3.4 节；依赖感知编排已有工作 [4]。

### 2.3 接入能力与调度信息

#### 2.3.1 Q15｜你们怎么接入现有 Agent？只做 API 代理就够了吗？

**只做 API 代理不足以管理本地工具，首版需要运行时的模型和工具两个受控入口。** 我们计划用适配器拦截实际调用，记录任务身份，再分别进入 L1 或 L3。对闭源 Harness，只使用它公开且可验证的接口，不承诺透明重排全部内部步骤。

定位与依据：PPT 第 14—15 页；原技术计划书第 1.4、2.2—2.3 节。具体运行时版本与接入覆盖率需在原型阶段确认。

#### 2.3.2 Q16｜★必备：平台只收到一段上下文，怎么知道它属于什么任务、谁更紧急？

**平台不能仅凭上下文可靠推断这些信息，需要运行时显式提供最小元数据。** 包括认证用户、根任务、步骤与尝试编号，以及类别、期限和请求规模。网关保存这些调度字段，再转发正常模型请求；用户本地的完整文件和未来全部步骤不必交给调度器。

定位与依据：PPT 第 23—24 页；原技术计划书第 2.3 节。会话关系不自动等于任务调度关系。

#### 2.3.3 Q17｜如果每个用户都自称紧急，或者故意低报成本怎么办？

**客户端声明只能作为受约束的信息，不能直接获得额外硬额度。** 用户身份由平台认证，紧急类别受用户份额和平台策略限制；请求成本在返回后用实际用量修正，低估形成后续欠账。严格预算还需可强制的单次消费上界，不能只相信预测值。

定位与依据：PPT 第 22—23 页；项目说明书第 3.3.2—3.3.3、3.4.1 节。

### 2.4 协同如何产生作用

#### 2.4.1 Q18｜★必备：举一个只有交换反馈才有帮助的例子。

**当平台派发会继续制造本地瓶颈工作时，端侧反馈可能减少无效积压。** 例如已知某类模型响应后要解析大量文件，而解析工具已经拥塞，就暂缓这类请求，仍让无关问答推进。释放后再恢复发送。这个判断依赖已知或可信的后继信息，是否优于两端独立优化仍需实验。

定位与依据：PPT 第 24、27 页；原技术计划书第 3.3 节。此例解释机制，不代表已取得收益。

#### 2.4.2 Q19｜两端不断调整，会不会来回振荡，甚至都等着对方？

**有这个风险，因此反馈不能追逐每一次瞬时波动。** 我们计划使用固定更新周期、平滑、调整幅度限制和有效期，保留必要探测机会；反馈过期时回退到保守独立策略。实验同时测管理开销、窗口波动和低负载表现，不预先宣称控制一定稳定或最优。

定位与依据：PPT 第 24 页；原技术计划书第 3.3 节。这些是拟采用的工程控制规则。

#### 2.4.3 Q20｜共享额度到底归谁管？状态最终一致会不会导致超发？

**共享上游额度由平台权威账本裁决，压力反馈不能代替硬授权。** 个人端控制自身任务、预算和发送节奏，不能各自重复分配同一份全局额度。压力摘要可以延迟；平台内的额度预留与结算必须原子、幂等。失联回退也不能绕过仍然有效的硬限制。

定位与依据：PPT 第 10、12、23—24 页；项目说明书第 2.1.3 节，原技术计划书第 2.3、3.2—3.3 节。

## 3. OS 机制与算法：为什么这样设计能够成立

### 3.1 本地工具准入与共享访问

#### 3.1.1 Q21｜为什么固定“最多并发四个工具”还不够？

**固定并发数无法表达不同工具的资源差异。** 一个解析器和一个高内存测试进程虽然都算一个工具，占用却可能相差很大。我们按当前步骤的内存预算、实例数和临时空间逐维检查，再原子预留；同时与调参后的固定并发比较，资源宽松时不预设一定更优。

定位与依据：PPT 第 17、27 页；PeakBench [2]；项目说明书第 3.1.1 节。

#### 3.1.2 Q22｜工具实际用多少内存，你们能预测准确吗？预测错了怎么办？

**我们不把预测当成硬保证，而是结合实测画像、预算和 OS 保护。** 画像辅助决定是否启动，cgroup 限制故障扩大；工具超过硬限制可能失败，因此要计入失败和重做成本。CPU 槽也只是逻辑许可，实际 CPU 时间仍由 OS 调度。资源申请无法拦截时，不纳入银行家的严格保证。

定位与依据：PPT 第 12、17、19、28 页；cgroup v2 [11]；OS 算法补充说明第 2.1、3.4 节。

#### 3.1.3 Q23｜让小工具先跑，会不会导致大工具永远排不上？

**会，因此允许绕过队首必须配合等待保护。** 我们记录等待时间和被绕过次数，合法大工具久等后，暂缓同类新工作进入，等待容量释放。但不能阻止已准入阶段取得完成所需的安全分配。保护可能损失短期利用率，所以要同时比较最长等待和吞吐。

定位与依据：PPT 第 17 页；项目说明书第 3.1.1 节。超过设备总容量的请求应拒绝或改写，老化不能让它变得可行。

#### 3.1.4 Q24｜锁顺序和优先级继承各解决什么？

**锁顺序预防循环等待，优先级继承缓解持锁者被其他任务拖延，两者不是同一个问题。** 多锁按统一顺序申请；紧急任务被低优先级持锁者阻塞时，只有知道拥有者且能影响执行，才提升其相关工作优先级。继承不解除真正死锁，也不允许绕过预算和容量上限。

定位与依据：PPT 第 19 页；死锁资料 [13]、RT-mutex [14]。普通应用锁不会因记录一个优先级字段就自动具备内核继承机制。

### 3.2 银行家算法的阶段化应用

#### 3.2.1 Q25｜★必备：任务动态到达、需求还会变化，银行家算法怎么用？

**动态到达本身不排斥银行家算法，关键是当前阶段有可信上限、申请受控且能结束归还。** 我们把检查单位限定为受控工具阶段，由 L2 提供阶段信息、L1 执行安全检查。新阶段可以登记；提高上限或改变容量必须重新核验，不需要预先知道整个 Agent 的未来。

定位与依据：PPT 第 18 页；Dijkstra [12]、死锁资料 [13]；OS 算法补充说明第 1—3 节。

#### 3.2.2 Q26｜★必备：用 PPT 中的例子说明，为什么最后一个名额不能直接给 A？

**因为给 A 后虽然没有立即超额，但已经无法保证存在安全完成顺序。** 总名额 3，A 最大需 3、已占 1，B 最大需 2、已占 1。再给 A 一个后，空闲为 0，A、B 都还可能需要 1 个；给 B 则能先让 B 完成并归还 2 个，再满足 A。不安全不等于已经死锁。

定位与依据：PPT 第 18 页；OS 算法补充说明第 2.4 节。A 再获得一个名额后，剩余需求是 1，不是 2。

#### 3.2.3 Q27｜运行中发现最大需求报小了，直接提高 Max 不行吗？

**不能直接提高，因为旧的安全判断依赖原声明上限。** 增加 Max 要作为状态变更重新检查；可选扩展被拒后可以按原计划结束。若旧上限已不足以完成，则需要安全停止、释放后重新准入；不能持有资源无限等扩容。无法安全退出时进入故障处理，并承认原保证失效。

定位与依据：PPT 第 18 页演讲备注；OS 算法补充说明第 3.1 节。均值或 P95 预测不能直接当作有保证的 Max。

#### 3.2.4 Q28｜一次拿齐资源已经能避免部分占有，为什么还要银行家算法？

**一次性申请已经足够时，就应优先用简单的原子准入。** 银行家主要用于确实需要分批取得可归还实例的受控阶段，检验能否减少过于保守的预留。我们会比较收益和检查开销；若没有增量，就把它保留为有明确适用边界的实验机制，不要求所有工具都经过它。

定位与依据：PPT 第 17—18、27 页；OS 算法补充说明第 3.2—3.3 节。小规模先采用朴素安全搜索，优化前先测开销。

### 3.3 模型请求排序与额度管理

#### 3.3.1 Q29｜为什么选成本 DRR，而不是 FIFO、最短任务优先或 WFQ？

**我们优先考虑可解释的成本公平和实现复杂度，DRR 是候选基础策略。** FIFO 不表达任务份额，短任务优先依赖耗时估计且需保护长任务；WFQ 也是合理对照。DRR 通过逐轮积累信用支持不同成本请求，再在份额内结合期限和老化；是否合适最终由同条件实验判断。

定位与依据：PPT 第 22—23、27 页；DRR 原始研究 [15]。不宣称 DRR 对所有 Agent 工作负载最优。

#### 3.3.2 Q30｜模型输出长度还不知道，DRR 的成本从哪里来？

**成本先用可观测输入和预测输出估计，再按实际用量修正。** 估计低了形成欠账，高了核销差额；子 Agent 不能借新身份重置账目。估计影响排序，但不能冒充严格预算上界。合法长请求还要能积累足够信用，不能被过小的信用上限永久卡住。

定位与依据：PPT 第 22 页；原技术计划书第 3.1—3.2 节。成本单位是明确的调度或合同单位，不是真实 GPU 执行时间。

#### 3.3.3 Q31｜★必备：RPM、TPM、并发和费用不是同一种“额度”吗？

**不是，它们的恢复方式不同，必须分开记账。** RPM、TPM 按服务商时间窗口或补充规则恢复；在途名额要等真实占用结束；费用一经消费就累计，不因失败自动返还。统一入口可以同时检查这些限制，但不能用一次“释放额度”把所有账目一起清零。

定位与依据：PPT 第 12、22 页；API 合同资料 [17]、[18]。不同提供商和端点的具体计量规则需分别适配。

#### 3.3.4 Q32｜用了 EDF 和 Aging，就能保证任务按时完成、永不饿死吗？

**不能无条件保证，因为外部请求通常不可无损抢占，耗时也不完全已知。** EDF 只在明确期限的候选请求中提供排序依据；Aging 改善长期等待，还需要足够份额和可行资源。持续过载、永久失联或需求超过容量时，要明确拒绝或等待，不能用优先级承诺无法满足的期限。

定位与依据：PPT 第 17、22—23 页；实时调度研究 [16] 的经典保证有特定模型前提。

### 3.4 依赖等待、取消与异常恢复

#### 3.4.1 Q33｜父 Agent 等子 Agent，会不会把执行槽占满，导致子任务跑不起来？

**会，这是需要显式避免的上层资源等待模式。** 父任务等待时释放已经不再使用的执行许可，但驻留内存、浏览器和锁继续计账。受检阶段不能拿着本域资源，等待一个未纳入模型且又依赖这些资源的子阶段；首版通过结束并释放父阶段后再启动子阶段处理。

定位与依据：PPT 第 20 页；项目说明书第 3.2.2 节，OS 算法补充说明第 2.1 节。

#### 3.4.2 Q34｜★必备：用户点了取消，为什么还不能立刻把资源和钱退回来？

**取消是控制请求，实际停止与计费结果还需要证据。** 本地工具可能留下后代，远端 API 也可能仍在运行；SIGSTOP 还会保留内存和锁。未派发预留可以按规则撤回，已经消费的费用不能抹去。无法确认的外部效果先保留 UNKNOWN，再查询核对，避免重复执行或超发。

定位与依据：PPT 第 12、21、38 页；cgroup 文档 [11]、API 合同 [17]、[18]。

#### 3.4.3 Q35｜有检查点和代次编号，就能保证恢复时只执行一次吗？

**不能，它们主要保证受控状态和结果发布不会被旧尝试覆盖。** 外部操作可能已发生，但完成记录尚未写回，因此恢复前还需查询结果、检查输入版本或利用对方的幂等接口。外部服务不支持这些能力时保留待核对，不能盲目重放；旧尝试真实产生的费用仍需结算一次。

定位与依据：PPT 第 21 页；工作流恢复能力 [7]；原技术计划书第 3.4 节。检查点不等于保存任意进程的完整执行现场。

#### 3.4.4 Q36｜守护进程和 IPC 在项目中具体做什么，如何证明不是摆设？

**守护进程独立核验受管执行，IPC 负责传递可驱动任务推进的真实事件。** 工具进程通过消息报告结果和退出状态，大输出传文件引用；取消事件与普通输出区分处理。我们会终止执行器并观察守护核对、残留回收和日志变化。心跳超时只触发检查，不能直接证明资源已经释放。

定位与依据：PPT 第 15、19、21、26 页；原技术计划书第 2.2、3.4 节。守护组件放在工具 cgroup 之外，账本修改在短事务或短临界区内完成。

## 4. 实验与实施：怎样证明有效，怎样完成课设

### 4.1 假设、基线与因果归因

#### 4.1.1 Q37｜H1—H4 为什么这样划分，分别要证明什么？

**四个假设分别对应需求中的公平、容量、协同和恢复，不是四个独立口号。** H1 检验根任务成本公平，H2 检验资源需求准入，H3 检验动态反馈增量，H4 检验故障后的状态与占用交接。整体方案对比之外，具体算法还要做开关消融，避免把全部收益归给单个机制。

定位与依据：PPT 第 6—7、27 页。需求映射为 R3→H1、R1→H2、R4→H3、R2→H4；H1 也涉及平台内根任务分配。

#### 4.1.2 Q38｜★必备：怎样证明“两端协同”确实优于“两端分别优化”？

**关键是比较 B11F 与 B11，只改变动态反馈。** B11 已启用两端候选策略，B11F 保持同样算法、静态身份、资源和预算，只增加规定的信息交换。B00、B10、B01 用来判断基础与单端增量；故障注入单独比较。只优于朴素基线，不能证明协同信息本身有价值。

定位与依据：PPT 第 7、24、27 页。B11F 的 F 表示反馈实验组，不是故障注入组。

#### 4.1.3 Q39｜你们如何避免把弱基线或模型随机性当成调度收益？

**先用同一任务轨迹隔离机制，再用真实 Agent 验证可用性。** 各组保留合理限流、重试、清理与质量标准，固定工作量和合同；真实运行采用重复、交错或配对比较，并记录轨迹差异。相同 prompt 不保证相同执行过程，排队时间与外部服务时间也要分开报告。

定位与依据：PPT 第 27—28 页；原技术计划书第 4.1 节。调参数据与正式评价数据分开，低负载和无收益结果同样报告。

### 4.2 指标定义与收益边界

#### 4.2.1 Q40｜★必备：什么叫“按时、合格完成”？模型说完成就算吗？

**不算，完成需要满足预先定义的期限和外部验收规则。** 代码任务跑既定测试，文档任务核对必要字段，资料分析检查来源与结论覆盖。拒绝和未完成任务保留在提交分母，尚未到期的单列或继续观察；无期限后台任务另报合格完成数量和时长，不能只统计成功者。

定位与依据：PPT 第 28 页；原技术计划书第 4.1 节。用户主动取消应单列原因，避免与调度失败混算。

#### 4.2.2 Q41｜短任务变快、长任务变慢，这样也能算改进吗？公平怎么量化？

**需要同时报告收益和代价，不能只挑短任务的漂亮数字。** 我们比较交互根任务 P95、长任务最长等待及相对独占执行的 slowdown。公平性按约定权重和有服务需求的对象衡量，Jain 指数要先说明输入量和统计窗口；原始 token 数相等不自动代表公平。

定位与依据：PPT 第 22—23、28 页。slowdown 的独占分母应对应同一工作轨迹，不能拿不同工作量的任务直接相除。

#### 4.2.3 Q42｜★必备：能提高多少？P95 降低 10% 有依据吗？

**目前不能承诺收益，10% 是候选工程目标，不是实验结论。** 我们会先确认测试集确有竞争，再冻结对照、阈值和评价口径，重点比较相对 B11 的增量。如果只有个别负载有效，就报告适用条件；如果反馈没有增量，也应据实保留独立方案，而不事后修改门槛。

定位与依据：PPT 第 28 页演讲备注；原技术计划书第 4.4 节。目标不得通过放宽质量、扩大预算或饿死后台任务获得。

### 4.3 数据、长期仿真与故障实验

#### 4.3.1 Q43｜为什么不用 TraceLab 直接重放全部真实任务，还要自己测工具？

**公开轨迹可以校准分布，但不能代替原始任务和本机资源画像。** TraceLab 删除了原始工具输入输出，也不提供本项目需要的主机 CPU、内存需求轨迹。我们会用它校准到达、调用类型、token 和耗时，再实测受控工具并设计有明确答案或测试标准的任务。

定位与依据：PPT 第 28 页；TraceLab 的脱敏和数据范围说明 [1]。不能从调用耗时直接推断 CPU 占用。

#### 4.3.2 Q44｜把系统模拟运行一个月，怎么保证结果有说服力？

**月度仿真必须由短期实测校准，并保留真实的依赖、容量和额度恢复规则。** 我们先比较仿真与实测在相同负载下的表现，再扩展到 30 天，观察交付、费用和异常积累。多种随机种子与参数敏感性分析用于说明稳定程度；仿真结果明确标注，不冒充连续运行一个月的实测。

定位与依据：PPT 第 28 页；项目说明书第 4.3.4 节。不能只加快请求到达来制造有利拥塞。

#### 4.3.3 Q45｜故障实验怎样判定成功？“不一致率低于 5%”可以吗？

**已定义的安全不变量不能靠允许 5% 错误来验收。** 我们在受支持的故障集合中检查超发、重复释放和旧结果覆盖，另测清理时延、自动核对成功率和 UNKNOWN 比例。进程崩溃、断连、工具超时或资源耗尽都需要真实注入；无法确认可以保留未知，不能计作成功恢复。

定位与依据：PPT 第 21、27—28 页；原技术计划书第 4.2、4.4 节。保证范围以受控工具、明确合同和故障集合为准。

### 4.4 实施可行性与延伸判断

#### 4.4.1 Q46｜★必备：这么多机制，课程周期内能做完吗？最小版本是什么？

**我们先做有限范围的任务闭环，再增加有证据支持的扩展。** 最小版本包含一个可修改运行时、受控工具、统一模型入口、应用网关、状态记录与独立守护。先实现简单公平和原子准入，再加入反馈、阶段银行家或继承实验。按运行时、本地执行、请求平台、实验界面四个工作包衔接。

定位与依据：PPT 第 15、29 页；项目说明书第 4.4 节。首版不承诺兼容全部商业 Harness 或所有操作系统。

#### 4.4.2 Q47｜调度器会不会比直接运行更慢？如果协同没有效果，项目还有价值吗？

**会有管理开销，所以低负载与无收益条件也是必须报告的结果。** 我们测 CPU、消息与排队开销，用轻量事件和短临界区控制成本。若反馈不如两端独立策略，就收窄协同主张；可解释的资源准入、正确回收和实验结论仍有课设价值，但不能继续声称协同带来加速。

定位与依据：PPT 第 24、27—30 页；项目说明书第 3.4.4、4.4.4 节。增加机制需要收益依据，不能只以功能数量评价完成度。

#### 4.4.3 Q48｜你们现在已经实现了什么？答辩时有哪些内容不能说成已经完成？

**按当前开题材料，可以确认的是调研、需求、架构、算法边界和实验设计，性能收益仍待原型验证。** 我们只用可运行代码、日志和原始数据证明实现进度；图示、界面规划和论文数字不算本项目结果。后续若有新增实现，答辩前据实更新这一回答，不把计划自动改成完成。

定位与依据：当前 PPT 第 1、26、28—30 页的开题口径。本文件不替代代码验收，也不预先宣称已独立复现社区故障。
