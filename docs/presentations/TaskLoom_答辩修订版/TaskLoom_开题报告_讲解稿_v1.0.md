## 第一章：快速交代痛点与研究依据

### 第 1 页｜封面

各位老师好，我们的项目是 TaskLoom「织序」，面向 Agent 多任务的个人端与平台协同调度系统。

我们关注一个问题：当多个 Agent 任务同时运行，本地工具和模型请求都受到资源限制时，怎样安排它们的执行顺序，让有限资源支持更多任务及时完成。

### 第 2—3 页｜汇报路线与项目全景

本次汇报沿四个问题展开：首先说明问题从哪里来，再介绍系统怎样组成，重点解释四层调度采用的 OS 方法，最后展示当前实现与对照实验。

可以先把项目理解为：以完整任务为单位，协调它在本地工具和远程模型之间的多次往返，并保留每一步的等待、执行和消费记录。

### 第 4—5 页｜立项背景

Agent 完成一项工作，往往需要先请求模型，再读取文件或执行命令，之后继续请求模型。一个人同时开几个任务，就会出现两类竞争：本机的工具资源竞争，以及个人账号下的模型调用机会竞争。多个用户连接同一平台时，还会出现平台共享名额的竞争。

这些工作差异很大。简单提问可能很快结束，资料分析需要读取多个文件，代码任务还可能运行较长的命令。统一限制任务数量，只能控制“同时有几个”，还需要进一步判断“每个占用多少、谁应该先执行、执行结束后怎样回收”。

### 第 6—13 页｜调研广度与关键结论

[翻页提示：第 6 页先停留，再快速翻过论文、Issues 和实践页面。]

我们的调研分成三类。

论文方面，TraceLab 帮助我们认识工具耗时的差异；PeakBench 提醒我们同时考虑依赖与资源容量；HiveMind 则提供了模型请求准入、限速和预算管理的已有方法。[1—3]

工程问题方面，我们查看了 OpenClaw 和 Codex 的具体 Issues，关注数量限制下的内存压力、退出后的进程清理，以及重负载下的控制响应。[4—6]

开发实践方面，Anthropic 和 Cursor 的经验进一步说明，并行任务需要配套检查点、消费记录和较短的持锁时间。[7—8]

这些材料共同指向：**任务数量、实际资源占用和完整任务的完成效果，需要一起管理。**

### 第 14—15 页｜需求归纳与研究目标

我们把需求归为四类：资源要承受得住，任务结束要有据可查，请求之间要有公平次序，两端要能交换有效状态。

对应到项目，我们已经建立了工具准入与资源账本、任务检查点与取消回收、个人和平台的分层公平调度，以及基于平台状态的请求背压。

评价时保持模型和资源条件一致，观察短任务等待、后台任务推进、预算占用和完成情况。这样才能把改进落实到使用者能感受到的响应速度和任务交付。

### 第 16 页｜项目实现路线

为了控制任务入口、请求排序和工具启动，我们自研了轻量 Agent 运行时与调度核心。现有系统已经形成“模型提出操作、本地执行工具、结果返回模型”的完整循环。

接下来介绍这条循环怎样穿过个人端和平台端。

## 第二章：讲清系统、架构与功能

### 第 17—18 页｜总体结构：同一系统，两端四层

TaskLoom 是一套两端协作的系统。

个人端运行在用户设备上，管理任务和本地工具。平台端面向多个账号，管理共享的模型调用机会。个人端使用 TaskLoom 平台账号的 API Key，平台再连接固定模型服务池。

我们按职责划成四层：L1 管本地工具资源，L2 管 Agent 任务推进，L3 管当前用户的模型请求顺序，L4 管平台多用户请求分配。

四层之间有两条主要路径：工具操作从 L2 交给 L1；模型请求从 L2 经过 L3，再由 L4 分配共享服务名额。结果回到 L2，任务继续推进。

### 第 19 页｜以一项资料任务说明输入与交付

以“分析附件并统计资料”为例。用户在聊天界面输入要求、上传文件，系统为本次工作建立根任务，记录它的期限、预算和优先级。

Agent 请求模型判断下一步。模型提出读取或统计操作后，工具在用户自己的设备上执行，结果进入后续上下文。模型再根据结果组织回答，界面展示回复、步骤和消费记录。

当前已经支持普通多轮对话、文本与图片附件，以及六类本地工具。个人端和平台端可以沿同一调用链使用真实模型。

### 第 20 页｜对象模型：每次执行怎样归属

系统首先用根任务记录用户要完成的工作，再用步骤记录其中一次具体操作，用尝试记录这一步的一次实际执行。

例如，“分析课程资料”是根任务，“读取文件”是步骤，这次读取成功或失败都形成一条尝试记录。重试会建立新的尝试，重复传输则沿用原请求身份。

这样设计有两个作用：调度和预算能归到完整任务，每次真实执行又能单独追踪。当前运行时主要推进单 Agent 的多轮步骤，模型每次揭示下一步后，系统再安排执行。

[翻页提示：跳过第 21 页计划类图，进入第 22 页。]

### 第 22 页｜模块怎样配合

四层按照一个任务的生命周期交接工作。

L2 保存对话和步骤，判断当前需要模型还是工具。需要工具时，L1 检查工具名额、内存和产物空间，再启动进程。需要模型时，L3 在当前用户的各个根任务之间选择请求，L4 再在多个用户之间分配共享名额。

结果完成后，执行事实和消费回到相应账本，L2 根据结果继续工作。这样，任务推进、资源准入和请求排序各司其职，并通过统一身份连接起来。

### 第 23 页｜浏览器怎样调用本地工具

个人端采用“浏览器界面加本机服务”的结构。用户在网页中操作，本机 Python 服务负责任务管理，独立执行器通过 Unix socket 接收工具请求，再启动真实工具进程。

因此，文件读取和命令执行由本机服务完成。系统还为工作区外或敏感路径读取、每条命令执行设置操作确认。

执行器记录进程身份并持续收集输出，监督进程协助确认退出。配置可写的 cgroup v2 目录后，还能限制工具的内存、CPU 和进程数量，并采集实际占用。

### 第 24 页｜两端如何处理一次模型调用

个人端提交模型请求后，平台先保存请求身份和派发事实，再调用模型服务。返回结果后，平台记录实际消费并释放相应预留。

如果网络中断，平台会保留原请求身份和已有事实，进入核对状态。这样可以追踪这次请求是否执行，以及对应消费是否已经结算。

这条路径把请求排序和可靠性连在一起：只有资源与账本反映真实执行，后续请求的分配依据才准确。

目前的个人端已经具备会话管理、多轮聊天、附件上传、技能选择、操作确认，以及任务优先级调整。工具包括文件读取、命令执行、资料统计、文件列表、文本检索和高频词统计。

## 第三章：沿四层讲清算法与实践

### 第 26—27 页｜本章主线

这一章继续沿同一个任务展开：先解决工具能不能启动，再解决步骤怎样推进和结束，然后处理个人模型请求的竞争，最后处理平台多用户的共享分配。

每一层都回答三个问题：管理什么资源，按什么规则决策，以及怎样从运行记录观察决策效果。

### 第 28 页｜L1：可行选择，缓解队首阻塞

先看本地工具。假设总内存预算是 8 GiB，当前剩余 4 GiB。队首工具需要 6 GiB，后面的小工具只需要 2 GiB。

如果一直等待队首，剩余内存就会闲置。当前调度器会继续寻找资源条件满足的工具，让小工具先运行。图中小工具的等待由 8 个时间单位降为 0，整体结束时刻保持一致。

这体现的是资源约束下的可行选择：**按当前可用资源决定谁能启动。** 当前主链具备这项选择能力。

### 第 29 页｜L1：多资源原子准入

可行判断同时检查三项资源：工具名额、内存预算和产物空间。

每种工具都有资源画像。例如，文件列表工具声明 64 MiB，读取文件和运行命令声明 256 MiB。它们是调度前使用的资源预算，实际占用由执行侧另外记录。

三项都满足，系统才一次性预留。暂时超过剩余量的工作等待，超过总容量的工作直接拒绝。预留完成后再启动工具，避免一边占住部分资源、一边等待其他资源。

这里还结合了**加权轮转 WRR**。高、普通、低优先级按 4∶2∶1 分配工具派发机会，同档内部再按根任务轮转。可行判断负责“现在能不能跑”，轮转负责“能跑的任务谁先获得机会”。

工具完成或确认停止后，资源回到池中，调度循环被唤醒，再检查下一批候选。

### 第 32 页｜L1：共享访问组件怎样减少冲突

这一页对应已经实现的独立并发组件，按组件样例说明。

single-flight 处理重复初始化：两个调用者同时申请同一项准备工作，由组件只执行一次，双方等待同一个结果。一个等待者取消后，共享操作仍可为其他等待者继续服务。

读写锁允许多个读取者并行，写入时独占资源；有序锁则要求多个资源始终按相同顺序加锁，消除反向加锁形成的循环等待。

这些组件分别处理重复工作、读写冲突和锁顺序问题。主链中已经使用异步锁、短事务和文件拥有者锁管理共享状态，长工具执行和网络等待安排在临界区之外。

### 第 33 页｜L2：依据结果推进任务

L2 负责把用户目标推进为可执行步骤。当前运行时先调用模型，保存模型返回的工具操作，再依次执行这些操作，将回执放回上下文，最后进入下一轮模型请求。

每次模型返回和工具完成后都会保存检查点。因此系统知道：当前到了哪一轮，哪些工具已经完成，还有哪些操作等待执行。

工具等待、模型等待和用户确认分别交给对应机制处理。不同根任务可以并发推进，每个任务仍保留自己的上下文和执行身份。

这样，调度器只需要安排已经明确的工作，任务未来的步骤由后续模型结果逐步揭示。

### 第 34—35 页｜L2：阶段银行家算法的组件实现

银行家算法目前已经实现为独立资源安全检查组件。它管理声明过最大需求的、执行结束后可以归还的资源。

普通容量检查只看“现在够不够”，银行家进一步检查“分出去以后，是否还能找到所有阶段依次完成的顺序”。

看这个例子：总名额为 3，两个阶段各持有 1 个，还剩 1 个。阶段甲最多需要 3 个，阶段乙最多需要 2 个。把最后一个给甲，双方都还缺资源；给乙，乙就能完成并归还名额，随后甲也能完成。因此组件允许后者，拒绝前者。

代码通过试分配和安全序列搜索完成判断。已有阶段修改最大需求时，也先检查新状态，检查失败就保留原分配。这里把银行家的安全状态思想用于有声明上限的阶段资源，为动态任务保留了重新声明和检查的入口。

### 第 37 页｜L2：把“任务结束”拆成可核对的事实

任务生命周期中，一个状态标签往往表达不全。例如，用户已经点了取消，工具进程可能还在退出；界面失去连接，模型调用也可能已经发生消费。

因此，当前系统分别记录工作进度、任务结果、物理执行是否静止，以及消费是否结算。

这样，系统能区分“用户不再需要结果”“执行已经停止”和“账本已经结清”。调度器根据这些实际状态决定何时归还资源，恢复流程也能找到尚未完成的收尾工作。

### 第 38 页｜L2：取消、进程回收与检查点恢复

取消时，系统先保存取消意图，再通知执行器停止。执行器先发送 SIGTERM，必要时再使用 SIGKILL，并根据进程组或 cgroup 确认实际退出。

确认停止后才归还对应预留。进程身份同时记录 PID、启动时刻和系统启动标识，帮助监督过程识别原执行。

模型侧同样保留尝试与请求身份，实际消费按尝试结算，旧结果发布前检查当前代次和输入版本。重启时读取持久记录，沿原身份核对未结束的执行。

这部分把 OS 的进程管理、通信、互斥和恢复机制连接起来，保证资源回收有真实执行事实作为依据。

### 第 39 页｜L3：按根任务进行成本公平调度

接下来是个人端模型请求。多个任务都在请求模型时，简单按条数轮转，会让一次大请求和一次小请求获得同样一轮机会，却占用不同成本。

我们采用**成本赤字轮转，也就是成本 DRR**。每个根任务逐轮积累信用，请求成本由所属任务承担。普通轮转中，信用积累到能支付请求时，就获得派发机会。

图中每轮增加 2 个单位。大请求成本为 6，需要积累三轮；小请求成本为 2，每轮都能发送。大请求保留跨轮信用，小请求也能持续前进。

派发时按预计费用记账，结果返回后按实际消费校正。预计 6、实际 8，就补扣 2；多预留的部分则退还。Token 数、费用和并发名额分别计量，避免不同资源单位混用。

公平账本归属根任务，并在任务的多轮模型调用之间延续，使一个完整任务的成本能够连续计算。

### 第 39 页补充｜L3：期限、老化与手动优先级

成本公平还要结合使用体验。系统对临近期限、等待较久和手动设为高优先级的请求提供有界提升。

当前配置中，距期限 60 秒内进入紧迫范围，等待超过 20 秒进入老化范围。连续提升最多两次，随后恢复正常轮转；提升的请求仍承担相应成本。

这样，紧急任务可以更早获得机会，普通轮转也能继续运行。已经过期的等待请求进入明确终态，暂时额度不足的请求留在队列中，其他可行任务继续选择。

用户可以在界面调整任务优先级。工具侧改变后续轮转档位，模型侧改变等待请求的提升次序，运行中的操作保持当前执行。

### 第 40 页｜L4：先分用户，再分用户内的任务

到平台层，公平对象增加了一层。平台先在账号之间选择，再选择账号内部的根任务，最后检查账户、根任务和全局额度，取得共享模型池的名额。

目前已实现四种策略。默认 RR 按用户和根任务轮转；maxmin 优先照顾当前占槽较少的一方；界面中的 drr 按已经获得的槽位服务时间排序；hybrid 先比较当前占槽数，再比较已经获得的槽位时间。

这里要统一计量口径：个人端 DRR 使用费用信用，平台 drr 使用占槽时间。两者分别对应账号内的成本分配和多用户的服务占用。

平台对请求时长采用指数加权移动平均，也就是 EWMA：每次完成后，用新的耗时修正估计。运行中的请求按“估计耗时与已运行耗时中的较大值”计入占用，帮助调度器在结果返回前考虑它已经使用的服务。

管理员可以切换策略，观察后续派发。模型池容量保持固定，比较的是相同服务能力如何分配给不同用户和任务。

### 第 40 页补充｜L4：准入、预算与重试

排序之外，平台还统一检查共享并发、账号并发、请求窗口、Token 窗口和费用预算。派发前预留，完成后按回执结算，同一账号的多个 Key 共用账号额度。

预算保护按配置价格和请求上限计算费用上界，同时保留基于历史消费的预计值。费用以平台预算单位计量，实际 Token 用量来自模型回执。这样，安全准入和消费估计分别承担自己的职责。

如果上游明确拒绝且确认没有执行，平台采用有上限的指数退避，再安排重试。已发送而结果未知的请求保留原身份和相关预留，进入核对流程。

因此，平台调度同时回答“谁先获得服务”和“这次服务是否满足容量与预算约束”。

### 第 41 页｜两端协作：已实现的平台反馈背压

个人端在发送请求前，会读取平台反馈：当前账号有没有可用额度，平台是否允许继续提交，排队数是否达到建议上限，以及需要等待多久。

反馈有效时，个人端据此选择提交、等待或拒绝。单个大请求暂时额度不足，只影响它自身，其他根任务仍可被选择；账号整体受限时，则让整个发送过程等待。

反馈带有原始观测时间，超过 5 秒会被视为陈旧。系统短期复用快照减少查询，并在需要时重新读取。

这项基础背压使个人端能根据平台真实状态安排发送时机，也为观察本地等待和平台等待提供了明确记录。

### 第 42 页｜把四层机制连成完整工作过程

四层方法可以用同一个过程串起来：工具启动前，用资源向量和加权轮转决定准入；执行中，用独立进程、通信和同步管理状态；执行结束后，用取消核对和检查点恢复保证回收；模型侧再用个人成本公平、平台两级分配与反馈背压安排请求。

我们的实践特点是把这些方法落实在 Agent 的完整执行链里。用户看到的是任务更有序地推进，系统保留的是每次排队、占用、执行和结算的依据。
