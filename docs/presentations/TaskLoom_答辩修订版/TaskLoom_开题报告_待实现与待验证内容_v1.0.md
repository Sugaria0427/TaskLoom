# TaskLoom 开题报告：待实现与待验证内容

版本：v1.0 · 核对日期：2026-10-28。

本文与[讲解稿](TaskLoom_开题报告_讲解稿_v1.0.md)配套，按“执行链补齐、算法接入、实验与证据、PPT 状态同步”四部分整理。范围以当前本地代码为准，供后续开发和答辩准备使用。

## 1. 执行链需要补齐的能力

### 1.1 并行子 Agent 与通用依赖图

**当前已有：** 多个根任务可以并发推进；单个任务支持多轮模型—工具循环，保存待执行工具、回执和检查点。同一轮多个工具目前按队列逐项执行。

**尚需实现：** 在同一根任务下创建和监督多个子 Agent，建立依赖边、汇合屏障、分支失败与取消传播，并控制父任务等待时的许可交接。

主链需要始终保留根任务归属：分支继承预算和公平份额，分支扇出不能凭数量获得额外份额。还需明确失败分支对汇总步骤的影响，以及恢复时如何识别已完成分支。

**对 PPT 的影响：** 第 20 页按当前 Task—Step—Attempt 关系讲解；第 21 页完整类图和第 33 页双子 Agent 汇合图属于后续架构。讲解稿用已实现的顺序依赖推进解释第 33 页。

### 1.2 工作区共享资源的完整管理

**当前已有：** 工具注册、画像、进程执行、路径确认、有界输出、输入版本检查，以及 single-flight、读写锁和有序锁组件。

**尚需实现：** 把这些访问组件接到真实共享工作区，例如共享索引的初始化、文件读写协调、修改与测试的依赖关系，以及多任务共用产物时的生命周期。

接入时要先定义共享资源键、拥有者和销毁条件，保证单个等待者取消后，其他使用者仍能继续工作。当前可以讲组件原理和已有样例，整体共享工作区收益需在接入后测量。

## 2. OS 算法与协同机制需要补齐的部分

### 2.1 阶段银行家的主链接入

**当前已有：** `PhaseBanker` 支持最大需求声明、试分配、安全序列搜索、释放、动态最大需求更新检查，以及关闭安全检查的贪心对照。

**尚需实现：** 让运行时为真实阶段提供可信最大需求，将阶段申请和归还接入工具调度器，并在同一状态所有者下完成检查与提交。还需处理阶段变更、并发申请、未知执行和重启恢复。

当前 L1 工具采用一次性多资源预留。银行家的应用场景应选择“已持有部分可归还资源、后续仍需继续申请”的阶段，使安全检查能对应真实循环等待风险。

**展示口径：** 第 34—35 页讲已实现的算法组件与资源例子；完整阶段安全接入作为后续开发项。

### 2.2 大工具的接纳保护

**当前已有：** 可行工具选择能绕过暂时无法启动的队首；工具优先级三档按 4∶2∶1 轮转。

**尚需实现：** 当轻工具持续到来时，为等待中的大工具建立接纳保护，例如达到等待阈值后逐步保留所需资源，并规定旁路次数、等待阈值或保留比例。

需要测量轻工具响应与大工具最长等待之间的取舍。L3 已有模型请求老化，L1 大工具资源接纳保护应独立设计。

**对 PPT 的影响：** 第 28 页“可行轻工具先行”已有代码；同页“大工具老化和接纳保护”仍需接线和持续竞争实验。

### 2.3 First Fit 与 SCAN

| 设计 | 当前状态 | 后续实现应解决的问题 |
| --- | --- | --- |
| First Fit 动态分区 | 当前代码未实现对应分区分配器。 | 如保留该方向，应建立由应用管理的解析缓冲区，真实进行空闲块分割、回收、相邻合并，并与固定分配等策略比较碎片和开销。 |
| SCAN 磁盘调度 | 当前代码未实现相应块位置模型或队列调度。 | 如作为课程扩展，应在具备块位置的教学模型中比较寻道距离，明确任务模型与介质条件。 |

**建议顺序：** 先补齐四层任务调度主线，再决定这两项扩展的价值。第 30—31 页从本次讲解中跳过，第 42 页课程对应表暂不逐行介绍这两项。

### 2.4 更完整的压力反馈控制

**当前已有：** 平台反馈包含额度、并发、队列、建议待办上限、重试时间和观测时刻；L3 使用有效快照进行提交、等待或拒绝，区分账号级和请求级阻塞。

**尚需实现或验证：** 识别任务下一阶段会使用的本地资源，把相关本地压力与平台状态结合，形成可解释的动态发送窗口，并在延迟反馈下验证平滑、恢复和振荡行为。

当前可确认的成果是基础反馈背压。第 41 页完整自适应窗口曲线的稳定性与增量收益，需要配对实验给出证据。

## 3. 性能与产品对照需要补齐的证据

### 3.1 原版 OpenClaw 对照与五组消融

**当前已有：** 自研运行时、真实模型接入、六工具执行、个人与平台策略，以及独立对照计算页面。

**尚未完成：** 固定版本的原版 OpenClaw 产品对照，以及 B00、B10、B01、B11、B11+FB 五组统一控制实验。

当前实验页比较三种组合：两端 FIFO、本地 FIFO 加平台 RR、TaskLoom 本地组合加平台 hybrid。五组实验需要进一步独立切换个人策略、平台策略和反馈，同时保持账号、容量、任务和调用路径一致。

**对 PPT 的影响：** 第 46—47 页作为后续实验方案，正式讲解跳过。现有三组实验在第 48—49 页介绍。

### 3.2 真实任务的质量与改善幅度

**当前已有：** 执行轨迹、用量与资源记录、统计技能的真实数字核验，以及接收外部质量判断的指标汇总接口。

**尚需补齐：** 代码、资料分析、问答等不同任务的固定验收规则与成组质量结果，再计算按时合格完成率。

现有仿真报告按设定期限计算按时完成率。资料统计技能能够核验统计回执，普通开放式回答还需要具体质量规则。系统性能改善百分比以保存的当次实验结果为准，汇报中不预填目标收益。

### 3.3 实测校准与长时间外推

**当前已有：** 采集、校准和仿真基础工具，以及支持最长 30 天、多种子重复的合成负载对照页面。

**尚需补齐：** 统一真实场景的阶段轨迹，将模型服务时间、平台排队时间和本地工具时间分离，保留真实阶段数量与依赖，再校准长期模型。

当前三阶段合成模型尚未覆盖网络、故障、Token 窗口和反馈控制。长期结果应先表述为“设定负载下的仿真”，真实月度交付收益由后续校准和实测支持。
