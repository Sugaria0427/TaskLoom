### 1.3 版式与颜色怎样阅读

UML 视图中的青绿、蓝、琥珀与紫色分别对应本地资源、任务管理、客户端请求和平台调度。灰色表示外部系统或共用支撑，珊瑚色用于异常处理与核对。层次名称直接写在对应模块中，不再占用页底绘制图例。思维导图按四个叙事主题着色，以分支标题直接说明主题。

插入 PPT 时保留原始比例，不要把 4∶3 的部署图强行拉伸为 16∶9。图片已经取消额外副标题和页脚，可按图形有效内容安排版面。SVG 使用原生文字，不使用 `foreignObject`；换到没有微软雅黑字体的设备时，优先使用 PNG 或已嵌入字体的 PDF。

## 2. 这套模型保留的项目边界

### 2.1 两个场景与四层职责

个人端包含 L1 本地资源与工具执行、L2 Harness 与任务管理、L3 客户端模型请求调度。每位用户有自己的个人电脑，多个任务在该电脑内共享受管工具资源和个人预算。

平台端只包含 L4 多用户请求调度。这里的平台是本项目可控制的应用 API 入口，负责接纳、排队、公平分配和派发请求；不假设能够接管商业模型服务商的内部调度。

模型能力、推理资源与服务配置在比较中保持不变。本项目不管理 GPU、KV cache、推理批处理或模型切换。个人端调度“自己的哪个请求先发送”，平台端调度“哪个用户的请求先派发”，两端通过任务身份与必要的压力信息协作。

### 2.2 任务与资源的归属

根任务是公平分配和最终交付的归属单位。子 Agent 形成无环的执行分支关系，派生数量不会自动增加根任务的服务份额。工具步骤与模型步骤都继承抽象步骤，当前依赖可以随执行逐步展开。

一次执行尝试属于一个步骤。重试创建新的尝试，结果版本阻止旧尝试覆盖新结果，但旧尝试真实产生的费用仍需独立结算。类图中的字段为领域模型，不代表已经冻结的代码接口；例如 `parentId` 表示父 Agent 的标识。

阶段声明由具体工具尝试拥有。一个工具尝试可以先后经历多个阶段，因此 `Attempt` 到 `StageClaim` 的多重性为 `0..*`；模型步骤没有此类声明，只有当前有效阶段进入资源安全检查，历史阶段保留在记录中。产物与产生它的尝试使用普通关联，避免把“清理尝试记录”误解为可以删除仍被使用的结果。

### 2.3 结束、回收与结算互相独立

状态机描述执行状态，不把“结果已知”“资源已回收”“费用已结清”合并成一个完成标志。执行结束之后，产物引用与费用核对仍可能继续存在。

取消时先记录取消代次，再经执行器发起停止。独立守护进程通过操作系统接口核验自有进程组与 cgroup；即使原执行器失效，也不能仅依赖它的主动汇报判定清理成功。图中的两个 `alt` 分支互斥：确认退出才归还对应许可，无法确认就保留占用并继续核对。

远端请求适用相同的证据原则，但其停止与收费需要另外查询，不能把本地进程退出协议直接套用到服务商。网络超时、请求取消或租约到期都不能单独证明远端未执行。

### 2.4 银行家检查的适用条件

银行家检查只覆盖可信最大需求、可统一拦截申请、能够完成或安全终止并归还的资源阶段。首版使用工具或浏览器实例等可归还许可；内存预算和 cgroup 是另外的保护手段，RPM、TPM、费用和已消耗 token 不进入银行家矩阵。

活动图先取得一致快照和版本，再检查 `Request ≤ Need` 与 `Request ≤ Available`。前者不满足，需要拒绝当前声明之外的申请；后者不满足，可以等待容量变化。扩大阶段上限属于额外的受检状态变更，不能直接修改账本数值。

试分配后执行标准安全搜索：令 `Work = Available'`，逐次找出满足 `Need_i' ≤ Work` 的未完成阶段，并令 `Work += Allocation_i'`。只有所有阶段均可假想完成，才存在安全序列。试算不修改真实账本；提交前版本改变必须重新取得快照并检查边界。真正的等待注册与资源事件唤醒也必须原子衔接，避免遗漏唤醒。

安全性是分配许可的条件，不取代公平排序，不保证期限，也不证明外部计算一定成功。大工具的等待保护不能阻止已准入阶段取得完成所需的安全分配。遇到原最大需求已无法满足实际完成条件的情况，必须安全停止、释放并重新准入，不能占着资源无限等待。

## 3. 软件工程记法与视图间的一致性

### 3.1 需求与组件的对应

提交运行、查看进度与交付结果、取消、恢复续作及目标配置均为个人用户可以直接发起的独立用例。查看正常任务结果不依赖取消。取消包含清理状态核对，恢复包含检查点与已有结果核验；平台管理员独立查看平台负载并配置份额。`«include»` 指向所包含的行为，不表示前后时序或部署包含关系。

组件图的虚线开箭头表示依赖，读作“这个组件使用另一个组件的能力”。工具与模型请求是两条分支，不能把四层误画成所有工作都要依次穿过的流水线。该视图为了说明四层分工省略部分持久化依赖，并不意味着 Harness 或平台不写入状态记录。

### 3.2 类与部署的对应

类图中的实心菱形位于整体端，空心三角指向抽象父类，端点数字表示关联多重性。为了突出核心领域对象，类图省略方法区和适配器实现类；省略方法区符合 UML 类图的表达范围，并不意味着对象没有行为。

部署图的设备节点承载执行环境，程序模块与持久化文件使用制品标记。用户个人电脑中明确展示 L2 任务管理、L3 客户端请求管理、L1 本地资源与工具执行，平台服务器中明确展示 L4；通信路径连接运行环境。独立守护进程位于工具执行域之外。图中 L1 是资源管理与工具执行环境，只有其中受管工具受到相应 cgroup 限制，不表示所有控制组件必须放入同一个工具 cgroup。

### 3.3 时序与状态的对应

时序图从上向下表示时间。实线实心箭头表示同步调用，实线开箭头表示异步调用或通知，虚线开箭头表示应答；不把“异步”画成“虚线”这一错误规则。取消图开头的持久化调用按同步完成处理，后续停止消息在其完成后发出。

正常请求图和工具分支图分别展示一条成功交互，不声称覆盖全部异常分支。取消图展示已进入工具执行流程的情形；尚未派发的取消由状态机中的等待到清理路径覆盖。状态机的终态结束本次执行尝试，费用与结果交付仍按独立账本管理。

### 3.4 用什么证据评价设计

最终效果以相同模型、资源、预算和质量标准下的完整任务交付衡量。对照应包含基础方案、仅个人端改进、仅平台改进、两端独立改进及两端动态协同；最后两组保持相同静态信息和调度规则，只改变动态反馈。

按时合格完成率、交互任务等待、公平性、实际费用及异常残留需要一起报告。可靠性修复与排序收益分别评价；月度仿真先用真实测量校准，不预先承诺没有实验依据的提升比例。

## 4. 依据、编辑与复核

### 4.1 设计依据

本图集直接依据 [分层项目说明书](../TaskLoom_项目说明书_分层清晰版.md)及 [OS 算法补充说明](../TaskLoom_OS算法补充说明.md)。文献与问题单的证据边界沿用上述文档，图示不会将社区报告扩展为普遍缺陷。UML 记法以 [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1) 的通用语义为依据。

### 4.2 可编辑文件怎样维护

使用 diagrams.net 或 draw.io 打开多页源文件即可编辑。建议先在多页文件中完成修改，再同步独立单图；不要把修改后的源文件和修改前的图片混合交付。

模型编写与渲染程序位于[图集编写工具](../../agent-workspace/scripts/pictures/README.md)，只服务于当前图集。可编辑文件独立于构建环境，打开和修改它不需要 Python、Node 或联网。重新执行模型生成会按本次模型定义重建页面，因此手工编辑源文件后，应先决定保留手工版本还是同步生成定义。

### 4.3 复核材料

[图集检查记录](../../agent-workspace/outputs/pictures/qa/)保留原生渲染器输出的节点、标签边界和连线路径，结构验证记录，以及最终文件检查结果。文字、图片和 PDF 的检查均针对实际导出结果，不仅检查 XML 是否能够解析。

本图集只验证建模表达、可编辑性和出版质量，不构成 TaskLoom 的实现验证或性能测试。
