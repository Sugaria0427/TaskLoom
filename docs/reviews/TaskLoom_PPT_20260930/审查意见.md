# TaskLoom「织序」开题 PPT 内容与流程审查

**审查文件：**`TaskLoom_正文放大版.pptx`，共 40 页。**审查日期：**2026 年 9 月 30 日。页码均指文件中的实际顺序，包含封面和章节页。

**审查结论：**选题、两端四层的范围和四章结构可以保留，但当前版本需要先修正技术语义、图文一致性与实验对照，再用于正式答辩。最严重的问题包括银行家例子的算术错误、将暂停和终止等同于资源释放，以及将 B11F 改成故障组后失去对协同收益的直接验证。材料数量充分，当前主要工作是统一表达与证据边界。

本次读取了全部页面正文及演讲备注，使用 PowerPoint 只读导出检查实际画面，并与项目说明书、算法补充说明和已有归档证据核对。审查未修改原 PPT，未把附件内的文字视为执行指令，也没有重新开展一轮全面文献调查。

## 1. 必须先修正的技术内容

### 1.1 第 25 页：银行家算法例子的剩余需求算错了

当前写法是：“若给 A 分配剩余 1 个：A 还需 2，B 还需 1 → 不安全”。A 在原来已占 1 个的基础上再获得 1 个，已占应变为 2；最大需求为 3，所以剩余需求为 **1**。

| 状态 | Available | A：已占 / 还需 | B：已占 / 还需 | 判断 |
|---|---:|---|---|---|
| 分配前 | 1 | 1 / 2 | 1 / 1 | 存在 B → A 的安全序列。 |
| 再给 A 一个名额 | 0 | 2 / 1 | 1 / 1 | 两者的剩余最大需求都无法由当前空闲量满足，找不到安全序列。 |
| 改为再给 B 一个名额 | 0 | 1 / 2 | 2 / 0 | B 可以先完成并归还 2 个名额，再满足 A。 |

建议将红字直接改为：“A 已占 2、还需 1；B 还需 1，空闲为 0，因此找不到安全完成顺序，应暂缓这次分配。”原来的“不安全”结论仍成立，但演示计算必须正确。

右侧“不安全不等于已经死锁”的说明是正确的，应保留。再补一句适用条件：“最大同时需求可信、相关申请均可拦截、阶段能够结束并归还资源。”仅写“可以声明上限”还不足以建立保证。[依据：OS 算法补充说明第 1—3 节。]

### 1.2 第 12、14、28、29 页：执行状态、物理释放与费用结算混在了一起

这些页面的说法会直接影响实现正确性，不能作为简化表达保留。

| 当前表述与位置 | 问题 | 建议改法 |
|---|---|---|
| 第 12 页：“每个资源唯一归属于某个 Attempt，Attempt 结束时必须归还。” | 清理责任需要明确，但浏览器上下文、产物和共享对象可能跨步骤驻留。逻辑上的结束也不能证明后代进程已经退出。 | 改为“每项受管占用都有明确的清理责任；共享或驻留对象持续记账，确认实际占用结束后才归还对应许可。” |
| 第 14 页：“CPU/内存，进程结束即释放，cgroup v2 自动回收。” | CPU 时间、内存驻留与进程树不是同一种资源。cgroup 提供分组、计量和控制，并不自动完成任意工具的退出、临时文件回收和外部资源清理。 | 改为“使用 cgroup 约束工具执行域；守护进程核验自有进程树退出，并分别检查资源和产物回收。” |
| 第 28 页：“超时自动进入 QUIESCENT，不无限占用资源”；“QUIESCENT ≈ SIGSTOP”。 | SIGSTOP 停止进程执行，通常仍保留内存、文件描述符及锁。超时只说明没有按时得到结果，不能证明工作已停止。 | 改为“超时触发取消与清理；无法确认停止时进入待核对状态。只有满足约定的实际停止条件，才设置 QUIESCENT 标志。” |
| 第 29 页：“超时则强制结束”“归还所有资源……额度”“TERMINATED，资源释放完成”。 | 受控本地进程可以按协议终止，但远端请求未必可撤销。已经消费的费用和 token 不能因本地结束就退回，发出强杀也不等于已确认退出。 | 将结果结论、实际执行停止和费用结算分别记录；未知远端效果保留待核对项，未派发预留、在途容量、速率窗口和已消费费用分别处理。 |

建议把“执行结束”“QUIESCENT”“结算完成”定义成不同事实。QUIESCENT 在本项目中表示受管工作已经满足约定的停止条件，不表示未来永远没有迟到响应，也不自动意味着产物空间或远端费用已结清。

第 28 页的两个 OS 类比也应改写。有时间上限的工具执行不是 CPU 时间片轮转，因为它通常没有可无损抢占并续跑的执行现场；端平台反馈更接近异步消息、IPC 与背压，SIGTERM 是本地进程终止控制的一个具体手段。用真实接口解释 OS 落点，比笼统对应更可靠。

### 1.3 第 9、16、23 页：公平算法没有定义完整，并存在过度保证

“慢者导向惩罚”“慢者惩罚”“慢者加权”在不同页面交替出现，却没有解释“慢”究竟指请求长、排队久、消耗多，还是相对独占执行的 slowdown 大。这几种情况对应不同决策，不能用同一个名称代替规则。第 9 页也将 H1 缩成“长任务被短请求挤占”，弱化了原方案中根任务扇出获得额外份额的主要问题。

建议统一成以下可实现的层次，不必增加新算法名称。

1. **平台先分用户，再分根任务。**用户获得约定的服务份额，其内部根任务按成本 DRR 轮转，子 Agent 继承原份额。若全平台只按根任务平均分，多开根任务仍可能改变用户份额。
2. **个人端在自己的根任务之间选择当前就绪工作。**工具使用资源约束列表调度，请求使用成本公平轮转；两类工作不共用一个未经解释的物理成本分数。
3. **期限与老化在公平约束内影响排序。**EDF 是按截止时间排序，不自动等于“交互步骤优先”。没有明确截止时间时使用已声明类别与等待老化；长请求需要能够积累足够份额或得到合法的大任务保护。
4. **防饥饿说明成立条件。**第 23 页“只保证没有根任务被无限期饿死”应改为有条件的活性目标。任务需求可行、资源最终归还、服务持续可用及负载允许等条件不能省略；持续过载时需要有界接纳和明确拒绝。

DRR 的“成本”至少给出一个可计算例子，例如同一模型合同内的输入、输出 token 加权成本，完成后用实际用量修正。它不是 GPU 占用，也不宜直接与本地 CPU 秒、内存字节相加。未定义的 slowdown 权重可以删除，或者作为单独的候选策略给出公式和消融实验。

### 1.4 第 20、23、24 页：准入、排序和额度所有权还需分开

**资源可以统一展示和归属统计，但恢复规则不能统一。**第 24 页把 token、API 次数和 CPU/内存都列入“准入先冻结、完成后结算”的账本，容易误导实现。建议在该页明确区分四类：速率窗口按合同恢复，在途与工具容量按实际占用归还，总费用按消费累计，文件或工作区访问按锁协议管理。cgroup 可以观测和限制相应 CPU、内存等资源，工具锁及句柄责任仍需运行时账本和相应 OS 接口，不能写成全都由 cgroup 实时给出。

**调度路径必须按当前步骤分支。**第 23 页的五步流程容易读成每项工作都先预扣 API 额度，再申请 CPU/内存/锁，再由平台调度。正确的共同顺序应是：确认依赖和授权；在公平份额内选择候选；到对应的工具或请求资源域复核并原子预留；执行、交付结果并按类别结算。等待模型时不提前长期占着无关工具槽。提前承诺根任务总预算可以成为明确政策，但应与实际步骤的在途容量预留分开，说明可用性代价。

**协同反馈与硬授权使用不同一致性要求。**第 20 页笼统地说“最终一致性”和“信号只用于参考”，不能覆盖额度发放、结果发布权和释放账本。压力摘要可以延迟并在过期时回退，硬额度的权威账本与幂等结算必须有明确的原子操作边界。平台应下发汇总队列压力、建议在途窗口和重试提示，不需要把其他用户的根任务详情广播出去。

**补齐协议真正需要的元数据。**第 20 页列了进度、资源压力和预计耗时，却未明确根任务与执行尝试的身份。至少需说明认证用户、`root_task_id`、`step_id`、`attempt_id`、服务类别与截止时间、成本估计和反馈时效。平台使用这些显式信息排队，不能只凭对话内容推断。失联回退应保留硬额度约束；“异步非阻塞”只能减少同步等待，仍要实测通信和控制开销。

## 2. 实验与文献能否支撑核心论点

### 2.1 第 32 页：B11F 被改错，导致 H3 无法直接检验

当前页面写“B11F：B11 + 故障注入模式”。原计划书中的 F 表示反馈实验组，即在两端已经分别优化的 B11 上，仅开启规定的动态信息交换。这个差别关系到项目能否证明“协同”的独立价值，不是字母命名偏好。

建议恢复以下五组。故障注入作为另一条实验维度，在相同负载和故障条件下比较可靠性机制。

| 组别 | 个人端 | 平台端与反馈 | 回答的问题 |
|---|---|---|---|
| B00 | 使用合理配置的基础工具与 API 控制。 | 使用合理的公平队列、限流和过载保护。 | 成熟简单组合已达到什么水平？ |
| B10 | 加入个人端候选策略。 | 保持 B00。 | 个人端改进的增量是多少？ |
| B01 | 保持 B00。 | 加入平台候选策略。 | 平台改进的增量是多少？ |
| B11 | 两端均使用候选策略。 | 不交换动态协同反馈。 | 两端独立优化一起运行的效果如何？ |
| B11F | 与 B11 相同。 | 只增加规定的动态反馈。 | 反馈本身是否改善完整任务交付？ |

**H3 的关键对照是 B11F 对 B11。**两组保留相同静态任务身份、关系、算法及资源配置，只改变动态反馈。仅证明完整系统好于 B00、B10 或 B01，不能说明交换信息本身有价值。第 9 页的验证映射也要同步修改。

第 32 页“端侧资源治理关闭”还应改成“候选策略关闭，基础安全与资源控制保留”。性能实验中应给各组相同的正确依赖、合理重试、清理、硬限制与必要持久化；否则候选方案可能只是战胜了容易泄漏或无限重试的弱基线。

### 2.2 第 5、7、34 页：区分负载特征、缺陷证据和资源画像

第 5 页 TraceLab 的数字可以保留。归档原文支持 43 名开发者、4,265 次会话、357,161 个 LLM steps、432,510 次工具调用，以及超过 1 分钟的工具调用约占 4%、贡献约 85% 工具调用总时间。该页已有“不等于全部可优化”的限定，是正确的。

但这些统计主要支持阶段异质性与长尾，不能直接证明所有个人电脑都资源争用严重，也不能直接量化本项目可节约的 CPU 时间。第 34 页“真实工具画像来自 TraceLab 公开数据”范围过宽：公开轨迹保留调用、时间与 token 等信息，删除原始工具输入输出，也不提供这里所需的主机 CPU/内存需求轨迹。

建议第 34 页改成：“公开轨迹用于校准到达、调用类型、token 与耗时分布；本地工具的 CPU、内存和临时空间需求由团队实测；再结合可验收任务进行小规模真实运行与 30 天仿真。”不能把脱敏日志直接描述为能够重演原任务语义和资源竞争的数据集。

第 7 页也要给证据分级。特定版本的退出残留和交接问题可作为公开案例；PeakBench 提供容量约束的方法依据；平台对根任务信息不足则是需要实验检验的机制问题。将“平台看到单次调用，不理解完整任务”直接列为普遍现象，会被追问已有平台如何处理、何种负载下发生损失以及如何复现。

### 2.3 第 10、34 页：指标应先定义，再设门槛

“自选待验证”已避免把目标写成实测结果，应保留。仍需修正四项口径。

| 指标组 | 当前不足 | 建议定义 |
|---|---|---|
| 有效交付 | 第 10 页列出 P95 等目标，却未优先列出完整任务按时合格完成率；第 34 页缺少具体合格标准和截止时间来源。 | 预先固定代码测试、文档字段或资料覆盖要求及任务期限；拒绝与未完成任务保留在提交分母，尚未到期任务单列待定，无期限后台任务另报完成数量和时长。 |
| 等待与公平 | “交互 P95 延迟”不明确测请求还是根任务；Jain ≥ 0.85 没有说明对什么量计算；slowdown 缺少分母。 | P95 优先统计交互根任务完成时间；slowdown 使用同一轨迹独占时间；公平性按约定权重归一化服务，并明确只比较有可服务需求的对象及统计窗口。不能把原始 token 数均等自动视为公平。 |
| 正确性与恢复 | “故障后资源不一致率 < 5%”可能被理解为允许少量重复释放、超额分配或旧结果覆盖。 | 受支持故障集合内，不允许这些已定义的安全不变量被破坏；另报规定时间内自动核对成功率、清理时延与 UNKNOWN 比例。无法确认可以保持未知，不能伪报成功。 |
| 改善幅度与重复性 | 10% 改善缺少对照、负载条件与测量波动说明。 | 明确相对哪组、在哪些已确认竞争的负载下比较；冻结调参规则，多种子或配对重复，报告波动和额外开销。固定模型设置不等于外部 API 每次时延恒定。 |

### 2.4 第 7、25、27、39 页：引用编号和书目信息需要统一

第 39 页仅列原技术计划书 29 条参考的部分简称，而正文又使用 `[S03/原6]`、`[S21]`、`[S22]`、`[S23]`。两套编号本身可以并存，但这份 PPT 没有给出完整映射；例如银行家算法的 S21 并不是原计划书编号 21。不能让读者靠猜或搜索另一个文件判断具体来源。

建议正文统一用作者或项目名、年份及简短编号；附录给出实际使用来源的完整名称和可点击链接。尤其应纠正以下名称，而非仅写主题概括。

论文发现、GitHub 报告、已有官方功能和本项目假设应分别说明。第 36 页的根任务公平、资源向量准入、反馈及代际机制已有成熟思想基础，更适合称为“拟验证的系统设计贡献和实现亮点”；具体创新空间由任务场景、控制边界和强基线对照建立，不能仅靠算法名称证明。

## 3. 内容流程与实际画面的改进

### 3.1 开场需要一个贯穿全篇的具体案例

现在第 3 页先给完整思维导图，第 5 页进入“从请求处理转向完整任务交付”，第 6 页又进入用例图。听众尚未看见用户到底被什么困扰，就需要理解根任务、Harness 和平台协同等多个概念。四章标题本身合理，问题在于开头缺少可感知的工作现场。

建议用同一个案例贯穿后续页面：一个学生同时整理资料、修改并测试代码、发起临时问答；这些工作竞争本机工具资源和个人模型预算。当多个用户通过受控应用网关访问固定模型服务时，还会竞争共享派发机会。分别画出工具排队与模型请求排队，再说明 TaskLoom 如何改变它们的推进顺序。

案例应明确标成设计或演示场景，不捏造“原来需要十分钟，改后只需一分钟”的结果。尚无先导数据时，也可以提出可复现条件：限制工具容量与 API 速率，观察临时问答等待、后台任务推进和取消残留。随后用第 5 页的文献特征和第 7 页的公开案例说明为什么值得验证。

### 3.2 第 16—19 页重复介绍架构，且抽象层次不统一

这四页分别展示总体架构、组件图、两端四层、部署图，却没有明确“职责划分”“软件依赖”和“物理位置”各回答什么。第 16 页将若干端侧组件与平台算法并列，还引入“协同协议层”，容易让人以为项目已经从四层变成了另一套分层。

建议以第 18 页作为正文中的统一总览，先说明个人端 L1—L3、应用平台 L4 和边界外的固定模型服务。第 17 页用于需要讲接口时展开；第 19 页用于说明运行位置、真实进程与守护隔离；第 16 页合并或改成一张清楚的模块分工图，不再与四层架构竞争解释权。

“平台”应在首次出现时明确为团队可控制的应用网关，并说明它如何取得任务元数据。第 18 页给个人端加上“每位用户一套”的组标题。客户端请求经理与平台共享额度账本的职责需要一致，避免老师误以为两端各自分配同一份上游额度。

### 3.3 第 13、15、21、30 页：图示与讲稿必须使用同一套语义

## 4. 建议的修改顺序和答辩版本

### 4.3 增补首版实施边界，不再扩大算法清单

当前第 37 页给出了课程阶段与工作包，这是有用的，但“接通运行时”仍偏抽象。建议加上一页四项明确承诺。

- **接入对象：**首版选一个可修改运行时或受控工具/模型调用适配器，说明如何在调用真正发出前拦截。具体实现选型尚未冻结就标为待选，不宣称透明控制所有商业 Harness。
- **控制范围：**一个 Linux 工具执行环境、一个可控制应用网关、一份明确的模型 API 合同，以及有限种可验收工具；每位用户仍有自己的个人端。
- **实际 OS 对象：**工具使用真实进程，独立守护进程核验清理，通过 IPC/事件传递就绪与完成，信号量和锁保护有限许可与账本。不能只用界面状态动画代替执行机制。
- **首个验证场景：**用文档解析、代码测试和短问答构造混合任务，分别测本地紧张、API 紧张、双侧紧张和宽松条件。真实工具测量用于校准仿真，固定模型回放用于隔离排序因素，结果质量另行验收。

银行家检查、优先级继承与协同反馈都应说明触发条件和独立验证位置。课程时间不足时优先保证最小任务闭环、真实守护和可信对照，再按先导证据决定哪些扩展最有价值。

### 4.4 可以保留的内容与审查依据

当前版本中有四项值得保留。

- **第 5 页的目标转向与统计限定合理。**它把完整任务交付置于单请求吞吐之上，同时没有把 85% 的长尾时间直接宣称为可节省时间。
