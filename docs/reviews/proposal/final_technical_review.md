## 1. P1：同一共享额度必须明确唯一权威；旧 attempt 的真实费用仍须结算

位置：§2.2 第97、112行；§3.2 第161–169行；§3.4 第187行。

“端侧和平台侧分别拥有自己的权威账本”对于不同资源成立，但目前没有明确同一 provider 组织/账号配额最终由谁裁决。多客户端如果各把相同 provider 限额当独立完整额度，即便各自 SQLite 单写，也不能保证全局合同。该缺项会影响真实实现，而不是靠单机原子事务自动解决。

最小澄清：平台拥有共享 provider 配额和实际派发的权威记录；端侧拥有本地资源和自己的任务状态，对共享额度仅作镜像/预检或使用平台授予的有界份额。用户/根任务钱预算也指定唯一裁决位置，其他位置不得重复预留或重复结算。若端与平台本来是不同限制域，显式给每项额度记录 scope/owner 即可。

同时，第187行“旧 attempt 的迟到结果只写审计/不重复扣费”应补一句：旧代际不得发布当前语义结果，但其尚未结算的真实消费仍须按该 attempt 一次性入账。fencing 不能让旧 attempt 的合法成本消失。重发同一 request_id/attempt 的登记消息与创建新 attempt 要区分，网络重传不应再产生一次派发或额度预留。

## 2. P1：准时合格完成率的分母与观察结束条件尚不完整

位置：§4.1 第217行。

当前公式把观察窗口提交的全部 N 个任务放入准时率分母，但后文又说明后台任务没有 deadline。没有 dᵢ 的任务无法直接代入公式。此外，窗口最后刚提交、截止时间尚未来到的任务，不能因为统计停止就被判为未按时完成。

最小澄清：G 针对在提交时已定义期限的固定任务集合，N 为该集合大小；所有策略使用同一集合。观察至少延续至这些任务的截止时间已到或已完成，或者明确报告尚不可判定的删失，不将其直接判失败。无期限后台任务单独报告合格吞吐与等待。主动取消可在主意向完成率中保留并单列原因，若另报排除主动取消的指标，分母与排除规则需预先冻结；不能只说“另列”而不定义是否计入 G。

其余完成者 P95、补充观察和长任务代价的规定已经正确，无需重写整体评价架构。

## 3. P1：B11 与 B11F 必须保留相同的基本任务元数据

位置：§4.1 第210–213行。

当前 B11 是平台候选任务级调度但“不交换协同反馈”；B11F 开启“规定信息交换”，随后又移除“任务关系”作消融。如果 B11 缺 root_task 等关系，它实际上无法运行同一根任务公平策略，B11F 的收益就同时改变了调度算法和信息接口。

最小澄清：身份、根任务关系、已就绪状态、请求成本及服务目标属于运行候选算法的基础协议，在 B11/B11F 中完全相同。主对照仅切换动态本地压力与平台拥塞/建议窗口反馈。删除根任务关系可以另设机制消融，但明确它改变分组策略，不能并入“反馈本身的增量”。这样能保留现有五组设计，无需扩张主实验矩阵。

## 4. P2：只读不自动意味着可复用或语义可重放

位置：§3.4 第191行，并关联§4.2 第234行。

“对只读或经验证幂等步骤”容易把所有只读工具默认为安全重放。读取可变远端页面、权限已变的数据、时钟或变化中的目录，即使没有写副作用，也可能使恢复后的结果与先前步骤不一致。第234行已要求输入版本一致，但需要将这项条件提前放进可恢复步骤定义。

最小澄清：改为“对经过验证可重放的只读或幂等步骤”，验证内容包括数据/输入版本、当前授权、环境依赖与结果验收要求；无法固定版本时明确采用重新读取并使相关下游结果失效，或转为需核对状态。已有成功结果的复用也应检查其产物仍可用，而非只看日志中的成功标记。
