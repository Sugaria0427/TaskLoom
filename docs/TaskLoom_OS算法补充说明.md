# TaskLoom「织序」OS算法补充说明

**主题** 银行家算法的阶段化应用，以及工具选择、死锁预防与优先级继承。** 文档更新** 2026-10-20；** 算法依据核查** 2026-09-29。

本文解释[当前完整项目说明书](TaskLoom_项目说明书_当前完整方案.md)中的补充分配机制。项目由个人端 L1—L3 与平台端 L4 组成；当前已具备原子资源准入及 cgroup 保护，阶段银行家、锁等待优先级继承和相关性能实验属于后续工作。实现进度统一见[当前状态](engineering/TaskLoom_当前实现与开发状态.md)。下文依次说明算法条件、资源模型、动态处理和评价方法。

## 1. 银行家算法可以用，但要明确它保证什么

**动态产生任务并不排斥银行家算法。** 真正需要限制的是：当前参与资源分配的工作是否有可信的最大需求，申请能否被统一控制，以及工作能否在得到这些资源后结束并归还。

### 1.1 区分三种不同的“动态”

不同变化对算法的影响不同，不能一概归为“Agent是动态的，所以不能使用”。

| 变化 | 是否可以处理 | 处理条件 |
| :--- | :--- | :--- |
| 新任务不断到达 | 可以。 | 新工作在取得资源前登记最大需求，随后接受同一资源管理器的安全检查。 |
| 当前阶段希望提高最大需求 | 有条件可以。 | 把上限调整作为一次状态变更，安全检查通过才允许生效；拒绝后的处理见3.1。 |
| 工具随意申请未声明资源，且无法拦截或停止 | 无法直接给出经典安全保证。 | 需要先增加工具约束、改变执行方式或排除出保证范围，不能只修改预测数值。 |

经典银行家模型允许实际占用随执行变化；它要求的是占用不超过预先声明的边界，而不是实际资源需求从头到尾都相同。Dijkstra的论述以有界需求、有限事务和可归还资源为前提。[S21]

### 1.2 现代操作系统也会针对场景选择不同方法

现代系统能够管理动态任务，不能直接推出它们普遍用银行家算法管理全部资源。不同资源可能采用申请顺序、冲突后退让、优先级继承等不同机制。

例如，Linux的Wound/Wait互斥文档讨论了动态对象加锁顺序难以统一时，通过事务身份和退让处理冲突；RT-mutex文档则解释了如何通过优先级继承减少优先级反转。[S23–S24] 这两个实例说明应按资源特性选择方法，并不是要求TaskLoom同时实现全部内核机制。

对TaskLoom而言，应用层可以选择一组受控工具，明确其资源申请接口。这比试图预测任意程序的全部需求更容易建立适用条件，也是课设可以验证的范围。

### 1.3 安全状态与死锁不是同一件事

**安全状态** 指存在一个完成顺序：按照当前声明的最大需求，系统能够让这些工作依次获得所需资源、完成并归还资源。

**不安全状态** 表示这样的保证已经不能建立，但任务尚不一定真的死锁。如果实际需求低于最大值，后续仍可能完成；银行家算法会为保住保证而提前拒绝某些看似还能分配的请求。[S21–S22]

安全序列是一份“存在可完成顺序”的证明，不是强制执行时间表。实际调度仍可按公平性选择请求，只要每次分配都保持安全；是否会饥饿、是否满足期限、程序是否出错，还需要其他机制和实验回答。

### 1.4 四种机制各管一个问题

本次新增机制的职责如下，避免把全部等待都当作银行家算法的问题。

| 机制 | 主要问题 | 不负责的事情 |
| :--- | :--- | :--- |
| 列表调度、老化与大任务等待保护 | 就绪工具先运行谁，资源不足时能否先运行其他工作。 | 不直接证明分批资源申请不会死锁。 |
| 一次性原子申请与固定锁顺序 | 预防部分占有、循环申请等明确等待模式。 | 不保证任意未知依赖都能完成。 |
| 银行家安全检查 | 分批分配后是否仍能在声明上限内完成并归还资源。 | 不替代公平调度，也不管理消耗型费用。 |
| 优先级继承 | 紧急任务被低优先级持锁者阻塞，而持锁者又被其他工作拖延。 | 不解除真正的资源循环等待，也不加速远端模型计算。 |

## 2. 在TaskLoom中怎样建立银行家模型

算法位于第一层的本地资源管理器，由第二层提供执行阶段的信息。首版只纳入能够完整管理的资源，不跨越个人端与平台端维护一个全局银行家矩阵。

### 2.1 管理单位是能够独立结束的执行阶段

一个阶段从开始申请受管资源，到结束并释放这些资源。它可以是一个工具内部的若干操作，但不能只是任意截取的一段时间。

阶段必须满足四个条件。

1. **最大需求有依据。** 上限来自受控工具模板、输入规模规则或可强制执行的约束，表示本阶段可能同时持有的最大数量，不是累计调用次数。

2. **相关申请可拦截。** 阶段不能绕过管理器另开未记账的实例；子进程和插件使用的同类受管名额也必须计入。

3. **完成不依赖隐含的资源等待。** 阶段不能拿着本域资源，等待一个必须使用这些资源、却没有纳入模型的子任务。首版通过先结束并释放父阶段、再启动子阶段处理这类情况。

4. **实际结束可以确认。** 阶段取得足够资源后，按受控工具约定能够完成或安全终止并归还。若工具失控或外部服务无法确认，按异常流程处理，不能把逻辑结束当作资源已经释放。

首版选择工具实例和浏览器实例等可归还名额。CPU时间、API的RPM/TPM窗口、已经消费的token与费用，不放入这个银行家模型。内存先保留启动预算与cgroup保护，未拦截每次内存申请时，不声称银行家检查已经覆盖真实内存分配。

### 2.2 只需要四类核心数据

每一类资源单独计数。多个资源维度之间逐项比较，不把实例数、内存字节和费用直接相加。[S22]

| 数据 | 通俗含义 | 在TaskLoom中的例子 |
| :--- | :--- | :--- |
| `Available` | 当前还能分配多少。 | 还空闲几个受管浏览器实例。 |
| `Max` | 一个阶段最多同时需要多少。 | 某受控采集阶段最多持有3个实例。 |
| `Allocation` | 一个阶段已经拿到了多少。 | 当前已经占用1个实例。 |
| `Need = Max − Allocation` | 按声明还可能再需要多少。 | 最多还需要2个实例。 |

已结束阶段仍保留的产物或驻留对象不能被假设为已经归还。它们若不再属于本轮阶段模型，仍须从可分配容量中扣除，并由明确的拥有者负责释放。

阶段的最大需求增加、容量变化或新工作进入时，都需要重新维护这些数据。固定安全条件依赖资源容量与占用记录真实，不能把外部程序占掉的容量继续记成空闲。

### 2.3 一次申请如何获得批准

每次受管申请经过四步，安全试算只操作账本副本，不提前给工具真实资源。

1. **检查申请边界。** 请求量不得超过该阶段的剩余声明需求，也不得超过实际空闲量。越过原声明需要走上限调整流程，不能当作普通申请放行。

2. **试算分配后的账目。** 从空闲量扣除请求量，将其加入申请者的已占用量，计算更新后的剩余需求。

3. **寻找安全完成顺序。** 从假想空闲量出发，找一个剩余需求逐项不超过它的阶段，假设其完成并归还原来占有的资源；重复直到全部阶段都能完成，或再也找不到可完成者。

4. **提交或保持原状。** 找到完整安全序列才原子提交真实预留；否则撤销试算，真实账本保持不变，请求等待资源变化或明确退出。检查与提交之间不得让其他申请悄悄改变所依据的状态。

在第3步中，假想阶段完成后的净变化是归还它原来已经占有的资源。为完成它临时提供的剩余资源也会归还，因此不会凭空增加系统总容量。

### 2.4 一个完整的数值例子

下面仅是说明算法的手工例子，不是项目性能实验。设系统共有3个相同的可归还名额，两个阶段的状态如下。

| 阶段 | 最大需求 | 已占用 | 最多还需要 |
| :--- | :--- | :--- | :--- |
| A | 3 | 1 | 2 |
| B | 2 | 1 | 1 |

系统剩余1个名额。当前存在安全顺序：先给B最后1个，B完成并归还2个，再满足A余下的2个需求。

如果A先申请增加1个，单看空闲量似乎可以批准。但批准后空闲量变成0，A与B仍各可能需要1个；找不到安全完成顺序，所以应暂缓A的申请。

如果B申请增加1个，批准后B已经满足最大需求，可以完成并归还资源，随后A也能完成。因此可以批准B。例子体现的是“分配后的完成能力”，并不意味着B在所有场景下都必须比A优先。

## 3. 怎样适应动态任务，并尝试改进

可研究的方向是把经典安全检查适配到明确的执行阶段，降低不必要的预留或检查成本。当前属于待验证的系统设计，不宣称已经形成全新的死锁理论。

### 3.1 动态变化必须先核验、后生效

变化处理分成四种，避免在实际需求增加后继续沿用失效的安全证明。

1. **新阶段到达。** 先登记上限，再根据同一资源账本申请。一个尚未占用资源、上限可行且没有隐含依赖的新阶段，可以被安排在既有工作之后完成；动态到达本身不会让算法失效，但公平性仍需单独保证。

2. **阶段结束并开始下一阶段。** 先确认旧阶段资源实际归还，再以新阶段自己的上限登记。仍保留的对象继续扣减可用容量，不能靠切换阶段编号把占用从账上清除。

3. **阶段希望提高上限。** 对新上限及相关申请进行原子安全试算，通过才生效。若扩展只是可选能力，被拒后可按原计划完成；若原上限已不足以完成，就必须确认能安全停止、释放并重新准入。不能无限持有旧资源等扩容；不能安全退出的情况转故障处理并明确原保证已不适用。

4. **资源容量变化。** 对可控制的缩减，先检查是否仍安全；不可控制的容量损失发生时，暂停新的分配、核对占用并进入恢复流程。算法不能拒绝一场真实资源故障，也不能继续引用故障前的容量证明。

以2.4的例子为例，如果B想把上限从2提高到3，而A、B仍各占1个，剩余1个就不足以保证任何一方按新上限完成。此时应拒绝这次上限变更，而不是先更新上限再等问题出现。

### 3.2 改进方向一：按阶段声明，减少不必要的保守限制

一个完整Agent任务会先后运行不同工具。把它所有未来阶段的需求都长期归在一个不变的大上限下，可能让安全检查过于保守；按真实资源释放点划分阶段后，可以只检查当前阶段的需求。

这种收益依赖阶段确实能够释放相应资源。如果浏览器上下文必须一直保留到后续步骤，就不能在前一阶段结束时假装释放；它仍需有连续的资源记录。

对于能够一开始拿齐全部所需资源的工具，一次性原子申请已经是清晰的方案。只有分批申请能够带来有意义的资源重叠时，才值得增加银行家检查；否则增加的只是管理开销。

### 3.3 改进方向二：复用安全序列，减少重复计算

对n个活动阶段、m类资源，直接安全检查的朴素实现最坏需要约O(n²m)的比较工作。首版规模较小时先采用这个简单版本，再测检查开销是否值得优化。

一个可验证的优化是保存上次找到的安全序列。状态变化后，先用新账目验证这个顺序是否仍安全；若成立，就得到当前状态的有效证明；若不成立，再执行完整搜索，不能直接判定整个状态不安全。

这种复用保持安全判定标准不变。快照之外计算时，提交前必须核对状态版本，变化后重新检查；首版也可在单一资源管理器内直接计算，先保证正确性。

只把已经结束且实际释放的阶段移出检查，不能为了降低n而忽略等待中、仍占资源的工作，也不能随意拆开相互依赖的资源池分别宣称安全。

### 3.4 预测可以帮助排序，但不能冒充安全上限

历史平均值、P95和模型预测可以帮助选择工具顺序、估计等待时间，但实际占用仍可能超过这些数值。直接将它们写成`Max`，就不再具备经典银行家算法的保证。

若希望用更小的上限提升可用性，需要改变工具的可执行约束，例如分块处理、限制实例数或在超界前安全停止。此时应一起报告失败、拒绝和重做成本，不能只展示并发数量变多。

本项目优先研究“阶段边界真实、上限可解释、申请受控制”的版本。估计型准入可以作为另一实验模式，但其概率性风险必须与严格模式区分。

## 4. 如何实现和评价这次补充

新机制放在现有四层中，按从简单到复杂的顺序实现。算法演示、故障验证和真实性能评价分别记录。

### 4.1 一并补齐其他三项设计

除银行家检查外，当前完整说明书同步补充三项规则。

- **工具队列选择。** 允许资源可行的就绪工具先执行，并记录大工具的等待与被跳过次数；必要时暂缓未启动阶段的同类新占用，等待现有工作释放资源。已准入阶段完成所需的安全分配仍可进行，避免等待保护反而阻碍资源归还；该保护不保证持续过载时所有任务都及时完成。

- **基础死锁预防。** 一次性资源申请失败不留下部分预留，多锁访问遵循固定顺序，父任务等待子任务时释放不再使用的执行许可。锁与资源实例的控制协议必须衔接，不能遗漏跨边界等待。

- **条件性优先级继承。** 记录等待者与持锁者，把阻塞的高优先级传递给相关持锁工作；锁释放或等待取消后，按剩余等待者重新计算有效优先级。先在能够控制执行机会的本地场景验证，远端API与未经调度器控制的工作不自动受益。

这些规则共同使用真实资源拥有者信息。优先级变化不修改资源上限；银行家判定通过也不能覆盖授权、文件访问或费用限制。

### 4.2 分三个实现层次推进

实现顺序应保留随时可以比较的简单方案。

| 层次 | 实现内容 | 进入下一层次的条件 |
| :--- | :--- | :--- |
| 基础版本 | 工具列表调度、原子资源申请、锁顺序与真实释放。 | 混合工具与取消场景运行正确，形成可靠基线。 |
| 安全检查版本 | 受控阶段声明固定上限，分批申请经过银行家检查。 | 上限、实际占用与安全序列能够在事件记录中核对。 |
| 动态与优化版本 | 阶段边界更新、上限变更协议，以及可选的安全序列复用。 | 相对于前两者能解释正确性、收益与新增开销。 |

优先级继承在发现并能复现对应锁阻塞后作为独立增强。Linux的Wound/Wait用于理解替代设计，本轮不额外纳入实现清单。

### 4.3 实验应回答四个问题

实验同时保留无竞争、阶段需求稳定和频繁变化的情况，避免只选择适合复杂算法的负载。

1. **分配是否正确。** 检查每次已批准分配能否给出有效安全序列，以及资源是否发生重复释放、漏记或越过声明。请求因不安全被暂缓，不等于实际死锁已经发生。

2. **效率是否改善。** 在相同工具语义、资源上限依据与负载下，比较一次性全量申请、固定阶段银行家检查和阶段化更新；测完成时间、资源闲置、拒绝及取消重做。允许得出简单方案已经足够的结论。

3. **等待是否更公平。** 分别启用或关闭大工具等待保护、优先级继承，测最长等待与受影响任务的代价。安全性、吞吐和公平不能用一个指标互相代替。

4. **动态与异常是否收敛。** 加入新阶段、上限增加被拒、实际需求超声明、容量骤减和旧执行迟到事件；检查是否按规则暂停、释放、恢复或明确保留待核实。安全序列复用必须与完整检查得到一致的安全判定，再比较计算开销。

银行家算法不会修复未建模的逻辑依赖、无限网络等待或工具本身错误。实验的结论只覆盖声明的资源域和工具合同，不能扩展为“整个Agent系统永远不会卡住”。
