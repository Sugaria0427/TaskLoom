# TaskLoom WP2 检查点升级修复

版本：v1.0。日期：2026-10-24。修复基线：PR #3，`89e8036`。

本文说明旧任务恢复问题、兼容方案、验证和工作范围。本次修复针对旧检查点升级为轮次化工具身份时的恢复行为。

## 1. 问题与目标

旧任务使用 `{task}-tool-{call_id}` 记录工具 Step，检查点按原始 call_id 保存完成结果；PR #3 改用模型轮次与调用 ID 组合。直接恢复旧状态会错过原 Attempt，导致未确认工作重复派发，或使已完成工具无法成为下一模型步骤的前驱。

本次目标是让旧任务继续沿用原执行身份：已完成结果能够复用，实际执行不明的工作核对原 Attempt，取消意图和资源预留在升级中保留。

## 2. 兼容方案

### 2.1 按持久化证据建立别名

`client/checkpoint_upgrade.py` 从已成功保存的模型回复恢复工具名称、参数与模型轮次。`TaskState.tool_step_aliases` 保存“轮次化逻辑键 → 原 Step 键”的对应关系，原 Step、Attempt ID、执行器请求和历史图记录保持连续。

检查点中的完成键与工具元数据同步转换。后续模型依赖通过别名解析到原 Step，工具续作也查找原 Attempt。新任务继续使用现有轮次化规则。

### 2.2 原子保存与一次备份

升级后的任务、补齐请求内容的 Attempt 和升级前快照通过同一 Repository.apply 保存。`checkpoint_backup` 按根任务保存首次升级前的任务与尝试记录。重复启动复用现有备份和别名。

### 2.3 未确认工作只核对原执行

恢复中的工具首先查询原 Attempt，执行器记录缺失时保留隔离预留与待核对状态。返回的请求身份、参数或输入版本与原工作不同，也保留隔离状态。确认成功后复用原结果；确认结束及资源释放后按现有重试规则推进。

### 2.4 证据不足时暂停该任务

同一旧调用 ID 对应多个候选轮次、模型回复缺失、参数冲突或记录归属不一致时，以 `CHECKPOINT_UPGRADE_REQUIRED` 暂停该任务自动恢复，并保留原始快照和执行事实。其他任务继续运行；取消请求保持有效。显式 resume 同样检查这些条件。

## 3. 验证

新增集成测试覆盖：

- 已完成检查点升级、实际依赖图衔接和重复启动。
- 未确认工具只查询原身份、核对完成后续作，以及执行器记录缺失。
- 执行器回执与原请求不一致时保留隔离占用。
- 已取消任务保持取消，缺失或歧义历史在自动派发前暂停。
