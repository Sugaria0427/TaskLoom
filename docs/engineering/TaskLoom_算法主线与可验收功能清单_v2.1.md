# TaskLoom「织序」四层算法与设计策略验收清单

版本：v2.1 · 日期：2026-10-28 · 功能基线：已合并提交 `644aae0`。

本文按 L1—L4 四层组织，每层先说明职责，再介绍具体算法、OS 机制或设计策略。每项统一说明应用场景、算法原理、应用效果和触发操作，勾选框用于记录现场展示情况。

清单中的方法分为三类，名称按实际性质使用：

| 类别 | 代表方法 |
| :--- | :--- |
| 经典调度与死锁算法 | 轮转调度、优先级调度、老化、银行家算法。 |
| OS 机制 | 互斥锁、进程隔离、检查点恢复。 |
| 通用调度与工程策略 | DRR、多资源分配、依赖调度、背压控制、指数退避、亲和调度。 |

例如“多资源分配”是一项设计策略：同时检查工具名额、内存和产物空间，满足条件才执行；大工具暂时放不下时，继续选择资源足够的小工具。具体选择规则放在原理说明中，标题保留简洁名称。

四层分工如下。个人端负责 L1—L3，平台端负责 L4，模型服务能力在对照中保持固定。

| 层次 | 管理对象 | 核心问题 |
| :--- | :--- | :--- |
| L1 本地资源与工具执行 | 工具名额、内存、产物空间和工具进程。 | 哪个工具现在能运行，运行后如何回收资源？ |
| L2 Agent 任务管理 | 完整任务、执行步骤、依赖和检查点。 | 下一步何时就绪，多个步骤如何协调？ |
| L3 个人模型请求调度 | 当前用户各任务产生的模型请求。 | 有限的请求机会先分给哪个任务？ |
| L4 平台多用户请求调度 | 多用户请求、共享槽位和平台额度。 | 共享服务能力如何在用户之间分配？ |

**展示状态：** “已接入”表示位于实际任务执行链；“组件演示”表示算法已有独立实现，按组件样例展示；“条件接入”表示需要指定配置才能生效。涉及组件样例或特殊资源条件的操作，均在对应条目中注明。

**现场入口：** [Alice 个人端](http://127.0.0.1:8795/)、[Bob 个人端](http://127.0.0.1:8798/)、[平台控制台](http://127.0.0.1:8796/admin)。同一用户在不同会话提交任务，形成个人端竞争；Alice、Bob 同时提交任务，形成平台端竞争。

**整体效果：** 在[对照实验页](http://127.0.0.1:8795/experiments)固定容量、任务负载与随机种子，比较 FIFO、平台轮转和 TaskLoom 组合策略。查看交互平均/P95 周转时间、全部任务平均周转时间、按时完成率及后台最大等待；选择 7 天或 30 天观察逐日变化。页面使用合成负载开展离散事件仿真，真实任务另以执行记录展示。具体参数见[课程验收与演示](TaskLoom_课程验收与演示_v1.0.md)。

## 1. L1：本地资源与工具执行

L1 接收工具执行请求，安排其使用本机资源。它先判断资源是否够用，再决定执行顺序，最后负责进程运行、停止和资源回收。

### 1.1 多资源分配

- [ ] **已接入：** 工具执行前统一申请资源，暂时无法执行的大工具可以让出机会。

- **应用场景：** 一个耗内存的大工具排在前面，后面还有资源需求较少的小工具；此时机器剩余资源只能容纳小工具。
- **算法原理：** 把每个工具的需求表示为“名额、内存、产物空间”三项资源。三项均满足才一次性预留；当前候选放不下时，继续寻找符合资源条件的工作。
- **应用效果：** 避免只因队首工具暂时放不下，就让剩余资源全部闲置；工具结束后归还预留。需求超过总容量的工具直接拒绝，暂时超过剩余量的工具等待。
- **触发操作：** 在工具槽位为 2、内存为 384 MiB 的受控配置中，先运行一个需 256 MiB 的长工具，再排入需 256 MiB 的工具和需 64 MiB 的 `list_files`。观察小工具先利用剩余资源，大工具待资源释放后运行。

观察个人端的工具队列、内存预留和资源归还。当前 `read_file`、`run_command`、`top_words` 声明 256 MiB，`file_stats`、`grep` 声明 128 MiB，`list_files` 声明 64 MiB；这些数值是准入预算。

实现：[资源模型](../../src/taskloom/domain/model.py)、[工具画像](../../src/taskloom/execution/catalog.py)、[工具调度器](../../src/taskloom/client/dispatcher.py)。

### 1.2 加权轮转（WRR）

- [ ] **已接入：** 高、普通、低优先级任务按不同权重获得工具执行机会。

- **应用场景：** 用户同时运行前台任务和后台任务，希望紧急工作更快推进，同时保留后台的执行机会。
- **算法原理：** 工具请求按优先级分成三档，按 4∶2∶1 分配轮次；同档内部再按根任务轮转，每次选择当前资源可满足的工具。
- **应用效果：** 高优先级获得更多派发机会，低优先级仍有轮次。权重对应执行机会，实际完成数量还与工具耗时、资源需求有关。
- **触发操作：** 在不同会话提交工具任务，形成排队后，把其中一个等待任务改为高优先级。观察后续工具派发顺序，并确认普通、低优先级任务仍能推进。

运行中的工具保持原执行；修改优先级影响等待和后续步骤。个人模型请求如何响应同一个优先级设置，见 L3 第 3.2 节。

实现：[加权工具队列](../../src/taskloom/client/dispatcher.py)、[根任务轮转](../../src/taskloom/policies/fair.py)。

### 1.3 银行家算法

- [ ] **组件演示：** 在资源够用之外，再检查分配后是否仍有工作能够完成并归还资源。

- **应用场景：** 多个工作先占用一部分资源，后续还要继续申请，可能出现彼此等待的局面。适用条件是当前阶段最大需求可声明、申请可拦截、资源可回收。
- **算法原理：** 先试算本次分配，再查找一条“某工作完成并释放资源，接着满足其他工作”的安全顺序；找不到安全顺序就暂不分配。修改最大需求时也进行同样检查。
- **应用效果：** 提前拒绝会破坏安全顺序的分配；不安全的需求更新保留原声明与分配，帮助受控阶段避免资源僵持。
- **触发操作：** 用独立样例设置总内存 10、两个工作的最大需求各为 10，并给足执行名额。先给其中一个工作 4，再尝试给另一个工作 4；对比安全检查拒绝第二次申请与贪心模式继续分配的结果。

当前真实工具使用第 1.1 节的一次性资源准入。银行家按独立组件展示，其阶段需求声明与真实任务流程的接线属于后续集成。

实现及样例：[阶段银行家](../../src/taskloom/policies/banker.py)、[安全序列与动态需求样例](../../tests/unit/test_banker.py)。

### 1.4 进程隔离

- [ ] **已接入的 OS 机制：** 工具在受管进程中运行，超时或取消时核对停止并回收资源。

- **应用场景：** 工具执行时间过长、消耗过多资源，或者创建了额外子进程；用户希望取消后真正停止执行。
- **算法原理：** 按执行尝试建立进程组；具备 cgroup v2 委派时，另外设置内存、CPU 和进程数限制。取消或超时后停止相关进程，确认退出后归还预留。
- **应用效果：** 将单个工具的资源占用控制在声明范围，避免只停止父进程却遗留后代。停止状态不明时保留资源记录，交给核对流程处理。
- **触发操作：** 请求执行一条持续数秒的本地指令，确认后观察工具占用，再点击取消；查看进程停止和工具名额、内存预留恢复。超时场景可为指令设置较短超时时间。

命令以当前本机用户权限在 WSL/Linux 执行，逐条确认内容；cgroup 负责资源约束。任务取消与恢复的整体流程归入 L2。

实现：[执行器](../../src/taskloom/adapters/executor.py)、[Linux 资源管理](../../src/taskloom/adapters/linux.py)。

## 2. L2：Agent 任务管理

L2 维护完整任务，决定哪些步骤已经就绪。工具步骤交给 L1，模型步骤交给 L3，结果返回后继续推进任务；检查点、取消和共享操作也在这一层协调。

### 2.1 依赖调度

- [ ] **已接入：** 根据 Agent 已经提出的步骤和实际执行结果，逐步推进完整任务。

- **应用场景：** Agent 需要先读取资料，再分析结果；后续具体操作依赖前一步的返回内容。
- **算法原理：** 将任务拆成步骤，保存前置关系；只有依赖满足的步骤才可提交执行。模型产生新操作后，再把新步骤加入记录。
- **应用效果：** 任务按实际依赖推进，工具结果能够对应到后续模型回答；每个步骤和执行尝试都有清楚归属。
- **触发操作：** 上传文本并选择 `/stats`，查看读取、统计和模型回复的步骤记录。确认最终统计使用 `file_stats` 回执；再做普通问答，对比简单任务的执行路径。

资料统计技能会补齐必需的核验步骤，普通对话由模型按需调用工具。查看任务图或执行详情时，重点解释“哪个步骤在等待什么前置结果”。

实现：[Agent 循环](../../src/taskloom/runtime/agent.py)、[步骤与依赖管理](../../src/taskloom/client/service.py)。

### 2.2 检查点恢复

- [ ] **已接入：** 保存任务进度，并区分取消意图、真实停止、结果返回和费用结算。

- **应用场景：** 用户取消任务，或者运行时中断；系统需要知道哪些工作已经完成，哪些仍在运行，哪些结果尚未确认。
- **算法原理：** 保存步骤进度与执行身份，先记录取消意图，再通知对应执行方。恢复时查询原执行，已完成结果沿原身份接回；结果未知的工作进入核对。
- **应用效果：** 任务能够从已保存进度继续处理，避免重复执行或重复记账；旧执行结果有明确归属。守护进程负责发现个人端服务退出并重启。
- **触发操作：** 运行任务后取消，查看状态和资源收敛，再使用“核对并续作”观察后续推进。服务重启演示使用独立 profile，避免影响其他正在运行的任务。

这一机制协调 L1 的物理停止与 L4 的请求结算。现场可以用同一任务的执行记录，串起取消、停止确认、资源归还和结果核对。

实现：[任务状态管理](../../src/taskloom/client/service.py)、[检查点升级](../../src/taskloom/client/checkpoint_upgrade.py)、[守护进程](../../src/taskloom/adapters/supervisor.py)。

### 2.3 互斥锁

- [ ] **已接入的同步机制：** 多任务并发时，资源分配和任务账本保持一致。

- **应用场景：** 一个任务正在完成，另一个任务同时提交或取消，多个执行分支都要修改共享状态。
- **算法原理：** 用异步互斥锁保护短临界区，用数据库事务一起保存相关变更。网络和工具的长时间工作在锁外运行，通过 IPC 与执行器交接。
- **应用效果：** 防止重复分配和账本覆盖，同时允许多个任务的实际工作并发推进；状态变化仍能对应到同一任务与执行尝试。
- **触发操作：** 在不同会话并发提交任务，取消其中一个，让另一个正常完成。检查两项任务状态、资源归还和消费记录是否各自对应。

L1 的资源预留和 L4 的平台账本也使用各自的原子更新边界。此处重点展示完整任务协调过程中的同步与通信。

实现：[任务服务](../../src/taskloom/client/service.py)、[IPC](../../src/taskloom/adapters/transport.py)、[事务存储](../../src/taskloom/adapters/sqlite.py)。

### 2.4 共享访问控制

- [ ] **组件演示：** 使用 SingleFlight、读写锁和有序多锁协调共享操作。

- **应用场景：** 多个任务重复初始化同一工作区，或者同时读取、修改共同文件；部分操作还要同时获取多个锁。
- **算法原理：** SingleFlight 让同键请求等待一次共享执行；读写锁允许并发读、独占写；有序多锁按统一顺序加锁，避免互相反向等待。
- **应用效果：** 减少重复初始化，防止共享写入冲突，并消除相反加锁顺序造成的循环等待。
- **触发操作：** 在独立组件样例中并发请求同一初始化操作，观察只执行一次；再分别演示多读、读写竞争及相反输入顺序的多锁申请。

这些组件已具备独立实现。真实 Agent 工具的共享工作区访问控制接入后，可进一步展示多任务修改同一文件的完整场景。

实现及样例：[共享访问组件](../../src/taskloom/policies/access.py)、[并发样例](../../tests/unit/test_access.py)。

## 3. L3：个人模型请求调度

L3 汇集同一用户各项任务产生的模型请求，决定谁先发送，以及当前是否具备发送条件。请求发送后由平台 L4 接管，共享模型服务的最终准入由平台决定。

### 3.1 赤字轮转（DRR）

- [ ] **已接入：** 让长短任务按成本份额竞争个人端的模型请求机会。

- **应用场景：** 同一个人同时运行简短问答、资料分析和长工作流，每次请求的预计消耗差异较大。
- **算法原理：** 每轮给根任务增加一份调度额度，请求预计成本不超过累计额度时才能派发，并扣除成本；昂贵请求可以跨轮累计。完成后按实际消费校正差额。
- **应用效果：** 轻量请求可以在同一份额内多次获得机会，昂贵请求积累额度后也能执行。后续步骤沿用根任务的成本归属和结转记录。
- **触发操作：** 在同一用户的不同会话交替提交短问答与资料分析，形成持续排队。结合派发顺序和消费记录，观察轻重请求如何获得机会；定量演示使用成本已知的受控样例。

这里的调度额度用于比较公平份额，账号余额用于限制实际消费。验收时比较成本服务量和等待时间，允许不同成本任务获得不同的派发次数。

实现：[成本 DRR](../../src/taskloom/policies/cost_drr.py)、[个人请求调度器](../../src/taskloom/client/model_scheduler.py)。

### 3.2 优先级调度

- [ ] **已接入：** 即将到期或被用户标为高优先级的请求，可以获得有界的提前机会。

- **应用场景：** 长任务积压时，出现需要尽快完成的交互任务；用户也可能临时提高某项工作的紧迫程度。
- **算法原理：** 在成本轮转上增加期限和优先级选择。接近截止时间的请求优先考虑；提升要扣成本，并受连续次数限制，之后给正常轮转机会。
- **应用效果：** 紧迫工作能更早推进，同时保留其他任务的服务机会；调整优先级影响待发送请求。
- **触发操作：** 在受控样例中设置一个较早截止的任务；另在界面提高等待任务的优先级。观察两类提升，以及持续加入紧急任务时普通任务仍然推进的过程。

当前个人端的紧迫窗口为 60 秒，连续提升上限为 2；运行中的请求沿原调用完成。期限到达后，等待请求进入明确终态。

实现：[提升规则](../../src/taskloom/policies/aging.py)、[算法参数](../../src/taskloom/client/service.py)。

### 3.3 老化（Aging）

- [ ] **已接入：** 等待过久的根任务获得提升机会。

- **应用场景：** 前台请求持续进入，后台工作可能长时间排在后面。
- **算法原理：** 记录请求入队时间，等待超过阈值后提高其选择机会。老化提升与期限、手动优先级共同遵守连续提升上限，提升仍计入成本账本。
- **应用效果：** 后台任务积累等待后能够推进，减少持续竞争下的长期饥饿。
- **触发操作：** 在受控队列中让后台请求先等待，再持续加入其他请求。越过老化阈值后，查看后台获得提升及后续执行的过程。

当前个人端老化阈值为 20 秒；演示可使用样例时钟直接推进到阈值，避免现场长时间空等。

实现：[老化队列](../../src/taskloom/policies/aging.py)、[持续竞争样例](../../tests/unit/test_aging.py)。

### 3.4 背压控制

- [ ] **已接入：** 平台繁忙或额度受限时，个人端合理保留请求并等待。

- **应用场景：** 多用户共用有限模型槽位，账号还受预算、Token 窗口和待处理数量限制。
- **算法原理：** 发送前读取平台反馈，分别检查账户整体条件和单条请求条件。暂时受限则等待，可恢复后唤醒；永久预算不足则拒绝，单条不可行请求可以让位给其他可行任务。
- **应用效果：** 减少拥堵时的无效提交，资源恢复后继续派发；某条大请求暂时发不出去时，其他可行任务仍能推进。
- **触发操作：** 在共享模型槽位为 1 的环境中，让 Alice、Bob 同时提交任务。观察本地等待、平台占槽及请求完成后的唤醒；请求级绕行用大小请求的受控额度样例展示。

L3 管发送时机，L4 管实际准入。两层使用同一平台路径衔接，反馈等待也受到任务截止时间约束。

实现：[反馈判定](../../src/taskloom/client/feedback_decision.py)、[反馈感知调度](../../src/taskloom/client/model_scheduler.py)。

## 4. L4：平台多用户请求调度

L4 接收各个人端的请求，在账号和根任务之间分配共享模型槽位，同时保护平台额度。它安排请求进入固定模型服务的顺序，记录实际占用和消费，并向 L3 返回反馈。

### 4.1 分层公平调度

本组四种策略均已接入，可以在平台控制台切换。演示占槽差异时使用至少 2 个槽位和持续竞争负载；相同初始负载的独立回放用于比较策略效果，热切换用于展示策略生效。

#### 4.1.1 轮转调度（RR）

- [ ] **已接入：** 按轮次分配用户和根任务的请求机会。

- **应用场景：** 一个用户提交大量任务，其他用户也有请求等待服务。
- **算法原理：** 外层在账号之间轮转，内层在该账号的根任务之间轮转，同一根任务内选择可行请求。
- **应用效果：** 请求归到统一账号份额，多个任务在用户内部继续轮转；长短请求按派发轮次竞争。
- **触发操作：** 控制台选择 `rr`，让 Alice 大量提交、Bob 少量提交，观察两人的交替派发及各自根任务的执行记录。

#### 4.1.2 最大最小公平（Max-Min）

- [ ] **已接入：** 优先把空槽给当前占用较少的用户与根任务。

- **应用场景：** 多个槽位被部分用户占用，其他用户有积压请求却占槽较少。
- **算法原理：** 先比较可服务用户当前持有的槽位数，优先选择最少者；用户内部同样选择占槽较少的根任务，同等占用时轮转。
- **应用效果：** 新释放的槽位逐步补给当前占用较少的一方，改善即时分配均衡。
- **触发操作：** 在至少 2 个模型槽位的回放中选择 `maxmin`，让 Alice 先占槽，再加入 Bob 请求；观察下一空槽分给谁。

#### 4.1.3 槽位时间公平

- [ ] **已接入，配置名为 `drr`：** 根据已获得的服务时间分配后续机会。

- **应用场景：** 长请求与短请求各占一个槽，但占用时长相差很大，仅按请求次数轮转容易产生服务量失衡。
- **算法原理：** 用“槽位数×占用秒数”记录服务量，优先选择已获服务较少的一方；在途请求也计入占用估计，EWMA 平滑历史耗时，新完成样本的权重为 0.2。
- **应用效果：** 长时间占槽的一方在后续分配中承担相应记账，已获服务较少的用户得到补偿机会。
- **触发操作：** 使用相同长短请求回放，切换到 `drr`，比较各用户累计槽位时间和派发变化。

平台这项策略按槽位时间衡量公平，L3 Cost DRR 按请求成本累计量子；两者的资源口径和选择规则分别说明。

#### 4.1.4 混合公平调度（Hybrid）

- [ ] **已接入：** 同时考虑当前占槽和已经获得的槽位时间。

- **应用场景：** 平台既要照顾眼下占槽较少的用户，也要缓解长短请求导致的长期服务量差异。
- **算法原理：** 先比较当前占槽数，较少者优先；相同时，再比较已获槽位时间，较少者优先。用户与根任务两级使用同样规则。
- **应用效果：** 在即时分配和历史服务量之间兼顾，具体改善通过相同负载下的对照测量。
- **触发操作：** 控制台选择 `hybrid`，回放同一份负载；对比 `rr` 的短任务等待和用户槽位分配。也可在对照实验页查看组合策略的长期结果。

实现：[四种平台策略](../../src/taskloom/policies/scheduling.py)、[平台接线与策略切换](../../src/taskloom/gateway/service.py)。回放操作见[L4 控制台说明](../../tests/l4/README_v1.1.md#5-调度控制台演示)。

### 4.2 限流与预算控制

- [ ] **已接入：** 统一限制共享并发、账号并发、请求数、Token 和费用。

- **应用场景：** 多个账号同时调用平台，既可能占满槽位，也可能超出时间窗口限额或可用预算。
- **算法原理：** 派发前一起检查根任务、账号和平台的许可；请求数与 Token 按固定窗口计量，费用按最坏情况预留，完成后用实际回执结算。
- **应用效果：** 容量与费用保持在约束内；临时占用释放后可以继续派发，永久预算不足有明确结束结果，重复查询保持一次结算。
- **触发操作：** 并发提交请求观察占槽上限；使用限额较小的受控账号分别触发窗口等待、在途预算占用和永久预算不足，再查看平台账本变化。

费用与 Token 分别计量。预算保护使用“已消费＋在途最坏费用”，预计消费预留用于展示和估计。

实现：[预算预留](../../src/taskloom/policies/reservation.py)、[平台准入与结算](../../src/taskloom/gateway/service.py)。

### 4.3 指数退避

- [ ] **已接入：** 对明确未执行的上游拒绝安排延后重试。

- **应用场景：** 上游暂时拒绝请求，并且系统能确认这次没有执行、没有消费。
- **算法原理：** 每次重试前增加等待间隔，当前从 1 秒起步，按倍数增长，最多 30 秒；结合次数和截止时间限制重试。
- **应用效果：** 缓解连续重发给上游造成的压力，保留暂时失败后的恢复机会；结果未知的请求进入原身份核对流程。
- **触发操作：** 用可控上游依次返回明确拒绝、成功，观察请求的等待时间和最终结算。对比持续拒绝样例，确认它能结束。

实现：[拒绝处理与退避](../../src/taskloom/gateway/service.py)。

### 4.4 亲和调度

- [ ] **条件接入：** 配置多个上游账号后，为同一任务链选择账号并控制亲和等待。

- **应用场景：** 平台有多个上游账号，同一任务链连续调用；切换账号可能失去可复用的提示词缓存。
- **算法原理：** 优先选择近期使用过且有空槽的账号，否则选择相对负载较低的账号。开启延迟放置后，可以在设定时间内等待亲和账号；关联记录超过上限时按 LRU 回收。
- **应用效果：** 在复用机会和等待时间之间取舍。账号选择可以直接观察，缓存命中与费用收益结合供应商回执评价。
- **触发操作：** 在受控配置中设置至少两个 `pool_accounts`，比较 `cache_wait_seconds=0` 与一个较小正值；观察亲和账号繁忙时，请求等待多久、最终分配给谁。

当前日常单上游环境用于展示 L4 共享调度，本项通过多账号配置或回放展示。

实现：[亲和放置与 LRU 记录回收](../../src/taskloom/policies/placement.py)、[上游账号配置](../../src/taskloom/contracts/models.py)。
