# TaskLoom「织序」工程搭建与后续开发计划

**更新日期** 2026-10-20 · **阶段** 0.2 基线维护与多工具、调度增量开发 · **依据** [当前完整方案](../TaskLoom_项目说明书_当前完整方案.md)

TaskLoom 由个人客户端和统一模型服务平台共同组成。个人端使用平台注册账号的 API Key，平台管理账户额度与固定总服务容量。本文规定可运行工程的边界、开发规则和后续算法实施顺序，当前代码结构见[基础工程架构](TaskLoom_基础工程架构.md)。

## 1. 工程目标与系统模型

### 1.1 产品边界

个人端在用户电脑运行 Agent、任务管理和工具执行，包含 L1—L3；平台端承载账号、L4、统一模型服务连接和固定模型池。首版使用 WSL2 Ubuntu / Python 3.12，Windows 作为编辑、启动与浏览器环境。

平台 API Key 确定用户身份和账户额度。个人端的所有受管模型步骤经过本平台，模型池内部密钥只由平台持有。反馈开关改变调度策略，保持调用路径与资源容量一致。

### 1.2 固定资源与比较条件

| 资源域 | 管理者 | 当前表达 |
|---|---|---|
| 本机工具。 | L1 与 executor。 | 工具名额、内存、产物预算、cgroup 硬限制。 |
| 根任务。 | L2/L3。 | 期限、私有预算、步骤、尝试与成果。 |
| 平台账户。 | L4。 | 累计预算、窗口请求/token、在途上限。 |
| 平台服务池。 | L4 与固定模型服务。 | 总并发容量、总预算/窗口、固定模型与处理配置。 |

当前模型池用固定并发槽位和模拟响应时间代表服务能力。对照实验保持池容量、模型、到达工作量和成果要求一致，再测任务等待、公平性和按时交付。真实模型服务接入时继续固定推理配置。

### 1.3 真实任务闭环

1. 用户在个人端连接平台账号，提交资料任务，创建 Task 和 Agent。
2. L2 生成模型步骤，L3 核对个人预算与平台反馈，L4 取得账户和全局许可后派发。
3. 模型提出工具调用，L1 预留资源，executor 启动真实文件工具并回传结果。
4. 后续模型步骤继续经过 L3/L4，个人端验收最终 JSON，分别记录结果、停止和消费。

## 2. 模块、协议与配置

### 2.1 代码所有权

| 代码组 | 职责 | 扩展位置 |
|---|---|---|
| domain、contracts、policies。 | 身份、资源规则、边界模型与纯队列。 | 资源算法、模型契约、成本策略。 |
| runtime、client、execution。 | Agent 推进、本机任务、个人请求与工具实现。 | 多工具、工作区、子 Agent、任务画像。 |
| gateway。 | 平台账户、L4 调度、两级额度和反馈。 | 账号份额、成本 DRR、期限和老化。 |
| adapters、bootstrap、web。 | SQLite/HTTP/Linux 实现、角色装配和本地界面。 | 真实模型池、部署适配、观测展示。 |

composition root 位于 bootstrap。业务模块依赖端口，client 与 gateway 经 HTTP 契约交互；domain/policies 仅使用标准库。import-linter 执行三个依赖约束。

### 2.2 角色与配置

| 角色 | 配置类 | 持有的配置 |
|---|---|---|
| client、executor、supervisor。 | ClientConfig。 | profile、本平台 URL、本地预算、个人并发与反馈开关。 |
| platform。 | PlatformConfig。 | 模型池连接、内部密钥、总容量、全局及注册账户限额。 |
| model-pool。 | PoolConfig。 | 固定容量、延迟、模型名称和内部密钥。 |
| 开发拓扑。 | tools/project.py 与 Topology。 | 端口、私有状态、真实开发账号初始化和进程清理。 |

个人 Key 单独存于 clients/<profile>/platform-credentials.json，权限 0600。账号密码在平台加盐哈希保存，API Key 在平台保存摘要。普通注册请求由平台分配额度。

### 2.3 接口与身份

账户接口提供注册、登录、本人反馈与 Key 撤销；请求接口提供根任务登记、请求接纳、查询及取消。个人端 API 代理账号连接操作并推进本地任务，浏览器经本机 HTTP 操作本地后端。

每次模型步骤携带 root_task_id、agent_id、step_id、attempt_id、request_id、deadline_at 和 cancel_generation；认证 Key 在传输层提供账户身份。平台内部请求身份由账号和外部请求 ID 共同导出，跨账户同名请求彼此隔离。

一个 profile 绑定一个 platform_id/account_id。一个账号可以拥有多个 Key，多个 Key 共享该账户的账本和限额。

### 2.4 持久化与升级

个人端持有任务和工具文件；平台持有账号、请求和两级额度；模拟模型池持有请求凭据。数据库分别位于 clients/<profile>/client.db、platform/state.db、platform/pool.db。

0.1 的 gateway/state.db、provider/state.db 首次复制到新位置，保留旧文件；已有新账本不覆盖。更换平台身份或账号使用新的 profile。未知派发继续按原请求核对，保持消费归属。

## 3. 正确性与验证

### 3.1 身份、资源与预算不变量

| 事实组 | 必须保持的规则 |
|---|---|
| 归属。 | 平台身份取自认证账号；子 Agent、Step、Attempt 继承根任务归属。 |
| 资源。 | 许可与预留原子取得，工具资源按实际停止归还；未确认执行保持隔离。 |
| 账本。 | 请求、账户额度与全局额度同事务更新，按实际消费结算一次。 |
| 结果。 | 检查输入版本和取消代次，旧结果保持原尝试消费及发布归属。 |

本地短锁和 SQLite 写入线程保护状态。网络调用、工具计算和长时间等待在事务之外执行。状态事件与对应记录原子保存，控制查询读取轻量状态。

### 3.2 有界运行与故障处理

个人端限制任务、工具、输出与产物总量；平台限制账户数量、Key 数量、请求/排队字节和保留历史；模型池维持固定容量。开发范围先使用受控文件工具。

取消先保存意图，再处理排队移除与实际停止。网络结果不明进入 UNKNOWN，保留相应预留并查询原请求。supervisor 核对 PID、启动 ticks 和 boot_id，避免按陈旧 PID 操作其他进程。

### 3.3 统一开发入口

| 入口 | 实际责任 |
|---|---|
| doctor、bootstrap、lock。 | 检查环境、locked 安装、显式更新锁文件。 |
| format、check。 | 格式、lint、严格类型与依赖边界。 |
| test unit/integration/smoke/linux。 | 定向行为、协议、进程和 Linux 资源验证。 |
| verify、verify-isolated。 | 聚合检查与构建；干净副本、新环境和源码外 wheel 双账户运行。 |

所有入口使用 tools/project.py，Windows 自动转交 WSL。Linux 使用 python3。更新依赖或发行版本后显式执行 lock，日常安装使用 locked。

### 3.4 验证矩阵

| 改动内容 | 必需验证 |
|---|---|
| 账户、协议与存储。 | 注册/登录/撤销、身份隔离、额度权限、持久恢复和 integration。 |
| 调度与额度。 | 根任务公平、双用户共享容量、账户/全局预留、未知派发和幂等结算。 |
| 工具、守护与取消。 | 输出排空、输入版本、排队/运行取消、SIGKILL 恢复及 test linux。 |
| 完整交付。 | 注册新 profile 后真实任务、双账户流程、浏览器、verify 和 verify-isolated。 |

## 4. 实施阶段与交接

### 4.1 当前里程碑

P0—P2 建立运行、资源保护和工程验证底座。0.2 在该底座上完成统一系统改造：平台账户、分离配置、账户/全局账本、固定模型池和基本反馈等待。已合并范围、待合并 PR 与最新验证以[当前实现与开发状态](TaskLoom_当前实现与开发状态.md)为准；原改造验收作为历史记录归档。

P3 先修复并接通多工具与 L3 调度增量，再扩展子 Agent、工具画像和平台分层公平；随后验证阶段银行家、期限/老化与反馈消融。真实原版 OpenClaw 对照纳入首版实验，完整兼容接入后续独立交付。各阶段先建立可验收工作负载，再测算法增量。

### 4.2 本机体验与新账号

最短启动命令见[根 README](../../README.md)。dev 自动启动 Alice、Bob 两套客户端，连接同一个平台与模型池，用于多用户竞争展示。

在 dev 运行期间，可另开终端创建尚未登录的个人端：

```powershell
python tools/project.py client --profile charlie --port 8799
```

打开 http://127.0.0.1:8799，在“配置平台账号”注册或登录，平台地址填写 http://127.0.0.1:8796。也可以连接已有账号 Key。客户端重启后读取本机凭证并恢复原账号。

```powershell
python tools/project.py stop-client --profile charlie
```

该命令只停止指定 profile 的监督服务；dev 拓扑由 stop 统一结束。运行数据和环境路径由 doctor 输出。

### 4.3 团队工作包

团队拆成总体集成、个人端 Harness、个人端请求调度、本地资源、平台调度和实验可视化六个工作包。建议人选及职责维护在[当前完整说明书](../TaskLoom_项目说明书_当前完整方案.md)第 4.4.1 节，实际负责人以 [Gitee 工作包 issue](https://gitee.com/Sugaria/TaskLoom/issues) 的认领结果为准。

各工作包 issue 给出当前基础、首批交付、代码入口、协作接口和验收标准。WP2 产生工具步骤与模型请求，WP3/WP5 消费其身份、参数和状态，WP4 核对真实执行与资源归还，WP6 统一指标；集成时共同核对成本单位、数量上限、终态和最终成果。阶段 PR 按[PR 交付约定](TaskLoom_PR提交与验收约定.md)提交。成员加入、链接邀请、分支与 Pull Request 流程见 [Gitee 协作说明](TaskLoom_Gitee协作说明.md)。

### 4.4 日常维护

当前代码、协议和执行命令定义工程事实，项目说明书定义产品与研究目标。修改公共契约同步调用方和集成测试；修改资源与消费同步不变量及故障测试。

本地 Git 保持可检查状态，提交、远程与发布由独立用户指令授权。当前研究原文继续本地留存，旧说明书、图稿与历史验收按[备份索引](../../backup/README.md)追溯；运行秘密与依赖继续使用忽略规则隔离。
