# L4 独立开发环境

WP5 在不启动个人端、执行器和模型池进程的情况下开发和验证平台 L4。真实的 `GatewayService` 运行在虚拟时间事件循环上，周边各层由 `l4kit` 替身提供。一小时负载通常在数秒内完成，同一负载重复运行得到相同结果。

## 1. L4 的输入与输出

| 方向 | 对接方 | 内容 | 替身 |
|---|---|---|---|
| 输入 | L3 个人端 | 账号身份、根任务登记、`ModelRequest`、取消、查询、反馈轮询，以及到达时间。 | `SimulatedClient`：闭环 Agent 链，支持扇出、思考时间和反馈等待。 |
| 输入 | 固定模型池 | 服务时长、实际用量，以及执行前拒绝、完成、结果未知和核对回执。 | `ScriptedPool`：按请求编排延迟、用量和故障。 |
| 输入 | 配置与时钟 | `PlatformConfig`、账户限额、当前时间。 | `VirtualEventLoop.wall` 注入 `GatewayService(clock=...)`。 |
| 输出 | L3 | 准入或拒绝原因码、请求状态、结果与用量、`PlatformFeedback`。 | 由 `SimulatedClient` 消费。 |
| 输出 | 模型池 | 派发顺序与时刻，在途量不超过容量。 | `ScriptedPool.log`、`peak`。 |
| 输出 | WP6 | 逐账号、逐根任务的服务量、等待与消费。 | `metrics.summarize`、`MemoryRepository.event_log`。 |

持久化使用 `MemoryRepository`，不使用线程，每次写入经过 JSON 往返。账户直接写入存储，不调用 PBKDF2 注册。

## 2. 常用命令

```bash
python3 tools/project.py test l4
uv run --locked python tests/l4/simulate.py --users 8 --tasks 6 --capacity 2
uv run --locked python tests/l4/simulate.py --seed 3 --save trace.json
uv run --locked python tests/l4/simulate.py --load trace.json --uncoordinated
```

`simulate.py` 输出各账号的请求数、派发数、成本服务量、等待 P50/P95、错误码，以及各任务类别的按时完成情况。`--uncoordinated` 使客户端忽略平台反馈，用于反馈消融。

## 3. 编写场景

```python
from l4kit import AccountSpec, Behavior, Scenario, ScriptedPool, TaskSpec, Workload, run_scenario

pool = ScriptedPool(capacity=2)
pool.plan("alice-root-b0-r0", Behavior(fault="lost"))  # 请求名为 <root>-b<分支>-r<轮次>
workload = Workload((AccountSpec("alice"),), (TaskSpec("alice", "alice-root", rounds=3),))
result = run_scenario(Scenario(workload, pool=pool))
assert result.violations == []
```

`Scenario` 运行期间定期检查 `ledger.ledger_violations`。检查项包括请求、账户和全局三级预留、消费与在途量是否一致，窗口和预算是否越限，以及模型池是否发生重放或超出容量。

`mixed_workload` 按交互、资料、代码三类任务生成泊松到达和对数正态 token 分布。`Workload` 可以保存为 JSON 轨迹，后续可以替换为真实运行或公开数据集轨迹。

## 4. Benchmark

benchmark 的用途是：用同一套负载、同一组指标和同样的随机种子测试任意调度策略，得到可以直接相互比较的分数。它由两部分组成：一般样本衡量平台在日常流量下的服务质量；对抗探针每个只放大一种在真实轨迹中观察到的特征，并检验一条明确的论断。

### 4.1 命令

```bash
uv run --locked python tests/l4/bench.py run                  # 完整运行：一般样本 × 两档负载，探针 × 3 个种子
uv run --locked python tests/l4/bench.py run --quick          # 冒烟：每类 2 个样本、每个探针 1 个种子
uv run --locked python tests/l4/bench.py run --policy rr      # 对照：原用户/根任务轮转
uv run --locked python tests/l4/bench.py run --placement rotate  # 网关不放置，由模型池轮转放置（WP5 前的设置）
uv run --locked python tests/l4/bench.py compare OLD NEW      # 两次结果在相同样本和种子上做配对差值
uv run --locked python tests/l4/bench.py facts                # 用本地轨迹重算校准常数，列出偏差
uv run --locked python tests/l4/bench.py export-traces --abyss PATH/abyss.sqlite
```

`run` 还接受 `--families`、`--probes`、`--seeds`、`--jobs`、`--policy` 和 `--placement` 参数（见 4.3）。结果写入 `.runtime/l4bench/results/<时间>/`：

- `runs.jsonl`：逐次运行的原始指标；
- `summary.json`、`summary.md`：得分和置信区间；
- `provenance`：记录 commit、`src` 改动摘要、调度策略、账号放置方式、每个上游账号的槽位数、校准常数和轨迹文件哈希，用来追溯结果来源。

### 4.2 数据来源与隐私

| 来源 | 内容 | 用途 |
|---|---|---|
| Aether `usage` 表（2026-07-06 至 10-19，22 个用户，34 个 Key，26 万条） | 到达时间、输入和缓存 token、输出 token、真实时延、状态 | 多用户到达过程、份额倾斜、时延、故障率 |
| abyss 采集库（183 个 Claude Code / Codex 会话，1.3 万次请求） | 会话、子 Agent、每轮的 token | Agent 链结构：轮数和思考间隔 |

- **导出方式**：`l4bench/traces.py` 只读导出。Aether 的用户 ID 和 Key ID 在 Postgres 内部就做了哈希，原始 ID 不会经过 SSH；abyss 在本地做哈希。导出只选数值字段，不读任何请求或回复正文。
- **存放位置**：轨迹 CSV 和结果都在 `.runtime/l4bench/` 下，该目录已被 git 忽略；缺少轨迹时只运行合成样本。
- **校准常数**：`l4bench/facts.py` 集中保存全部常数并注明来源，包括 token 分位数、缓存命中率、时延拟合、故障率、单用户并发与突发峰值、思考间隔和轮数。没有私有数据也能运行。`facts.measure` 从本地轨迹重算这些常数，`test_facts_match_the_local_traces` 要求偏差不超过 3%。

### 4.3 单位与负载

- **缩放**：所有 token 数除以 `SCALE = 100` 后再送入网关，避免网关每次扫描都要序列化 10 万 token 的正文。服务时长保持真实秒数，因此池占用是真实的。
- **代价**：模型池按价格加权的 token 当量计费，1 单位等于 100 个未缓存输入 token。Aether 这个部署的成本字段全为 0，所以使用公开标价的比例：

  | 系列 | 输出 | 缓存读取 | 缓存写入 |
  |---|---|---|---|
  | Claude | 5× | 0.1× | 1.25× |
  | GPT | 8× | 0.1× | 1× |

  `suites.platform` 把同样的倍率配置给网关（输出 5×、缓存读取 0.1×、缓存写入取较大的 1.25×）。网关按最坏值准入预算，按估算值记预留；benchmark 测量的是估算与实际计费之间的偏差。
- **负载**：负载等于"工作负载在容量无限的平台上的平均忙碌槽位数"除以池容量。这个均值沿每条链自己的理想时间线计算，所以闭环链在最后一次到达之后才完成的工作也会算在实际发生的时间里。一般样本使用名义负载 1.0（接近饱和）和 2.0（持续过载）。闭环链排队时会自我减速，所以实际利用率低于名义值。
- **容量**：池容量取 `round(理想并发 / 负载)`，下限为 2（`calibrate.capacity_for`），保证存在可以分配公平或不公平的余地。取整会让各样本的实际负载偏离名义值，所以报告按名义负载分组，并列出实际负载的均值和范围。
- **上游账号与缓存**：模型池由多个上游账号组成，每个账号 `SLOTS_PER_ACCOUNT` 个槽位，各自持有独立的提示缓存。链的缓存只留在服务过它的账号上，并随空闲时间衰减（`facts.cache_retention`）；调用落到别的账号时，未命中部分按未缓存价格补计，记入该次计费。链的第一次调用缓存状态未知，按计划计费。依据是 Aether 自 2026-09-05 起的数据（此后每个提供商是独立账号，统计输入不少于 2 万 token 的请求）。口径是"该用户最近是否用过这个上游 Key"，而不是与上一个请求比较：
  - 99.6% 的后续请求落在近期用过的上游上，命中率 0.93；从未用过的上游命中率只有 0.12（仅与其他用户共享的前缀）；
  - 缓存没有固定的 TTL，而是在约一小时内逐渐衰减：空闲 5–10 分钟命中 0.81，10–30 分钟 0.70，30–60 分钟 0.57，1–6 小时 0.31。
- **调度策略**：`run --policy` 设置 `PlatformConfig.scheduling_policy`，默认 `hybrid`；`rr`、`drr`、`maxmin` 为对照，见 `taskloom/policies/scheduling.py`。`--samples`、`--loads`、`--no-uncoordinated`、`--set KEY=JSON` 用于开发时跑子集和扫参数，正式结果使用默认值。
- **账号放置**：`run --placement` 选择由谁选上游账号：`gateway`（默认）在 `PlatformConfig.pool_accounts` 中列出模型池的账号（`a0`、`a1`……），由网关在派发时放置（缓存亲和：链上次用的账号有空槽就留在原处，否则选负载最低的账号）；`rotate` 和 `sticky` 不列账号，网关不指定账号，由模型池的替身放置：`rotate` 是不看缓存的轮转负载均衡，`sticky` 优先选最近服务过该链的账号，用于和 WP5 之前的结果比较。策略和放置方式写进每次运行的 `run` 字段和 `provenance`；`compare` 只按样本、负载、探针和种子配对，因此可以直接比较不同策略或放置方式的两次结果。

### 4.4 一般样本

共 32 个样本。每个样本分别在负载 1.0 和 2.0 下运行，客户端听从平台反馈；另外在负载 2.0 下用忽略反馈的客户端再运行一次，作为反馈的对照组。

| 类别 | 数量 | 构造 |
|---|---|---|
| `aether` | 16 | 从至少有 3 个用户、平均需求至少 2 个槽位的真实小时中随机抽两个，叠加到同一平台上，两小时的用户分别作为不同账号。Aether 没有会话 ID，所以按 Key 把重叠的请求还原成并行的链，空闲超过 10 分钟就视为新的根任务 |
| `abyss` | 8 | 把会话片段按 Aether 的份额倾斜分配给 4、8 或 16 个用户，起始时间服从泊松分布，片段内部保持真实时序 |
| `synthetic` | 8 | 按 facts 中的分布抽样生成泊松到达的任务，用户份额倾斜与 abyss 相同。生成时的目标是 `SYNTHETIC_SLOTS = 16`，但长链会延续到到达窗口之后，实际理想并发约为 4 |

每次运行最多 900 个请求（`MAX_REQUESTS`）。这原本是为了避开网关终身 1024 条记录的上限（现已改为只限制在途请求），这也把单个样本的理想并发限制在 2.5–6 个槽位左右。当前 benchmark 版本为 `VERSION = 2`：多账号模型池、缓存计费和新的权重改变了分数的含义，`VERSION = 1` 的结果不能与之比较。上限修复后放大样本会改变样本本身，届时也必须升级版本号，旧版本的结果不再可比。

### 4.5 对抗探针

每个探针默认运行 3 个种子；标注"配对"的探针还会运行一次去掉对抗方的对照。

| 探针 | 放大的实测特征 | 论断 | 判定（满分 → 零分） |
|---|---|---|---|
| `fanout-agents` | 单用户并发峰值为 16 | 一个根任务下开 16 个子 Agent，所得不超过最大最小公平份额 | 账号级公平偏差 0.05 → 0.5 |
| `fanout-roots` | 同上 | 拆成 16 个根任务，所得同样不超过公平份额 | 同上 |
| `decode-heavy` | 输出 P99 为 5.3k token，约占用槽位 140 秒 | 长输出不会挤占他人的槽位时间 | 同上 |
| `burst` | 单用户一分钟内发起 81 个请求 | 突发不降低其他用户的 SLO | 受害者 SLO 与对照组之比 0.95 → 0.5（配对） |
| `skew` | 头部用户占 36% 的请求 | 重度用户在场时，轻度用户的 SLO 不受影响 | 份额靠后一半用户的 SLO 达成率 |
| `outage` | 70% 的失败集中在故障分钟内，最长 10 分钟 | 故障过后容量和进度都能恢复 | (1 − 泄漏槽位/容量) × 完成率之比（0.9 → 0.4，配对） |
| `retransmit` | 回复丢失、重复传输、中途取消 | 每个可核对的请求都只结算一次 | 无遗留的可核对 UNKNOWN 为满分，否则为 0 |
| `endurance` | 单用户 3.5 个月内发送 9.3 万个请求 | 接纳不受任何固定数量上限的限制 | 1400 个任务中最后 200 个的完成率 |
| `budget-tight` | 输出单价是输入的 5–8 倍，缓存读取为 0.1 倍 | 预算能用足，但绝不超支 | 预算使用率 0.9 → 0.3，乘以超支 0 → 10% |
| `cache-affinity` | 链被换到没用过的上游账号时，只剩约 12% 的缓存 | 链留在持有其缓存的账号上，同时不被饿死 | 热链的缓存保留率 0.9 → 0.5 |
| `elephant` | 输入可达 90 万 token，与小请求共享 token 窗口 | 大预留请求不会被小请求饿死 | 等待的窗口数 2 → 10 |
| `namespace` | 根任务 ID 由客户端自选 | 其他账号使用同名根任务，影响不到你 | 受害者全部完成为满分，否则为 0 |

### 4.6 指标

- **需求按客户端计算**：一个请求从所在的链准备好发送（思考结束）开始算作需求，直到回复完成或客户端放弃为止。这样不管请求在客户端等待还是在平台排队，口径都一致。分配指平台的在途集合。
- **精确积分**：在相邻两个事件之间，需求和分配都保持不变，所以所有指标都是精确积分，不需要选采样间隔（`l4bench/timeline.py`）。
- **公平偏差**：在有人等待的时段，以当前在用槽位按最大最小公平（water-filling）分配作为参照，统计放错位置的槽位所占比例，再按时间平均。分别在账号级和账号内部的根任务级计算；只有一条链的账号持有 1 个槽位不算吃亏。公平的单位是**池的槽位时间**（同时占用的槽位数），也就是长输出请求实际占用的资源。这是有意的选择：按 token 代价分配的 DRR 也会按槽位时间来评判；代价份额只出现在原始指标里，不计分。
- **浪费**：有需求时池中空闲的槽位时间，占所需槽位时间的比例。
- **饥饿**：等待超过 300 秒（`STARVATION_WAIT`）的请求比例。300 秒是缓存开始衰减、交互用户早已察觉的时点，不是缓存有效期。
- **缓存**：取自 `ScriptedPool.log`，链的第一次调用除外。`cache_retention` 是后续调用读取的缓存 token 中仍留在所在账号上的比例，按缓存 token 加权，没有这类调用时记 1；`cache_miss_cost` 是未命中补计的费用占总计费的比例；`account_moves` 是后续调用中被放到与上一次不同账号的比例。
- **SLO**：按任务减速比给分，减速比是完成时间除以空闲平台上的完成时间。≤ 2 记 1 分，≤ 5 记 0.5 分，更慢或失败记 0 分。先在每个账号内求平均，再在账号之间求平均。
- **预留精度和超支**：预留精度是实际计费除以预留（网关的估算值）；超支是计费超出估算的部分占总计费的比例，衡量估算偏低，不是预算越限，预算越限由 `budget_overrun` 和账本的 `limit:` 检查报告。另外报告泄漏的在途量。
- **账本**：`ledger_violations` 分两类。一致性问题包括三级汇总不符、在途量超过容量、重放、计费与模型池执行不能逐笔对应（恰好一次计费检查），这些是硬门槛。窗口或预算超限带 `limit:` 前缀，算作估算误差，只计入扣分。

### 4.7 得分标准

**硬门槛**：账本一致性有任何违例，这次运行记 0 分，整份结果标记为未通过。

**一般得分**（每次运行 0–100 分，使用听从反馈的客户端）。各项锚点固定，这样不同策略、不同时间的分数可以直接比较：

| 部分 | 权重 | 满分 → 零分 |
|---|---|---|
| SLO | 25 | 各账号平均的 SLO 分 |
| 公平 | 20 | 偏差 0.05 → 0.5；账号级占 70%，根任务级占 30% |
| 缓存 | 35 | `cache_miss_cost` 0 → 0.5：放置和排队造成的缓存未命中，多花的钱占总计费的比例。按实际价格计，未命中的缓存 token 按写入价 1.25 计费，而不是读取价 0.1，约贵 11 倍；按 token 数算的命中率会掩盖这一点。0.5 表示一半的账单花在丢掉的缓存上 |
| 饥饿 | 10 | 超过 300 秒的比例 0 → 10% |
| 效率 | 10 | 浪费 0 → 20% |

计费不单独计分。上游账号超支后就停了，它的链只能换到别的账号，缓存随之丢失，这部分损失已经计入缓存项。预留精度 `reservation_precision` 和超出预留的比例 `overrun` 仍作为原始指标报告。

**探针得分**：用各探针自己的判定函数打分，取各种子的平均，≥ 80 分为通过。配对探针缺少对照运行时，该种子记 0 分，并在报告中列出。

**总分** = 0.6 × 一般得分 + 0.4 × 探针平均分。

- 一般得分是三个类别平均分的平均，各类别权重相同（aether 有 16 个样本，abyss 和 synthetic 各 8 个，样本数不影响权重）。每个样本先对两档负载求平均。95% 置信区间用分层 bootstrap，在各类别内部重抽样本。
- 探针每项只有 3 个种子，bootstrap 不可靠，所以用 Student-t 区间，同时报告最低分。

**反馈增益**单独报告，不计入总分：在负载 2.0 下，同一批样本中听反馈与不听反馈两组的 SLO 配对差值。

**比较两种策略**：用 `compare`，在相同的样本、负载和种子上计算配对差值及其置信区间。只有当置信区间不包含 0 时，才算有改进。

### 4.8 已知局限

- 网关内存只保留在途请求和最近完成的记录（默认 300 秒、最多 1024 条），较早的记录从存储读取；在途请求上限为 1024。`MAX_REQUESTS` 尚未放大，以保持样本可比。
- 网关每 0.1 秒轮询一次，会带来一点固有的等待和浪费。
- 控制路径的延迟在虚拟时间下测不出来，需要另做真实时间的压测。
- Aether 没有会话 ID，链只能按 Key 的请求流还原。
- abyss 只在回复完成时记录时间，所以请求的开始时间是用时延拟合反推的。
- 各项锚点、权重和 SLO 档位都是设计选择，需要在组内确认后再固定。

## 5. 约束

- 虚拟循环上只能运行进程内协程。线程通过真实 I/O 完成，虚拟时间会越过它们。
- 网关目前每 0.1 秒轮询一次，并多处全量扫描请求。规模扩大时运行时间主要受这两点影响。
- 标记为 `xfail(strict=True)` 的测试记录已确认的 WP5 缺陷。修复后测试会转为 XPASS 并报错，此时移除标记。
