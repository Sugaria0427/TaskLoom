# Agent 两层资源竞争：补充调研与课设方向重评

检索与复核日期：2026-09-27。本文补充并修正 [原调研报告](agent_scheduling_research.md)，用于选题讨论，不代表已经确定项目或开始实现。

## 1. 结论与研究边界

**平台推理资源竞争有充分证据；个人电脑上的工具资源竞争有条件成立，但不能从前者直接推出后者。** 新检索到的 PeakBench 为“有限资源下的多工具并行”提供了更直接的实验依据，同时也表明资源感知工具调度已经有人研究。

以“个人电脑上的 harness 调用云端模型”为前提，原来的两层划分基本正确，但选题时还应区分一个位于两者之间的控制边界：客户端可以安排自己何时请求 API，却不能安排服务商内部的 GPU。

| 研究对象 | 共享资源与竞争者 | 项目可控制的部分 | 当前判断 |
|---|---|---|---|
| 服务端模型推理 | 多个客户/工作流共享推理容量、显存与批处理机会 | 自建推理服务或仿真时可控；普通 API 客户端不可控 | 问题真实、研究成熟；实现门槛高，和现有 AI 算力调度课题需核对边界 |
| 客户端模型请求 | 同一账号、组织或端点限额下的多个请求共享配额；具体限额范围由服务决定 | 发送顺序、准入、退避、重试预算 | 不需多人共用电脑，但基本方案已有 HiveMind 等工作 |
| 主机工具执行 | 一个或多个工作流，以及其他应用，共享本地 CPU、内存和 I/O | 就绪工具的启动顺序、并发度、资源预算和进程生命周期 | 适合 OS 课设；应限定到确有重工具或并行压力的工作流 |

上述是资源与控制权的分类，不是声称所有用户同时遭遇这三种瓶颈。若模型也在本机部署，推理与工具可能争用同一台机器；那是不同部署假设，应另行建模。

## 2. 既有证据复核：哪些结论成立，哪些需要收回

### 2.1 平台调度是真问题，但普通客户端无法直接解决

Agentix（NSDI 2026）优化 LLM 调用和 Agent 程序层的队首阻塞，把程序上下文带入推理调度。JITServe（NSDI 2026）处理不同响应目标与不精确请求信息。两者官方页面本次重新访问成功。[S1–S2]

它们证明“工作流关系影响推理端的完成时间”，不能证明“本地加工具队列就能获得相同收益”。Agentix 的工具执行被作为外部阶段处理，其评估使用多 GPU 服务器。Architectural Implications 的主机角色干扰证据来自 Azure 及服务器控制实验，包括 96 核 EPYC 与 8 张 A100；这里的主机不能未经说明就等同于个人 PC。[S3]

若选平台方向，必须承认需要自建/模拟服务端，并把吞吐、响应目标和工作流完成时间作为指标；无法以调用商业 API 的客户端实验验证 GPU 内部调度收益。仅“Agent 调度”同名不能证明与同学撞题，但调度对象若仍是 GPU/推理作业，重合风险更高。

### 2.2 原报告遗漏了不支持“普遍本地拥塞”的证据

Agentic Coding in the Wild 的正文给出了三个重要限定。[S4]

- **耗时结构：**对同时含 LLM 和工具调用的单轮会话，LLM 时间占比中位数为 87.7%。论文明确判断，多数编码会话受 LLM 时间主导；工具优化主要惠及长外部操作占主导的少部分流程。不同汇总口径、会话类型和重叠时间不能直接相减。
- **并行结构：**93% 的工具 batch 只有一个调用，7% 并行；并行 batch 的中位宽度为 2，87.5% 不超过 3。该数据不能证明典型单会话经常启动大量本地重进程；多个会话的累计竞争仍需另测。
- **失败含义：**9.1% 指 deep-loop-with-failures 这一聚类类别，约 36 次 LLM 调用为中位数的 4 倍。失败包括错误假设、构建错误、缺失依赖等，并非全部是可以用检查点消除的系统重试。

因此收回“普通个人电脑上普遍存在工具拥塞”“约 9% 任务的四倍重试开销可以用恢复机制消除”等推断。长工具时间也可能来自实际工作量、外部服务等待或代码错误，不能只凭时长归因为调度差。

### 2.3 调度、工具并发和检查点已经存在

AIOS 已使用 FIFO/RR，工具管理器按工具实例并发上限检查冲突，并跳过暂时不能执行的调用。其 arXiv 记录标注 COLM 2025；本次核读了正文，独立 OpenReview 查询被限流。实验默认最多 250 个并发 Agent，使用单张 A5000 上的本地模型，不能把其加速数字迁移到“少量本地会话＋云端模型”。[S5]

LLMCompiler（ICML 2024，已核对 PMLR 正式页面）已经进行依赖感知的并行函数调用。LangGraph 官方文档已经提供检查点、故障恢复与 pending writes：同一步中其他节点失败时，恢复可保留成功节点的结果；还提供不同持久化模式。[S6–S7]

这些材料否定了“Agent 没有工具调度”“工具失败通常从头重跑”“首次加入检查点”的泛化叙述。它们并不意味着所有 harness 都配置了相同能力，也不等于任意工具进程或外部副作用都能自动恢复。

## 3. 新证据如何改变选题判断

### 3.1 PeakBench：最直接的工具资源调度证据

PeakBench: Benchmarking Resource-Aware Tool Invocation in LLM Agents，2026-08-25 arXiv 预印本，作者 Zhi-Kai Chen 等。[S8]

其核心区分是：**依赖允许并行，不等于当前资源允许同时执行。** 它把依赖规划与物理调度拆成两个评价维度，对工具执行采集资源数据，再比较在容量约束下的调度。

在 DeepSeek-V4-Flash 的表 9 消融实验中，提供 CPU 与内存信息后，可行调度比例由 74.9% 变为 87.6%，资源违反指标下降 48.5%。这说明资源信息可能有用；它不是本课设的预期收益，也不是普通 PC 实测的卡顿改善率。

使用这项证据必须保留四个边界：

1. **评估方式：**工具画像来自沙箱测量，但调度比较在模拟器中回放；small/medium/large 容量由负载分位数构造，不是三种实物 PC。
2. **先验信息：**调度维度直接提供验证后的依赖结构；真实 Agent 会逐步发现后续步骤，不能直接假设已知完整 DAG。
3. **强基线：**表 3 已有按时长、关键路径或归一化资源压力排序的资源约束列表调度。Best Rule 的完成时间为 9.13 秒、CVA 为 2.925；RASC 分别为 9.11 秒、2.938。不能宣称 LLM 调度明显击败经典算法。论文还已测试资源画像噪声，不能将“考虑估计误差”直接声称首次。
4. **复现条件：**论文所列 GitHub 仓库 `Czzzk/Staggering-the-Peaks` 本次网页和 API 均返回 404。全文可读，但尚未取得其公开代码/数据，不应承诺直接复现实验。

此外，CVA 是模拟的容量违反面积，不是实测 OOM 次数或用户卡顿次数。CPU 超需求通常首先表现为排队与变慢，内存不足可能发生换页或分配失败，不能把所有容量违反统一称为“系统崩溃”。

### 3.2 HiveMind：API 调度可做，但基础方案并不新

HiveMind: OS-Inspired Scheduling for Concurrent LLM Agent Workloads，2026-04-18 arXiv 预印本。[S9]

它是透明 HTTP 代理，协调多个 Agent 的 API 准入、速率限制、退避、重试预算与优先级。一个人的多个任务即可共享端点限额，不要求多人共用一台 PC。

但论文主要评估是 mock API 与 mock Agent，真实服务验证范围有限；很大的失败率改善不能当作商业平台常态。其消融显示，透明重试比单纯准入控制更关键。未来课设若比较 API 调度，基线必须包含合理的指数退避、随机抖动、限额遵守和重试预算，不能把无重试的脆弱客户端作为唯一对照。

论文还明确没有协调文件系统操作和工具调用。因此 API 配额与本地工具是不同资源边界。它们可以结合，但结合本身不自动构成创新。客户端也不能借队列增加服务商授予的配额。

### 3.3 其他前沿工作进一步压缩了宽泛创新空间

Decoupling Readiness from Release（2026-09 预印本）已经研究就绪模型调用的释放顺序和在途工作预算；其方法使用推理系统信息，不能直接等同于黑盒商业 API 的速率限制管理。本次读取了全文关键方法与评估段落。[S10]

SpecBox 与 AgentZip 的摘要分别涉及沙箱预热/内存权衡和高扇出沙箱内存压缩；AgentServe 的摘要涉及消费级 GPU 上的本地推理调度。本次只将这些作为研究边界线索，未深读/复现，不据此报告项目收益，也不将其视为个人 PC 工具拥塞的直接证据。摘要快照保存在材料目录。

## 4. 对课设的建议：保留方向，收窄可验证问题

### 4.1 候选问题，而非已定项目

**优先验证“个人设备上资源受限的 Agent 工具工作流执行”，暂不承诺面向所有日常 Agent 会话的通用加速。** 不需要假设多人共享平台；一个重工具工作流含有多个可并行分支，或一人同时运行几个工作流，都可构成实验场景。但负载必须来自明确实际任务，不能为了制造冲突随意堆进程。

可以先选资料处理这一种负载：检索完成后，对多份独立材料执行本地解析/OCR，再汇总。它只是候选场景，不是本次已经证实的常见瓶颈。若选择代码构建/测试，也应固定为另一组独立负载，并测量任务已有的内部并行，避免重复并发造成的人为偏差。

候选系统负责在工具启动前决定“现在是否允许进入执行、允许哪些已就绪步骤进入”，利用任务依赖、资源画像、实时可用资源和等待时间。操作系统仍负责底层进程调度。系统可以管理自己启动的 worker/子进程树，并对明确可重放的步骤做持久化恢复；不能仅靠普通日志恢复任意执行中的程序状态。

这种上层控制的理由是：OS 内核通常不知道某个进程属于哪个 Agent 目标、它完成后会解锁什么步骤、任务是否已被取消。反过来，已有 OS 的资源控制能力应作为实现基础和基线，而不是假设操作系统完全不会调度。

### 4.2 OS 机制如何对应实际问题

| 问题类别 | 机制与算法用途 | 必须说明的边界 |
|---|---|---|
| 工具等待与过量启动 | 依赖就绪队列、信号量、资源约束列表调度、老化 | 单个工具本身超过容量时，仅调整顺序不能使其可行 |
| 并发状态与输出一致性 | IPC、互斥/读写锁、原子结果提交 | 文件锁不解决两次语义修改之间的逻辑冲突 |
| 取消与进程故障 | 守护进程、子进程树管理、超时通知、持久化步骤状态 | 必须实测故障恢复；不得把正常构建失败误判为 worker 崩溃 |
| 性能观测与仿真 | 分阶段计时、资源采样、统一事件回放 | 模型等待、工具排队、工具执行要分开，避免归因错误 |

### 4.3 有意义的对比实验

先固定任务语义、依赖与结果验收，再比较以下四组；当前没有实现或实测结果。

| 组别 | 策略 | 对照目的 |
|---|---|---|
| 串行 | 依赖合法的顺序执行 | 提供保守参照，但不能作为唯一基线 |
| 固定并发 | 调参后的合理并发上限，保留必要依赖/错误处理 | 检查复杂调度是否真的胜过简单方案 |
| 成熟资源策略 | 资源约束列表调度，按关键路径/时长等排序 | 避免只战胜弱 FIFO；与 PeakBench 所含规则对照 |
| 候选在线策略 | 仅使用当时可见依赖，结合可用资源变化与估计误差调整准入 | 验证动态场景中的增量收益，额外机制需消融 |

恢复单独做消融：在相同调度和任务下比较已有检查点方案与候选恢复机制，不把“有重试”相对“无重试”的改善归功于新调度。加入调度器/守护进程、worker 故障以及取消后的进程清理，记录恢复代价。

宏观结果按四类展示：

1. **完成体验：**端到端 P50/P95、指定时限内成功完成率；若声称改善桌面流畅度，需单独定义并测量前台探针响应。
2. **容量压力：**峰值内存、换页/内存压力、过载持续时间；模拟容量违反与真实失败分别报告。
3. **可靠性：**故障恢复时间、可确认的重复执行量、取消后残留进程；区分逻辑失败、基础设施失败和用户取消。
4. **成本与约束：**CPU 时间、调度/采样/检查点开销、长任务等待代价、结果质量。不能仅用调用次数减少代替质量不变。

先在真实可控任务上测量并发 1/2/4 等条件，确认瓶颈和测量扰动，再用测得的资源与时长分布校准 30 天仿真。所有策略用同一输入和外部扰动，多随机种子报告波动。时间型故障可能因调度顺序而命中不同步骤，事件注入语义必须明确，不能只说“种子相同”便认为完全公平。

### 4.4 何时值得继续，何时应调整选题

支持继续的结果应是：目标任务确实存在可调度的工具并行，合理固定并发下仍有可观等待/资源压力，并且增量策略能在同质量下改善某一主要指标，而代价可接受。

若主要时间始终在远端模型、单个工具没有可分解并行、或简单固定并发已足够，则不能靠夸大故障率制造收益。此时应改为更具体的工具负载，或者重新考虑客户端 API 配额协调，但后者同样需要对比 HiveMind/成熟限流重试，并重新核验创新。

**当前可诚实主张的是课程级系统贡献：围绕明确负载，验证运行时掌握的依赖与资源信息能否带来增量收益。尚不能主张全新算法，也不能承诺一定得到显著改善。** 原报告“工具执行层适合研究”的判断可以保留，“通用空白、普遍痛点、必然大收益”的暗示应删除。
