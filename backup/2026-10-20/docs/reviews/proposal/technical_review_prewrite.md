# TaskLoom「织序」开题计划书技术审查备忘录

日期：2026-09-29。性质：主文写作前的方法论审查与候选算法规格，不是已实现系统、实验结果或新颖性证明。依据为 `research/agent-orchestrate/reports/07_integrated_agent_workflow_proposal.md` 当前版本及此前已核验的文献边界；本次未联网、未编写产品实现、未执行实验。

**建议将首版收敛为“分层成本公平＋当前步骤多约束准入＋单方向缓慢反馈＋有所有权的恢复”。** 固定模型、推理容量及推理配置，应用层只控制本地工具/子 Agent、客户端请求与自建平台接入。研究重点是完整任务前进与受控资源的一致使用，不涉及 GPU、KV 或批处理。已有 DRR、准入、租约与 fencing 原理均不宣称原创；增量须由受控工作流中的对比与故障实验建立。

## 一、算法组合：具体到能实现，同时明确它不保证什么

### 1.1 分层成本 DRR：公平份额、时限与老化分开负责

首版采用平台用户队列及用户内部根任务队列。认证用户由平台确认，root_task 来自受控运行时；子 Agent 继承根任务，不能靠扇出重新领取公平份额。客户端同样按自己的根任务组织请求。基础优先级由应用策略配置，用户自报 deadline 不能无限提升跨用户份额。

对每个持续有就绪工作的流维护 deficit，访问一轮增加 quantum×weight；选择费用估计不高于可用 deficit 且通过资源准入的步骤，派发后扣减估计服务量。完成后按实际可观测服务量进行差额结算；低估会形成负 deficit，后续用轮次补足，而不是重置账本。API 账目所用服务量可以是明确权重的输入/输出 token 单位；其权重是实验政策，不冒称真实 GPU 时间。

需要在主文中保留四个限制。

1. **长请求必须能攒足额度。** 若 deficit 有上限，它不能低于允许派发的最大单步骤成本；否则长请求永远不可选。可以选择不对活跃流的 deficit 设置过小上限，或为超大请求设计明确的等待/分块/拒绝策略，不能只写“DRR 自然避免饥饿”。未就绪或空队列流的历史信用不应无限累积；语义上的根任务累计服务账目仍保留，避免每次重新就绪都重获优惠。
2. **老化不能创造可行资源。** 一个工具峰值需求大于设备允许容量，或一请求超过 provider 单请求上限，无论等待多久都不可执行，应在入口给出明确不可接纳结果。可行的大任务若总被小任务绕过，需限制绕过次数或暂时为其保留下一次释放的本阶段资源，避免碎片化导致永久等待。
3. **同一公平域内才做期限次序。** 建议用户/根任务份额先约束候选集合，再在可行步骤内按真实 deadline 和等待年龄择优。EDF 不应绕开父级欠账；等待超过阈值时的老化只改变准入顺序，不突破资源上限。持续过载、无限长不可抢占服务及资源永不释放时，不能承诺有限等待上界。
4. **预测误差不能隐去公平代价。** 记录估计与实际服务差、根任务累计服务及长任务等待。对被取消、失败且已经消耗的调用也按合同计账；未获得最终用量的 attempt 留待核对。不能只对成功请求扣费，更不能将未知执行当成零成本。

首版可用滚动中位数或分位数估计端点/工具类别成本，不必训练复杂预测器。已知输入规模与预测输出分开记录，未发生的未来步骤不入就绪队列。完整工作流可能有循环，按实际发生的 step/attempt 展开；不要求预知最终 DAG。

### 1.2 异质资源用向量准入，公平量与物理量不要混为一个分数

准入向量按真实单位计量，例如内存字节、浏览器实例数、可运行工具槽与临时盘字节。候选步骤只有在相关维度均满足、冲突访问也被允许时才启动。CPU 槽是逻辑并发管理，不等于物理强制；实际 CPU/内存/进程数保护由所选 OS 的资源组承担。画像应包含工具内部线程、后代和输出缓冲，而不是只量 launcher。

不能把 token、CPU 秒、内存字节直接相加当作共同公平成本。建议第一版 API 队列采用加权 token 服务单位，本地工具队列采用明确的工具服务单位或独立公平轮转，向量约束分别判断。根任务统一身份使服务记录关联，不要求所有资源折算为同一货币。若后续采用归一化主导份额，需固定容量基准、资源时间口径与策略，并单独与简单方案比较。

画像估计不是内存硬上界。准入可用保守分位数和余量，硬限制作为故障边界；超过限制可能使任务失败，并非证明算法安全完成。即使 CPU 同时需求超估计，OS 调度首先表现为竞争与变慢，不能一律称资源违规或崩溃。

### 1.3 多维 API 合同账本：时间额度、占用槽、总费用分别结算

固定一种真实或明确模拟的 provider 契约，分别实现 RPM、TPM/ITPM/OTPM、并发和根任务总预算。provider 使用滑动窗口还是令牌桶、是否预估输出、缓存 token 如何计数、失败是否计入额度，都属于契约输入；不能用统一算法假装适配所有服务。

时间额度已消耗部分不会因请求完成返还；在途槽在确认实际结束后释放；最坏费用预留按已知实际结果转为已消费并退还未使用部分。已发送后结果未知时，保留对应不确定金额及执行状态。账本至少区分预留、已消费与待核对，展示时不把未结算费用算作省下的钱。

严格硬费用预算需要可强制的成本上界；未知最大计费范围时不能承诺零超支。估计预留可减少保守拒绝，但应展示其风险/拒绝权衡。分层准入检查用户与根任务账目应原子生效；首版优先用单一额度拥有者加 IPC，避免过早引入分布式锁和共识。共享 key 上存在绕过入口的请求时只能标注账本不完整，并据 provider 反馈保守校正。

## 二、跨层协同：只为当前步骤申请资源，不提前锁住整条流水线

### 2.1 防止跨层预占变成闲置与死锁

只在真正派发模型请求前占用其相应配额、费用预留和在途许可；只在工具步骤启动前申请实际工具资源。排在客户端等待的平台请求，不应提前占一个“执行中”平台槽。也不为尚未由模型响应揭示的工具长期占浏览器或 CPU 槽。

父 Agent 等待子任务时释放已不需要的执行许可；仍驻留的内存、浏览器会话和锁不能虚假释放。若父任务持有子任务需要的资源，必须禁止该等待路径、拆分阶段或显式转移所有权，否则逻辑并发上限也能导致死锁。局部准入应原子检查当前所需向量，或按固定申请顺序并具有失败释放；不能持全局锁进行网络调用。

在内存/实例碎片导致大步骤持续不可行时，可以有限 backfill，即先运行不妨碍其预计准入的小步骤，随后进入有期限的排空/保留模式。首版可以采用更简单的“最大绕过次数后保留下一次足够资源”规则。必须披露这种活性保护可能暂时降低利用率；“一直 work-conserving”与大任务等待保障并非自动兼得。

### 2.2 缓压反馈：一套平台接纳反馈，不堆叠多个互相追逐的控制器

建议第一版只由平台发布带版本和有效期的建议在途窗口/接纳 credits，客户端保留本地就绪队列。额度合同上限是硬边界，反馈窗口只是其内的软接纳策略。平台按自己的队列压力、在途数量和允许期限调整；客户端用本地实际资源决定工具启动，仅在已知下一阶段会产生持续积压时抑制相关请求，不能暂停所有模型调用。

反馈采用固定周期、平滑、死区、窗口上下界和每周期最大调整幅度；增加缓慢，下降保守，但不撤销已经实际开始的工作。短时外部模型响应慢不等于自己的额度不足，因此不能用总端到端时延直接同时驱动多个控制器。反馈过期时回到保守且明确的独立策略，保留最低探测/恢复机会，避免双方互等“先给我空闲信号”。

建议将协调增量首先限定为“平台接纳反馈＋已知后继步骤的本地压力摘要”，不增加实时 LLM 调度打分器、复杂预测器或主动扩容。每个消息需要计入频率、字节及处理开销。固定模型推理配置不等于外部服务时间恒定；派发模式带来的外部耗时变化应单独计时，而不称模型计算加速。

### 2.3 任意工具不可抢占，资源租约到期不等于执行结束

本项目不使用时间片暂停远端模型。对工具采用启动前准入，执行后依赖工具的合作取消，或隔离进程树终止；普通暂停仍保留内存和锁，不作为资源释放。

owned resource lease 必须绑定 root/step/attempt、拥有者和代际。租约过期表示拥有者失联/需核对，不证明旧进程、远端请求或外部写操作已停止。守护进程应核实并清理受控后代，确认 quiescent 后归还实际占用；未确认的远端工作进入 UNKNOWN，而非释放一切后启动替身。仅靠 lease TTL 重发可能同时留下旧、新两份执行。

attempt fencing 应覆盖本地结果发布、完成通知、账本结算和删除/清理。旧代际完成事件可以记录以便对账，但不得覆盖新结果或重复释放。fencing 只能约束检查该代际的接收端；不支持幂等/查询状态的外部工具不会因为本地 fencing 自动实现 exactly-once。

UNKNOWN 恢复首选读取可验证结果、按幂等键查询或等待对账。无法判断有副作用操作是否已完成时请求人工处理，不能盲重试。可重放步骤需要输入/数据版本与授权仍有效；检查点复用不得绕过当前权限。原子 rename 解决部分可见性问题；若宣称主机断电恢复还需定义文件及目录持久化顺序，不能把 worker 崩溃测试冒充所有故障保证。

## 三、四个可检验假设：性能、计账与恢复分别归因

| 假设 | 必要对照及输入 | 主指标与失败判据 |
|---|---|---|
| H1：根任务成本公平减少扇出造成的任务份额失衡，且不使长请求失去活性。 | 相同请求集合、资源和重试；对比请求级合理公平与分层成本 DRR，包含长请求、估计误差和不同子任务数。 | 按 root 累计服务、按时合格完成率、长任务最大等待/slowdown。若收益仅来自饿死长任务、丢必要步骤或扩大紧急份额，则不成立。 |
| H2：当前步骤资源向量准入在重工具混合负载下，优于合理固定并发的整体完成表现。 | 使用真实工具、实测画像和内部线程设置；所有组都有同样硬隔离、取消和输出上限。覆盖资源宽松与受限。 | 任务成功/耗时、峰值内存、资源压力持续时间与调度开销。单工具不可行不是排序可修复；若固定并发已同样好，应否定增量。 |
| H3：端—平台信息交换超出两侧独立优化的效果。 | 双方候选策略启用且无协同信息，与相同策略加反馈/本地摘要直接比较；再分别关闭信息项。 | 按时合格任务数、交互 P95、长任务代价及控制开销。若只优于某一侧未优化的组合，不能证明协同增量。 |
| H4：所有权、代际及 UNKNOWN 协议使受控故障后的资源账目与实际执行保持一致。 | 同调度下对比正确配置的常规 cleanup/checkpoint 与候选协议；注入执行前、中、效果已发生未记录、完成/取消竞态及控制器故障。 | 受控残留资源、重复发布/释放、确认回收时间和 UNKNOWN 收敛/人工处理率。外部效果不可知时安全保留 UNKNOWN 是预期行为，不能伪报自动恢复成功。 |

多维合同账本是共同正确性底座：在已定义、完整受控的模拟契约里，每次状态转移均核对各维度预算不变量。严格预算、估计余量两种模式的可用性/超界取舍可作为 H1/H3 的单独因素，不把模式放宽当作调度收益。

### 3.1 协同交互项与直接对照

设 Y 为越大越好的按时合格任务数，Y00 为端/平台基线，Y10 仅端侧优化，Y01 仅平台优化，Y11 为双方优化但关闭协同信息。可报告交互项 I=Y11−Y10−Y01+Y00，用来描述两侧优化是否呈现非加性影响。它不是协同通信贡献，也不是单次观察的显著性结论。

另设 Y11F 为双方优化并交换反馈，直接差值 ΔF=Y11F−Y11 才检验该协同信息的增量。对延迟指标明确方向，不把比例改善机械代入可加关系；P95 的交互项仅作描述，主要用任务级结果与多次配对置信区间。计划书可将此归为“基础 2×2 比较＋一个协同消融组”，不必为满足四行表格而省掉必要组。

### 3.2 因果识别和质量约束

控制回放保持同一工作量以验证调度，小规模真实 Agent 运行验证接入和结果质量，两类结论分开。模型、提示和采样设置尽量固定仍不保证轨迹相同；真实任务必须有独立验收条件，不靠减少调用次数证明质量不降。

所有策略共享合理重试、依赖与可靠性能力；未完成、拒绝、取消分别报告，完成率分母保留全部提交任务。固定窗口内完成者 P95 不能单独用来排名，另报告删失比例并延长观察/分析任务等待。公平服务计量与账户实际费用都需要披露，不能仅显示平均响应时间。

使用独立调参集和多次配对负载，报告种子、信赖区间与失败区间。真实 API 运行交错安排，记录模型版本、合同和环境变化。任务的资源宽松/只 API 紧/只工具紧/双紧四种条件均覆盖，不能只挑有利的过载强度。长时仿真根据实测画像与合约时钟校准，不把单一时长常数、任意失败率和压缩到达冒充一个月真实运行。

## 四、目标值、已有效果与首版验收表述

### 4.1 正确性要求与性能目标是两种不同承诺

正确性可以写成待验收的不变量，例如：“在明确支持的受控工具与故障集合内，不允许同一 attempt 重复释放额度或旧 attempt 覆盖当前结果；被报告为 QUIESCENT 的任务不应存在仍运行的自有后代。”这是将由实验检验的设计要求，不是已经证明实现满足。

性能应写成预先登记的目标/假设。例如：“以独立双优基线为参照，探索在指定混合负载中降低交互尾延迟，同时将长任务损失与控制开销控制在预设容忍范围；未达目标则报告适用边界。”在完成先导测量前，不填看似来自论文的提升比例。

若学校要求数字，可给出**明确标注为暂定工程验收目标**的示例：“在已确认存在竞争的测试集上，争取交互 P95 相对独立双优基线降低至少 10%，同时长任务 slowdown 不恶化超过 10%，并保持相同验收质量；该目标待先导实验确认测量分辨率后冻结。”这里的 10% 是项目方选定的最小有意义目标，不是文献预测或已有效果。应选择少数主指标，不保证上述目标对所有负载成立，不因观察结果不理想而事后调整门槛。

不建议现在规定“取消 1 秒内全部释放”“100% exactly-once”“零误差费用”之类无法覆盖远端与不可合作工具的指标。回收时限应依据具体 OS、终止协议和工具范围预设，UNKNOWN 单独统计；对没有结果质量标签的数据，只能评调度机制，不能宣称合格业务量增加。

### 4.2 首版应完成的最小技术闭环

首版固定一套可修改 Agent loop、自建应用网关、一种 provider 合同及一种本地 OS。实现根/步/attempt 标识、模型和工具队列、分层公平、当前步骤向量准入、合同账本、实际子进程管理及 UNKNOWN 状态；跨层反馈作为可关闭实验因素。

首版不引入 GPU/KV 优化、任意 shell 精确读写集分析、全部 harness 透明接管、分布式全局强一致或对模型任务长短的额外 LLM 分类。必要读写冲突采用已声明资源或保守独占，只有已证明独立的分支并行；单 Agent 推理状态按语义顺序推进。

最终可诚实表述的贡献是：在明确 Agent 工作流、固定推理服务与实际 API 契约下，形成可审计的多层调度/资源所有权协议，量化相对成熟策略的收益和代价。任何“优于现有”“减少多少”“无残留”等完成式表述，都应等待实现和相应证据。
