## 2. 图稿如何对应软件工程模型

本图集包含8张UML图和1张非UML思维导图。各图有明确的建模问题，不把同一幅框图重复冠以不同名称。

| 视图组 | 图稿 | 回答的问题 |
| :--- | :--- | :--- |
| 需求与全貌 | 01 用例图；09 思维导图。 | 谁使用系统、希望完成什么；整个项目的概念如何组织。 |
| 静态结构 | 02 组件图；03 核心领域类图；04 部署图。 | 模块职责与依赖是什么；核心对象如何关联；运行环境和部署位置在哪里。 |
| 执行与恢复 | 05 主执行时序图；06 取消与核对时序图；07 执行尝试状态机。 | 正常工作如何推进；取消如何收敛；单次执行结果怎样变化。 |
| 资源安全 | 08 银行家安全检查活动图。 | 一次资源申请如何经过边界检查、安全试算和原子提交。 |

### 2.1 需求与项目全貌

用例图的主体边界包含个人端和TaskLoom应用平台，外部模型服务与实际工具程序作为非人类参与者。关联线只表示参与某项用例，不要求每个任务都调用工具；未为了展示语法而强行增加`include`或`extend`。

思维导图围绕问题与目标、四层结构、OS方法、验证交付四个分支组织。它用于理解项目，不表达严格的UML执行或所有权语义。

### 2.2 静态结构

组件图表达主要运行期使用依赖；虚线箭头从使用方指向被使用方，反向的结果或事件依赖分别标明。图中只展示主要接口，未把每条日志、心跳和查询路径全部展开。共享上游额度的权威记录位于平台端，本地记录不复制出第二份全局额度。

领域类图是核心业务对象视图，不是完整数据库表结构。实心菱形位于整体一端，表示组合；空心三角指向父类，表示继承；`Step {abstract}`表示抽象类。任务包含逻辑Agent和步骤，步骤包含执行尝试；产物与尝试之间使用有向关联，避免暗示删除尝试即可无条件删除仍被使用的产物。

类图还应满足以下约束：步骤与负责它的Agent属于同一根任务；`parentAgentId`表示父子关系且不得形成祖先循环；`knownPredecessors`只包含当前已知的有效依赖；阶段声明归具体Attempt所有且仅用于工具步骤的受控尝试，满足`0 ≤ Allocation ≤ Max`。这样重试不会让新旧尝试误用同一份阶段占用。这些是模型约束，不表示代码已经实现校验。

部署图中的立体节点表示设备、执行环境或受管执行边界；进程节点承载相应软件职责，文档形节点表示持久文件制品。运行环境间的实线是通信或控制连接，对持久制品的虚线是使用依赖。守护进程位于可整体终止的工具资源组之外。首版采用单平台实例，不引入分布式共识。

### 2.3 执行过程与状态

主时序图限定为最终通过验收的场景，以`loop`表示逐步揭示工作，以`alt`区分模型步骤和工具步骤。同一根任务可能交替经过两条路径，不能把四层误读成所有调用都必须经过的直线流水线。

取消时序图用`par`表示本地与模型请求两条收敛路径可并行推进；`alt`区分未派发、已派发及后续核对结果。L3与L4在这一图中合并为请求路径参与方，“各自账本”是逻辑汇总，未把跨机器的记录画成实际共享数据库。

状态机只描述一次`Attempt`的结果处理，不把整个Task、Step和资源生命周期揉成一个状态变量。`UNKNOWN`可在后续核对后解析；重试创建新的Attempt。结果状态、实际执行状态和结算状态独立记录，所以SUCCEEDED、FAILED或CANCELLED都不能单独作为归还全部资源的依据。

### 2.4 银行家安全检查

活动图以一次检查调用为边界，读取同一资源域快照及版本后完成全部判断。条件判断采用逐维“小于或等于”；试算只改变快照，直到找到完整安全顺序并完成版本核对后才提交真实预留。

`RECHECK`表示状态在计算期间变化，调用方需要以新快照重新检查；不是获得许可。找不到安全序列表示不安全，不能等同已经死锁。上限变更走独立协议，图中没有允许直接修改Max后跳过安全检查的路径。

## 3. 文件格式与编辑

每一种格式有不同用途，建议按编辑对象选择。

| 目录／文件 | 格式与用途 |
| :--- | :--- |
| `svg/`、`png/` | 9张独立SVG及9张长边4096像素的PNG。SVG保留文字与矢量连线；PNG已按300dpi写入元数据，可直接插入报告。 |
| `pdf/`、总PDF | 每图一页的单图PDF，以及带9个书签的汇总PDF。采用A2横／纵向页面保留文字尺寸，打印时可按需要缩放。 |
| `source/` | 9份PlantUML源文件、统一主题；4张静态图另有可编辑draw.io及布局JSON。 |
| [编写工具](../../agent-workspace/scripts/diagrams/)与[内部检查材料](../../agent-workspace/outputs/diagrams/) | 生成脚本与渲染工具按工具目录管理；预览及检查记录按构建目录管理。 |

静态图01—04采用人工确定的布局，其节点名称及字段从PlantUML读取，坐标与路径由`layout_static.py`管理；draw.io文件中的节点、文字和连线均可编辑。直接修改draw.io后，需同步对应PlantUML中的实质关系；不能以未同步的另一份图稿作为新版本依据。

图05—09由PlantUML负责布局。统一标题、说明和输出尺寸由导出脚本添加；draw.io与PlantUML源文件主要保存模型内容，不包含统一出版页眉。SVG使用微软雅黑字体，跨设备分享优先使用已嵌入字体的PDF或PNG。

本地重新生成的顺序为：渲染PlantUML、运行静态布局脚本、导出SVG/PNG与浏览页、渲染PDF、合并PDF并检查。脚本记录了本机Java、Node和Python路径，更换环境时需调整；PlantUML版本与来源记录在`../../agent-workspace/scripts/diagrams/vendor/provenance.json`。
