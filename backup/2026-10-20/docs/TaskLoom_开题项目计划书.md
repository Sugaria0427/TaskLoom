# TaskLoom「织序」项目计划书

## 面向 Agent 多任务执行的端与平台协同调度及资源管理系统

操作系统原理课程设计 · 开题版本 v1.0 · 2026年9月29日

本计划书提出 TaskLoom「织序」的研究问题、系统设计、算法路线、实验方法与实施安排。项目当前处于开题阶段，文中的系统能力和验收指标均为拟实现内容，性能目标不代表已有实验结果。项目组成员、指导教师及实际设备配置在正式提交时据实补充。

### 摘要

Agent 正从单次问答工具转向能够持续调用模型、执行工具并派生子任务的工作流运行系统。一项用户任务的完成，需要在模型请求、本地计算、外部工具和结果提交之间多次切换；多项任务并行时，有限的 API 额度、执行槽位、内存与共享状态形成相互关联的约束。已有模型网关、Agent 框架和工作流系统已提供限流、并发控制、优先级与持久化等能力，但不同控制位置对任务关系、资源占用与终止状态的认识仍可能不一致，造成可避免的排队、过度保留、结果未交付以及失败后的资源残留。

TaskLoom「织序」拟在固定模型、推理容量与推理配置的条件下，构建应用层的端与平台协同调度系统。端侧统一管理本地工具、子 Agent 和待发送模型请求，平台接入层面向多用户进行准入与派发。系统以根任务、步骤和执行尝试为共同身份，采用分层成本公平调度、资源向量准入、多维额度账本和带时效的拥塞反馈，并以进程通信、同步互斥、持久状态和真实守护进程建立一致的执行与回收协议。项目将通过真实工具画像、受控请求回放、小规模真实 Agent 运行与经校准的30天仿真，评价按时合格完成率、交互尾延迟、长任务公平、预算使用和故障恢复。预期贡献是在明确控制边界内，将成熟 OS 方法组织成可解释、可核验的任务级调度机制，检验协同信息相对于两侧独立优化的增量价值。

**关键词：**Agent 工作流；应用层调度；多维资源管理；公平性；故障恢复

## 一 立项依据与研究目标

### 1.1 从请求处理转向完整任务交付

当用户让 Agent 分析一批文档、修改并测试代码、检索资料或整理数据时，系统执行的通常不是一个孤立的模型调用。Agent 需要依据当前结果继续决策，调用本地程序或外部服务，有时还会创建子 Agent 并等待其返回。一个任务可以拥有许多较短的模型请求，也可以因一个耗时工具而长期停留在中间阶段。因此，单次请求处理得快、工具池始终繁忙或 token 吞吐较高，都不必然意味着用户更快取得合格结果。

TraceLab 对43名开发者的4,265次编码 Agent 会话进行了分析，包含357,161个模型轮次和432,510次工具调用。研究发现工具调用存在明显长尾：超过一分钟的调用约占调用数的4%，却占工具总时间约85%[2]。这些数字说明任务阶段具有异质性，不证明85%的时间可以被优化掉，也不等同于 CPU 使用时间。另一项生产编码追踪指出，在其样本中排除用户轮次间空闲后，模型推理耗时总体高于工具执行耗时，93%的工具批次只有一次调用[3]。两者的样本、统计单位和长尾权重不同，共同提示本项目必须测量具体工作负载，避免预设所有个人设备都存在工具拥塞。

拟研究的现实场景是：每位用户在自己的工作站上同时提交交互问答、资料处理和代码验证等任务，任务在本地调用受控工具，又通过共同应用入口访问固定模型服务。用户之间不共享同一台个人电脑；平台共享的是模型请求接入与服务机会。端侧知道自己的任务意图与本地状态，平台知道整体到达压力与用户份额。TaskLoom 连接这些信息，使资源分配围绕完整任务推进展开。

「织序」的命名对应这一目标：将分散在模型、工具、子任务和平台队列中的执行片段组织成有依赖、有预算、有终态的工作过程。项目价值将落实为可核验的用户结果：重要任务少等待，后台任务能持续推进，有限额度得到有用产出，异常任务结束后不长期占用他人的执行机会。

### 1.2 已有工作及其留下的研究边界

已有研究和工程系统已覆盖大量基础能力。AIOS 实现了 Agent 调度、工具管理与并发控制；其效率实验的本地模型、高并发条件不能直接外推到少量本地任务调用云端模型的场景[4]。LLMCompiler 研究了依赖感知的并行函数调用[5]。PeakBench 将依赖正确性与物理资源可行性分开评估，以工具实测画像和模拟容量说明“能够并行”不等于“应该同时执行”，其强规则基线与所提出方法的部分指标接近[6]。这些工作为本项目提供方法依据，也排除了“首次给 Agent 加队列或并发控制”的新颖性表述。

在模型请求入口，HiveMind 已采用准入、配额跟踪、优先级、估计 token 成本和依赖关系，其主要评估使用模拟 API，较大成功率改善很大程度与透明重试有关[7]。LangGraph 已有持久检查点和成功节点 pending writes，Temporal 已有任务优先级、公平与下游速率控制[8-9]。LiteLLM 提供动态额度分配和多种预算管理路径，但不同入口的在途计数、预留与结算语义需要分别核验[10-11]。因此，TaskLoom 的比较对象必须是功能正确、参数合理的现成控制组合。

| 研究与工程方向 | 已有能力 | 本项目保留的问题 |
|---|---|---|
| Agent 与工具编排[4-6] | 依赖规划、工具并发、资源约束调度。 | 动态揭示步骤、真实本地压力及多根任务目标如何一致地参与准入。 |
| API 网关与额度管理[7,10-11] | 限流、重试、优先级、预算预留与结算。 | 根任务扇出公平、额度恢复语义与跨阶段推进是否仍有可避免损失。 |
| 持久工作流[8-9] | 检查点、恢复、任务优先和公平。 | 逻辑状态、实际工具资源与外部结果不确定性如何同步收敛。 |
| 运行时接口与 OS 控件[14-18] | 模型/工具包装、进程资源保护、标准重试与生命周期机制。 | 接入后能否形成清晰不变量，且额外治理成本低于所得收益。 |

本项目不修改模型权重、不优化推理算法，也不研究 GPU 分配、KV cache、prefill/decode 或内部批处理。模型及推理配置作为固定执行条件。平台部分指我们能够控制的应用 API 接入层：接纳请求、管理队列、选择派发顺序并反馈压力。通过自建网关调用固定服务，可以验证应用平台调度，但不能据此宣称已经改变商业服务商的内部策略。

### 1.3 痛点归因与可检验假设

公开案例支持以下具体缺口，但不支持“所有 harness 都缺少调度器”的概括。Codex 某关闭路径的 MCP 清理报告提供了复现场景，同时保留其他调用路径清理成功的对照[20]；DeepSeek 社区讨论描述了失败消息留下所有权依赖，导致工作完成却不能结算的情形[19]。这些资料适合定义生命周期不变量，不能当作本项目已经独立复现。补充报告中提到的 Claude workflow 限流与遥测收尾问题，也必须区分模型请求端点、遥测端点及具体版本[21-24]。

| 问题链 | 可观察损失 | 研究假设与边界 |
|---|---|---|
| 根任务被拆成多个子 Agent，各处按独立请求计机会。 | 大扇出任务可能获得不成比例的服务，紧急任务在多队列中等待。 | H1：根任务分组与成本公平可改善完整任务服务分配；必须同时检查长任务活性。 |
| 工具并发只按数量限制，需求与内部并行不同。 | 重工具同时进入后引发内存压力、执行变慢或资源碎片。 | H2：当前步骤资源向量准入优于调参后的固定并发；不预设轻负载有收益。 |
| 客户端知道本地阶段，平台知道整体压力，信息未共同使用。 | 过早派发积压后续工作，过度限流又造成资源闲置。 | H3：双侧优化加信息交换优于双侧优化但独立运行；若无增量，应收窄协同主张。 |
| 状态完成、额度结算和实际执行结束不一致。 | 挂起占槽、重复发布、取消后残留或已有成果未被交付。 | H4：有所有权和代际的恢复协议可减少受控故障后的不一致；未知外部效果不得伪报成功恢复。 |

这些假设分别对应性能、公平、协调和可靠性，不能将修复某个资源泄漏后的改善统称为调度算法加速。研究将保留已修复问题、可配置解决问题和无收益场景作为反例。缺少完全相同边界的现成系统，也不等于已经证明学术空白。

### 1.4 目标、范围与课程适配

项目总目标是在相同模型服务、硬件总量、费用或额度与质量标准下，提高规定时间内按时合格完成的任务比例，同时控制长任务受损和管理开销。任务完成质量由独立的结果验收规则判定，不能通过少执行必要步骤、换用不同能力模型或放宽结果要求获得优势。

首版支持一个可修改 Agent 运行时、一个自建应用网关、一种明确的 API 合同和有限的本地工具类型。工具范围优先选取可验证结果的文档解析、结构化数据计算与代码测试。任意 shell 精确读写集分析、全部商业 harness 的透明接管、多地域容灾与不可查询外部副作用的自动恢复，列为范围外或后续扩展。

课程课件要求可运行系统、真实守护机制、OS 原理应用及性能和可靠性评价，并安排第6周小组展示、第8周个人答辩[1]。TaskLoom 的进程通信、同步互斥、文件和日志管理、调度以及故障回收均有实际对象。系统通过一条任务的时间线解释其为何等待、占用何种资源、何时释放及最终是否合格，让课程知识对应到具体结果，而非停留在算法名称展示。

## 二 系统模型与总体架构

### 2.1 对象、资源与状态模型

系统以根任务 Task 表示用户目标，以 Agent 表示具有上下文和后代关系的逻辑执行者，以 Step 表示一次已经揭示的模型或工具操作，以 Attempt 表示某步骤的一次具体执行。一个 Agent 不要求对应一个 OS 进程；真正执行工具的 worker 可以独立进程化。一次模型轮次结束也不代表 Agent 的驻留状态、后代或全部资源都已结束。

每个步骤记录 root_task_id、agent_id、step_id、attempt_id、已知前驱、资源声明、结果位置和当前状态。动态工作流可能出现反复规划和重试，系统按实际发生的步骤展开事件图，不要求预知最终 DAG。就绪的必要条件是已知前驱完成且当前授权仍有效；未产生的未来步骤不参与真实调度，最多作为标明置信度的预测。

资源分为四类，分别采用不同的释放规则。

| 资源类别 | 典型对象 | 记账与释放语义 |
|---|---|---|
| 时间速率预算 | RPM、TPM 或分开的输入/输出 token 限额。 | 按提供商窗口或补充规则恢复，已消耗部分不能在请求结束时返还。 |
| 占用型容量 | 在途请求、工具槽、浏览器实例、内存与临时空间。 | 在实际执行或驻留占用结束后释放；逻辑等待不自动释放真实内存。 |
| 消耗型总预算 | 用户或根任务的 token、费用与总重试预算。 | 消耗后累计，预留转实际用量并核销差额，结果未知部分单列。 |
| 互斥与所有权 | 文件写权限、工作区、结果发布权和 attempt 代际。 | 在受控临界区或生命周期内持有；旧拥有者不得覆盖新代际结果。 |

工具准入使用向量而非一个混合分数。设本机容量为 R，本阶段已占用量为 A，候选步骤的带余量需求为 d，则只在各维度均满足 A + d ≤ R、且资源访问不冲突时启动。内存字节、浏览器实例和临时盘字节分别判断，不把 token、CPU秒和内存直接相加。CPU槽是逻辑并发许可，物理保护由 OS 资源组承担。画像超出容量的单个工具必须明确拒绝或调整实现，老化不能使其自然变得可行。

状态采用分组设计，避免把“暂时没输出”当作正在计算或已经失败。

| 状态组 | 状态示例 | 可执行动作 |
|---|---|---|
| 尚未就绪与就绪 | CREATED、WAIT_DEPENDENCY、READY。 | 维护依赖，只对READY步骤做准入。 |
| 条件等待 | WAIT_QUOTA、WAIT_TOOL、WAIT_APPROVAL。 | 等待明确事件，释放不再占用的执行许可，保留真实驻留资源。 |
| 在途与终止中 | RUNNING、CANCEL_REQUESTED、RECONCILING。 | 跟踪实际执行，传播取消，对账并确认收敛。 |
| 结果终态 | SUCCEEDED、FAILED、CANCELLED、UNKNOWN；另有QUIESCENT标志。 | 成功需通过结果验收；UNKNOWN需要查询/人工处理；QUIESCENT仅在自有工作已停止后置位。 |

终态和静止状态是两个不同事实。工具可以已经产生结果但仍有收尾进程，任务也可以取消但远端费用尚未确定。TaskLoom 不使用一个 finished 布尔值替代全部资源事实。

### 2.2 总体组织结构与进程职责

系统由四个职责组构成。端侧和平台侧分别拥有自己的权威账本，通过结构化消息交换必要信息；首版避免引入跨主机分布式锁和共识。

| 职责组 | 主要组件 | 实际职责及OS落点 |
|---|---|---|
| 端侧任务管理 | 工作流协调器、根任务目录、模型/工具就绪队列。 | 管理依赖、子任务、期限与本地预算；用异步事件推进任务。 |
| 平台接入管理 | 认证与合同适配、用户/根任务队列、派发器。 | 原子额度准入、公平服务、过载接纳和有期限反馈。 |
| 受控执行 | 工具worker池、模型适配器、产物存储。 | 执行已获许可的步骤，采集资源与结果，管理进程树和文件访问。 |
| 保障与观测 | 监督守护进程、持久日志、状态对账与可视化。 | 检测组件失联、恢复账本、回收受控资源，并展示任务级因果时间线。 |

![图1 TaskLoom总体架构](../agent-workspace/assets/taskloom/concepts/taskloom_architecture.png)

图1中的固定模型服务保留原有推理能力；实线表示工作或结果路径，反馈信息只影响应用层接纳和派发。

端侧协调器与工具 worker 采用独立进程，通过 Unix domain socket 传递类型化消息；大输出不直接塞入消息队列，而通过受限产物文件及摘要传递。平台服务使用HTTP或流式协议接纳客户端请求。初版不依赖共享内存传输大对象，以降低一致性负担；如分析证明统计传输成为瓶颈，可再为只读快照引入版本化共享内存。

SQLite WAL用于步骤状态、执行尝试、额度预留、结果索引和待发送事件。每个本地账本采用单一写入拥有者，短事务确保状态变更和待发布事件一起提交。网络调用和工具执行发生在事务之外。守护进程与被管理 worker 分离，保留独立存活能力与控制资源；监测对象失联后先核对实际进程和结果，再决定恢复。

首版主要验证环境拟为Linux或WSL2中的Linux环境，以便使用进程组、信号和cgroup v2。Windows Job Objects作为可选适配方向，不承诺首版跨平台行为完全一致[29]。开发与运行环境的具体版本、内存和CPU在先导阶段记录并冻结。

### 2.3 模型请求信息与端平台协议

无状态模型API通常由调用方提供选定历史与新输入，但不保证包含全部历史；也有接口通过会话对象或前序响应标识保存关系[12-13]。不论哪种方式，会话信息都不会自动给出用户目标的截止时间、本地工具需求和完整父子任务树。因此，平台基础调度使用认证身份、请求规模、等待和历史用量，任务级协同则使用额外的最小元数据。

| 元数据组 | 主要字段 | 真实性和使用规则 |
|---|---|---|
| 身份与关系 | tenant、root_task、agent、step、attempt、request_id。 | 租户由平台认证；子Agent沿根任务继承份额；request_id用于本系统去重，不冒充第三方幂等保证。 |
| 服务目标 | 交互/后台类别、相对剩余时限、结果是否仍需要。 | 优先级受平台合约和用户份额约束；用户不能通过自报紧急绕过公平。 |
| 成本与阶段 | 输入规模、输出上限、估计输出及置信度、已知后继资源类别。 | 已知值与预测分开；未知后继标unknown，平台按实际用量修正。 |
| 压力与控制 | 本地资源摘要、队列年龄、取消代际；平台建议在途窗口、有效期和重试提示。 | 消息带版本和时效；过期反馈回退到保守独立策略，取消须与完成竞态对账。 |

元数据由运行时从实际任务关系中产生，而不是要求模型在prompt中自由声称。平台不需要读取完整本地文件或工具输出才能排队；完整内容保留给模型服务，调度侧优先使用必要摘要。若商业API不支持这些字段，网关在旁路任务记录中维护它们，再转发原有模型请求。只有受控网关使用这套调度信息，不假设上游服务商自动采用。

请求生命周期设计为“登记就绪、接纳排队、取得执行许可、派发、接收结果、结算与提交”。排队令牌不同于执行槽，网关持久接纳也不代表模型调用已经发生。客户端取消尚未派发请求可直接从队列移除；已经派发则传播取消并等待合同允许的确认，未知效果进入UNKNOWN。平台拒绝或反馈拥塞时返回明确原因，避免把本地容量、临时速率限制、总预算耗尽和外部故障统称为429。

### 2.4 典型任务的执行与界面呈现

以“同时整理资料、运行代码测试和进行紧急问答”为例，资料任务的首轮模型调用生成若干解析工作，测试任务进入本地工具队列，问答产生另一个模型请求。协调器只调度已就绪步骤；不同文档的只读解析可以并行，同一工作区的修改和测试按声明依赖串行。后续模型请求在对应工具结果就绪后产生。

当本地重工具队列积压，协调器限制会继续制造同类已知工作的新派发，仍允许不依赖该资源的请求推进。平台在用户公平份额内安排请求，接近截止时间的请求获得有限的次级优先。模型返回子任务需求时，子Agent继承根任务身份和预算，不能重新获得整份用户额度。

若某工具超时，系统进入取消和核对流程：先请求合作退出，再根据执行器合同对受控后代升级终止。步骤结果和实际资源静止分别记录。已经成功的步骤不会因不相关worker崩溃全部重做；不确定的外部写操作不自动重放。

可视化提供任务画布、资源/额度面板、事件时间线和策略对照四个视图。任务节点应显示等待原因与下一次可唤醒条件，资源面板同时展示预留、实际占用和未知状态；实验视图对比同一任务集合的完成与代价。演示重点是“为何等待、何时推进、异常后如何收敛”，不能以动画取代实际守护和资源检测。

## 三 核心算法与OS机制设计

### 3.1 分层成本公平与期限感知调度

平台采用用户级、用户内部根任务级的分层队列。基础公平策略借鉴Deficit Round Robin（DRR）[25]，以明确的可观测服务单位安排机会。对于同一模型和合同域，可定义估计请求成本为“输入token权重×输入规模＋输出token权重×预测输出”，这些权重表示调度政策或合同成本，不冒充GPU运行时间。工具队列使用自身服务单位或独立轮转，避免把异质物理量混成一个未经解释的分数。

每个持续有就绪工作的队列维护deficit。轮转时按基础quantum与权重增加信用，只有候选成本不超过信用且通过资源准入时才派发，先扣估计量，完成后按实际用量补扣或退回差额。低估形成欠账，由后续轮次逐渐偿还，不能在每次子任务启动时重置。根任务暂时因工具等待而没有模型请求时，不无限囤积短期信用，但其累计已获服务记录保持，防止重新就绪后反复享受“新任务优惠”。

算法需要明确保护长请求。若设置deficit上限，该上限必须容纳最大允许单步骤成本；本来超过provider单请求上限或设备容量的工作应明确不可接纳，不能靠等待修复。对于合法但反复被小请求绕过的工具步骤，设置最大绕过次数或进入有期限的排空/预留下一次释放容量的模式。该活性保护可能暂时降低利用率，必须在实验中披露。

在父级公平份额允许的候选集合内，再依据真实截止时间与等待老化调整顺序。EDF提供期限排序思想，但经典最优性条件不能直接迁移到未知耗时、不可抢占的Agent请求[26]。TaskLoom 不用全局最高优先级覆盖一切，而限制交互类服务份额和突发额度，允许空闲份额被后台借用，在交互工作到达时收回尚未派发的机会。已经执行中的请求不被假定可以无损中断。

![图2 一次调度决策的约束顺序](../agent-workspace/assets/taskloom/concepts/taskloom_dispatch.png)

图2体现决策顺序：依赖与授权先确定“能不能做”，资源和额度决定“现在能不能做”，公平份额决定“轮到谁”，时限和老化在该范围内决定“先做哪一步”。候选筛选只读取资源快照，真正派发前必须在资源拥有者的短事务中重新核验并原子预留，避免多个候选依据同一份空闲量同时进入。不使用不可比较的权重把正确性条件与性能偏好直接相加。

持续过载、外部服务无限挂起或某资源永久不释放时，无法保证所有任务有限等待。系统必须用有界队列、接纳控制和明确的拒绝原因暴露不可满足条件。所谓防饥饿，仅在任务本身可行、必要资源最终释放且负载条件允许的范围内讨论，并通过长任务等待分布验证。

### 3.2 多维额度账本与阶段资源准入

模型额度采用provider合同适配器表示，至少区分请求速率、token速率、在途并发和总费用预算。不同接口对输入、输出、缓存token及失败请求的处理可能不同[10-11,27-28]。首版固定一种支持的真实或模拟合同，将计数窗口、补充规则和取消语义写入配置及实验记录，不声称一个令牌桶即可精确覆盖全部服务。

总预算采用“可用、预留、已消费、待核对”四类账目。未派发请求可撤回其预留；已派发请求按实际用量结算，结果未知时保留待核对项。严格费用上限依赖可强制的单次成本上界；若外部服务无法提供这样的边界，就不能同时承诺零超支与任意并发。估计预留加安全余量作为可选实验模式，必须与严格预留比较超额、拒绝和闲置，不将风险放宽伪装成算法提升[11]。

同一provider共享额度只能有一个权威分配者，首版由网关统一记账，所有纳入承诺范围的请求必须经过该入口。端侧维护自己的任务总预算及建议发送窗口，不另行生成一份同样的全局额度。端侧的本地预留与网关的合同预留用请求标识关联，但代表不同约束；若用户还从其他入口使用同一账号，隐藏用量只能靠上游响应更新估计，此时不能承诺精确全局分配。直连单机模式则由本地适配器独占该合同账本。

本地准入使用工具资源向量，画像由独立工具基准采样形成，并记录输入规模、内部线程与后代进程。初始采用滚动分位数加安全余量，不训练复杂预测模型。声明可并行的步骤还需验证文件、浏览器会话等访问冲突；任意shell无法准确推断读写集时采用保守独占。工具需求与内存硬限制不同：预测用于安排启动，cgroup保护用于限制故障外溢，超过硬边界可能导致任务失败而非安全完成[17]。

跨阶段只申请当前步骤实际需要的资源。等待模型时不提前长期占住CPU工具槽；父Agent等待子任务时释放自己已不使用的执行许可，但仍驻留的上下文、浏览器和文件锁继续计账。若父任务持有子任务必需的资源，调度器必须拒绝该等待模式、拆分阶段或显式转移所有权，防止上层线程池也出现“父等待子、子等待父释放槽”的死锁。

多约束准入在单一资源拥有者内原子判定，失败不留下部分预留；需要分步取得本地互斥资源时按固定顺序申请并在失败后释放。数据库事务和全局控制锁内不进行网络访问或长工具调用。这样的设计把OS中资源分配图与死锁预防用于实际工作流，而不是仅在报告中模拟四个死锁条件。

### 3.3 端与平台协同反馈及有界执行

协同首版采用一条清晰反馈链：平台根据自身队列年龄和在途压力发布带版本、有效期与上下界的建议接纳窗口，客户端保留自己的就绪队列，并根据本地资源可行性决定工具启动。硬合同额度始终独立约束，反馈窗口只在允许范围内调整发送，不把短时模型响应变慢直接解释为额度耗尽。

反馈按固定周期更新，使用平滑、死区和单次最大调整幅度，避免端侧和平台多个控制器同时追逐瞬时延迟。候选实现可采用缓慢增加、出现明确拥塞时乘性减小的窗口控制；具体系数由独立先导负载设定并在正式实验前冻结。反馈过期回退到保守独立策略，保留最低探测机会，防止双方互等空闲信号。该反馈是工程策略，不声称有未经证明的稳定性或最优性。

本地压力摘要只影响确实关联的工作类别。已经知道某模型响应后会产生大量同类工具工作、或预测具有足够置信度时，可限制相关请求的在途工作量；未知后续不得先锁资源，也不能因一个解析器繁忙而停止所有问答。客户端可以在适量在途模型请求与工具执行之间形成流水重叠，但必须测量双重排队和过度限流的反作用。

所有队列、日志和输出缓冲都有容量与保留策略。大工具结果写入有配额的产物存储，消息只传递定位符、校验和与有限摘要；容量不足时显式报错或按任务允许的规则处理，不能静默截断必要数据后声称质量不变。控制与取消事件拥有独立的小容量通道，防止后台逐token事件淹没监督消息。长期产物使用“仍被任务引用则保留，结束且可再生成则按TTL/容量策略回收”的分层管理；不把文本摘要类比为真正的内存分页。

底层执行优先采用Linux进程组和cgroup v2管理自己启动的工具树。cpu.weight是相对份额，cpu.max是带宽上界；memory.high产生回收压力，memory.max在无法回收时可能触发组内OOM。监控与守护进程留在受保护控制组，避免与失控工具一起被终止。设计不扫描整台机器按模糊名称杀进程，也不把只限制网关进程误当限制远处执行器。

### 3.4 一致终止、检查点与守护恢复

TaskLoom 为每次执行建立有期限的所有权记录，关联根任务、步骤、attempt代际、执行器及资源组。心跳超时只表示拥有者失联，需要核对；它不证明旧进程、外部API或写操作已经停止。守护进程确认受控工作达到QUIESCENT后，才归还真实占用。对远端无法确认的工作保留UNKNOWN，防止一边让旧请求继续、一边误把全部额度释放后启动替身。

状态更新和结果发布使用幂等键与代际检查。旧attempt的迟到结果可以写入审计记录，但不能覆盖新attempt的已选结果，不能重复扣费、释放槽或删除当前产物。旧attempt已经产生的真实消费仍须按其唯一账目结算一次，不能因其失去结果发布权而抹去费用。代际围栏只约束愿意检查它的接收端；不支持幂等或状态查询的外部服务，不会因为本地多了一个字段就实现exactly-once。

检查点分成两类内容：运行时控制事实与语义续作提示。前者包含已完成步骤、输入版本、结果引用、预算和待确认attempt，是调度恢复的权威数据；后者包含当前目标、已确认事实、拒绝路径和下一步建议，用于帮助模型继续工作，但不作为资源释放依据。上下文压缩可能丢失语义细节，结构化控制账本应独立保存；模型生成的“完成比例”不直接进入硬调度约束。

对经验证可重放的只读或幂等步骤，可从最近的已确认检查点继续；重放或复用前核验输入版本、当前授权和产物有效性，读取操作也不能无条件复用过期数据。对效果已发生但完成记录未写入的操作，先查询产物或按幂等键对账；不能确定时转人工处理，而非盲重做。文件原子重命名用于结果可见性，若将断电纳入承诺，还需同步文件与目录并明确存储保证；首版故障模型以进程崩溃、超时、连接中断和受控工具异常为主，不将其外推为任意断电可靠性。

![图3 任务终止与资源归还协议](../agent-workspace/assets/taskloom/concepts/taskloom_lifecycle.png)

守护进程承担可展示职责：检测worker或协调器异常、记录故障代际、回收自己拥有的进程树、对账资源与产物、按步骤安全性决定恢复。普通工具逻辑错误交回任务处理，基础设施崩溃走监督路径，遥测导出失败采用独立有界收尾，不能无限拖住主要进程[18,22]。重试分类依赖provider结构化错误、响应头和合同，不能规定“QUOTA永远比RATE_LIMIT优先级低”；总预算耗尽、临时速率限制和未知网关文本需要不同处理。

## 四 实验验证实施计划与预期成果

### 4.1 实验设计与评价方法

实验分为受控机制评估与小规模真实Agent验证。前者固定步骤工作量、到达和模型服务合同，隔离调度变量；后者使用实际运行时与可验收任务，确认接入、结果质量和成本。相同prompt与模型设置不保证生成轨迹完全一致，真实实验需要记录轨迹差异，不能将所有耗时变化归于调度。公开TraceLab可用于到达、调用类型、token和时长分布校准，但没有主机CPU/RAM画像且原始工具文本被去除，仍需自行补测真实工具[2]。

基线全部具备正确依赖、合理重试、取消清理、硬隔离和必要持久化。采用基础2×2比较加一个协同组，避免候选方案仅因比基线多了重试或更宽预算而获益。

| 组别 | 端侧工具与请求 | 平台接入 | 能回答的问题 |
|---|---|---|---|
| B00 | 调参后的独立工具控制与API控制。 | 合理公平/优先及有界队列。 | 成熟简单组合已达到什么程度。 |
| B10 | 根任务与本地阶段感知。 | 保持B00。 | 端侧增量。 |
| B01 | 保持B00。 | 候选任务级调度。 | 平台接入增量。 |
| B11 | 端侧候选策略。 | 平台候选策略，不交换协同反馈。 | 两个独立改进共同启用的结果。 |
| B11F | 与B11相同，开启规定信息交换。 | 与B11相同，开启反馈。 | 协同信息本身的增量。 |

B11与B11F采用相同的基础身份、根任务关系、静态任务声明和候选算法，只切换本地压力摘要与平台拥塞反馈等动态信息交换，从而定位反馈本身的作用。移除根任务关系属于另外的任务感知机制消融，不能混入该主对照。B11F相对于B10或B01更好不足以证明协同；主要协同差值是B11F相对于B11的改善。必要时报告两侧优化的交互项，但它只能描述非加性，不能替代直接反馈消融。

负载覆盖资源宽松、仅API受限、仅本地工具受限、双侧受限四种条件。每组再包含交互与后台比例、任务扇出、输出估计误差和突发程度的变化。参数来自真实合同、公开数据和工具测量，超出真实配置的压力测试单独标注。工具执行使用真实进程与数据，不用恒定sleep验证CPU或内存争用；可控模型回放仅用于隔离固定外部阶段，不冒充模型真实性能。

**主指标定义。**设观察窗口提交的有截止时间任务共N个，任务i的截止时间为dᵢ、完成时间为Cᵢ，验收通过指示为Vᵢ，则准时合格完成率为G = Σ 1[Cᵢ ≤ dᵢ 且 Vᵢ = 1] / N。拒绝和未完成任务保留在提交分母，用户主动取消另列原因，不混入系统失败。后台无deadline任务单独报告合格吞吐与完成时长。若任务截止时间尚未到达观察终点，延长随访或明确按尚未确定处理，不能提前计为逾期失败。

| 指标组 | 具体测量 | 防止误判的要求 |
|---|---|---|
| 有效交付 | 按时合格完成率、完成数、分任务类型的P50/P95。 | 对未完成任务作删失说明或补充排空观察，不能仅对完成者排名。 |
| 公平与代价 | 根任务累计服务、最大等待、长任务slowdown、用户份额偏差。 | 输入/输出权重固定；观察短任务改善是否以长任务饥饿为代价。 |
| 额度与效率 | 实际费用/token、预留/待核对余额、无效重试、管理CPU与消息开销。 | 不把尚未结算费用当节省，纯排序不承诺减少必要token。 |
| 可靠性 | 自有残留进程/内存/产物、取消到静止时延、重复发布/释放、恢复或UNKNOWN处理率。 | 逻辑状态与OS实际状态交叉核对，未知结果不得算自动成功恢复。 |

任务质量采用可以复查的标准：文档处理与计算任务核对固定字段或已知答案，代码任务运行既定测试集，资料任务检查必需来源和结论覆盖。语义性评价在资源指标之外单列，必要时盲评抽样；不使用“模型说完成了”作为唯一依据。长任务slowdown定义为从提交到完成的周转时间与同一轨迹、相同配置下独占执行时间之比；真实Agent轨迹变化时另列差异，不能以不同工作量的独占运行作精确分母。

先导阶段划出独立调参数据，正式实验冻结策略、权重和评价口径，采用多种子与多次配对运行报告波动和置信区间。真实API实验尽量交错执行各策略，记录模型版本、合同和时段；固定推理资源不等于每次外部响应恒定，调度改变到达后产生的间接外部耗时变化与自身排队时间分别报告。

### 4.2 故障实验与30天仿真

可靠性单独消融，保持性能调度相同。故障注入分为四类：执行前失败，执行中worker崩溃，效果已发生但完成记录未提交，以及取消与正常完成竞态。另测试协调器重启、迟到结果、重复消息和失效反馈，但不通过随意提高故障率制造收益。

应检查的不变量包括：同一资源许可不重复释放；当前结果不被旧attempt覆盖；报告QUIESCENT的受控任务没有仍运行的自有后代；已确认成功步骤的恢复结果与输入版本一致。故障按任务事件还是墙钟时间注入需明确，相同随机种子并不自动使不同策略承受相同故障。

30天实验采用离散事件回放，依据先导测量校准任务到达、工具资源曲线、API窗口和服务耗时。时间压缩必须同时维护依赖、服务和额度恢复时钟，不能只加快到达制造拥塞。真实工具并发导致的耗时变化用测得曲线或敏感性区间表示；不能把实际资源干扰删除后再宣布优化了它。

长期展示按日汇总任务交付、等待、费用和残留，也保留突发窗口和最差用户表现。报告结论明确区分实测、模拟和外推。仿真参数、原始事件、配置、种子及分析方法一并提交，形成可复查的课程成果。

### 4.3 实现路线组织分工与进度

拟采用Python实现可修改Agent loop、调度与实验框架，asyncio处理网络等待，独立进程执行受控工具，SQLite WAL保存状态，Pydantic或等价模式验证协议。平台服务使用轻量HTTP框架，Web界面展示任务与资源。选型允许在第一阶段依据接口试验调整，但核心机制不依赖重型分布式集群。首版固定一套OS和provider合同，Windows适配、多端点路由和复杂预测留作扩展。

团队按四个工作包划分，适配课程4至6人小组[1]。四人时每人主责一个工作包并交叉评审；五至六人时将工具执行/可靠性、实验/界面拆分增援。负责人姓名不在本计划中虚构。

| 工作包 | 主要产出 | 交叉接口 |
|---|---|---|
| A 任务与端侧调度 | 根任务/步骤模型、本地队列、Agent及工具接入。 | 与B统一请求元数据，与C统一执行许可及终态。 |
| B 平台与额度 | 合同适配、分层公平、预算结算、反馈。 | 与A对齐任务身份，与D冻结策略配置。 |
| C 执行与可靠性 | worker进程树、资源组、日志/检查点、守护与UNKNOWN处理。 | 为A/B提供可核对事件，为D提供故障注入点。 |
| D 实验与呈现 | 真实任务画像、强基线、统计分析、30天回放和可视化。 | 对全部工作包做独立验收与结果复查。 |

| 课程阶段 | 里程碑 | 可审查交付与进入下一阶段条件 |
|---|---|---|
| 第1至2周 | 范围冻结与先导取证。 | 可接入loop、provider合同、三类真实任务、最小事件协议和工具画像；发现实际排队位置。 |
| 第3周 | 开题与概要设计。 | 可演示的串通原型、状态机、算法规格和对照计划；完成小组方案汇报。 |
| 第4至6周 | 分层实现、集成和小组验收。 | 第4周独立基线与账本，第5周调度/守护及故障检查，第6周协同消融与可运行演示。 |
| 第7至8周 | 复核与个人答辩。 | 补齐统计与长期回放，交付文档/代码/数据；每人能解释所负责OS机制、证据与限制。 |

首版完成标准是可运行的任务闭环，不是功能列表无限扩张。若协同接口迟迟不稳定，先完成端侧与网关的独立模式以及相同事件协议；若真实API波动太大，保留可控机制实验并缩小真实验证范围；若简单基线已足够，则如实报告边界，不临时挑选弱基线挽救结论。

### 4.4 预期成果风险与创新价值

预期交付包括可运行原型及真实守护组件、任务/资源可视化界面、可复现基线与实验数据，以及开题到结题的设计和验证文档。基本体验是用户提交任务后能够理解它在等待什么，平台能够解释服务机会如何分配，异常发生后系统能说明哪些工作已完成、哪些资源已回收、哪些结果仍待确认。

正确性验收以受支持工具、合同和故障集合为边界，要求不发生已知重复释放、旧代际覆盖等违反不变量的行为。性能目标作为待验证工程目标：在先导确认存在竞争的测试集上，争取相对B11降低交互P95至少10%，同时长任务slowdown恶化不超过10%，且结果质量与硬约束不放宽。该阈值是项目自选的最小有意义目标，不来自论文效果；先导阶段检验测量分辨率后冻结，正式结果未达到时报告原因和适用范围，不事后改门槛。

| 风险类别 | 具体风险 | 应对与验收原则 |
|---|---|---|
| 场景与收益 | 真实负载主要等待外部模型，固定并发已充分有效。 | 保留低竞争负例，以分阶段计时决定重点，允许否定协同假设。 |
| 接入与信息 | 商业harness接口不完整，provider额度不可精确观察。 | 首版选可修改loop与自建网关，合同可控模拟与真实验证分开；未知信息显式记录。 |
| 活性与恢复 | 多资源等待、错误回滚、迟到结果、非合作工具。 | 单一资源拥有者、短临界区、固定申请顺序、代际校验和受控进程树；外部效果不确定保留UNKNOWN。 |
| 工程范围与评价 | 多层系统过大、弱基线或只报成功者延迟。 | 分阶段交付、双优无反馈基线、质量约束、删失与在途费用统一口径。 |

TaskLoom 的研究价值在三个具体方面展开。第一，将模型请求、工具与子任务关联到根任务，建立跨阶段可解释的服务计量与资源所有权。第二，在固定推理条件下，验证分层公平、向量准入和有限反馈能否改善完整任务交付，而非只优化一个局部队列。第三，将OS课程中的互斥、通信、进程控制、守护与恢复融入可观察的系统机制，形成故障与性能都可复查的实验平台。

这些贡献属于特定场景中的系统设计与实证验证，现阶段不主张全新调度理论或通用最优。项目愿景是为Agent执行建立清楚的秩序：计划可以动态变化，但资源必须有归属，等待必须有原因，完成必须有依据，恢复必须知道边界。只有经过对照实验确认的增量，才进入结题时的性能结论。
