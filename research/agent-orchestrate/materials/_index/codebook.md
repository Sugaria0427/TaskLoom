# TaskLoom 四层分析编码规范

> 将来源身份、主题判断、证据强度和问题剩余程度分开记录，形成可查询和可更新的调研体系。

**规范版本** 2.1　**整理日期** 2026-10-14　**适用材料** 本资料库当前索引与三篇报告。

本规范依次定义四层与主题、来源记录、分析状态和维护规则。原始材料中的旧分层或产品文字属于证据快照，当前归类以本规范及`source_catalog.json`为准；历史解读保存在整理前压缩快照中。

## 1. 四层与主题编号

### 1.1 主层的判定

主层依据本项目能够控制的对象及主要问题位置确定。L1–L3在个人端，L4在本项目拥有的应用API网关；层编号在全部当前记录中保持一致。

| 层编号 | 名称 | 判定对象 |
| :--- | :--- | :--- |
| L1 | 本地资源与工具执行 | 工具容量、实际进程、产物、共享访问和资源分配。 |
| L2 | Harness与Agent任务管理 | 任务身份、依赖、父子关系、状态、取消、交付和恢复。 |
| L3 | 个人模型请求与额度 | 一个用户的发送队列、任务预算、在途调用和重试。 |
| L4 | 平台多用户请求与协同 | 用户间份额、平台接纳派发和与个人端的信息交换。 |

每条有效项目来源只设一个`primary_layer`，关联层写入`related_layers`。推理内部、模型选择和范围外服务等级归入BACKGROUND；这类材料保留在归档并将主层设为`null`。

### 1.2 主题与案例的关系

主题ID使用`T-Lx-nn`，每层四个主题，共16个。主题记录的是一个机制问题，可以关联多产品、多来源和多种已有措施；案例状态另存于来源记录的`case_assessment`。

例如，`T-L3-01`汇总重试提示与等待预算；D892、D3128、D3852和D7926仍保持各自来源ID，同时共享`deepseek_retry_contract`机制家族。这个家族用于合并叙述，不把多条讨论当作多次独立事故。

## 2. 来源记录与追溯

### 2.1 稳定编号与引用别名

P、A、L、CX、CC、D等既有来源编号全部保留。OpenClaw使用OC-D（文档）、OC-S（源码）、OC-I（问题单）、OC-P（PR）及OC-M（版本资料），与S引用别名区分。OS资料使用OS21–OS24。归档分层说明书的S01–S23通过`citation_map.json`映射，OS算法补充沿用其中S21–S23；现行完整说明书使用来源编号与公开链接。S是特定文档的引用别名，T是主题编号。

来源记录采用以下四组统一字段，类型一致的记录可以直接筛选。

| 字段组 | 统一字段 | 含义 |
| :--- | :--- | :--- |
| 来源身份 | `source_id`、`title`、`url`、`canonical_key`、`source_type` | 标识来源及网页、论文或issue的去重键。 |
| 四层归类 | `primary_layer`、`related_layers`、`scope`、`theme_ids`、`theme_roles`、`mechanism_family` | 表明存放层、主题用途及同机制关系。 |
| 原文与核查 | `artifacts`、`preferred_text`、`usable_source`、`verification` | 提供原始文件、优先阅读文本、访问状态、阅读范围与条件。 |
| 分析与沿革 | `case_assessment`、`citation_aliases`、`provenance`、`coding_note` | 保存案例状态、引用映射和原始登记来源。 |

### 2.2 作用范围

作用范围与层归类分别判断。相邻合同材料可以放在对应层，但其用途会明确标为ADJACENT；待测的API竞争不会由订阅用量投诉直接证明。

| 编码 | 含义 | 主要使用方式 |
| :--- | :--- | :--- |
| CORE | 直接支持当前四层。 | 进入相应主题论证。 |
| ADJACENT | 相邻合同、版本或场景。 | 定义需求、反证或待核条件。 |
| METHOD | OS方法、接口或评价方法。 | 支持方法选择及成立条件。 |
| BACKGROUND | 当前范围以外的研究。 | 保存先例和背景，退出当前痛点排序。 |
| EXCLUDED | 已撤回或不采用的归因。 | 保留排除依据。 |
| ACCESS_FAILED | 访问失败或内容不可用。 | 保留检索记录，另找有效来源。 |

### 2.3 来源键与机制家族分别去重

`canonical_key`合并同论文的摘要、正文及已确认的正式版本页面；`mechanism_family`合并同问题的issue、讨论和相关源码。相同来源用于多个主题时，只产生一份原始材料。

整库来源数包含文档、问题单和数据记录。唯一来源键与机制家族都是查询和去重单位，它们分别对应不同的独立性口径。

## 3. 分析状态、证据与严重度

### 3.1 已解决程度

解决状态依据具体问题和已查能力决定。问题单的open或closed只保留为原始事实，当前编码通过修复、配置、路径覆盖和发布依据判断。

| 编码 | 状态 | 判定方式 |
| :--- | :--- | :--- |
| D | 已有覆盖 | 同问题同范围已核到实现或修复；发布适用性另外说明。 |
| C | 配置可解 | 现成配置或正确用法处理所述问题，注明成本与条件。 |
| P | 部分未覆盖 | 已有基础机制，特定路径或事件仍有明确剩余。 |
| T | 结构性取舍 | 成熟机制仍在安全、利用率、公平或时限之间取舍。 |
| U | 待确认 | 根因、当前覆盖或强基线后的实际损失不足以确定。 |

案例编码和主题编码承担不同职责。一个主题可以包含已覆盖反例和部分剩余案例，例如T-L2-01保留所有权回滚问题，同时把历史session写锁记录为D。

### 3.2 证据等级

等级评价的是某项陈述的依据。正式接口可直接证明能力，用户故障报告可证明报告者观察的现象，论文测量依照原实验条件解读；所有来源均另记阅读与复现状态。

| 编码 | 证据 | 使用要求 |
| :--- | :--- | :--- |
| E1 | 原文直接结果、正式契约或明确实现事实。 | 对应到被证明的具体事实与条件。 |
| E2 | 问题记录与已查源码相互支持。 | 说明选读路径及尚未独立运行复现。 |
| E3 | 用户案例、方案提案或社区测试。 | 归因与当前适用性分别保存。 |
| E0 | 线索不足或尚无直接证据。 | 用于研究假设与待验证项。 |

`cause_status`进一步区分正式合同、静态关联、条件案例和研究假设。主题中引用成熟方案，只能支持已有方法与机制分析；候选性能增量使用单独实验验证。

### 3.3 剩余严重度

严重度描述合理已有措施之后仍剩下的后果。高等级绑定触发条件，证据强度和行业发生率分别讨论。

| 编码 | 剩余后果 | 排序规则 |
| :--- | :--- | :--- |
| H | 任务阻断、资源耗尽或成果无法交付。 | P/T且有对应条件与证据时，层内优先。 |
| M | 显著等待、失衡、额外开销或人工恢复。 | 在高等级之后比较剩余程度与可介入性。 |
| L | 局部开销，已有可接受绕过。 | 作为较低优先级优化。 |
| NA | 已覆盖、只作方法依据或损失未量化。 | 退出剩余严重度排序，必要项单列待验证。 |

不确定案例归U/NA，原始报告中的严重后果保存在核查备注。主题中已知缺口与未归因子案例可以共存，报告按各子项准确引用。CSV可按主层、解决状态、严重度和证据筛选。`case_assessment.version_status`分别记录稳定版与main的解决状态，`repository_context`保存固定提交和版本材料；当前主分支已修复的案例使用D/NA，稳定版剩余写入版本明细。

## 4. 更新、目录与完整性

### 4.1 新增与更新步骤

维护顺序分为四步，使证据和结论同步。

1. 登记来源身份、原文、实际取得日期和适用版本，确认去重键。

2. 判定主层与作用范围，将材料放入来源目录并关联主题角色。

3. 更新案例和主题的解决状态、证据与条件，保留已有控制和反证。

4. 更新三篇报告中受影响的结论，再运行来源、路径、编码和链接检查。

研究假设、故障案例和已覆盖机制分别记录。后续实测结果需注明环境、工作负载、质量验收、基线和统计口径，形成新的证据记录。

### 4.2 当前维护文件

主题判断的结构化入口是[analysis_catalog.json](analysis_catalog.json)，原文入口是[source_catalog.json](source_catalog.json)；报告对二者做面向读者的归纳。[theme_matrix.csv](theme_matrix.csv)提供可筛选表，[source_index.md](source_index.md)提供阅读导航。

旧source registers、分析笔记、检索日志和脚本保存在历史快照（本地留存：`research/agent-orchestrate/materials/_archive/before_reorganization_20261014.zip`），迁移关系见[migration_manifest.json](migration_manifest.json)。[validation.json](validation.json)记录文件保留、来源ID、主题引用和当前链接检查结果。

### 4.3 检查范围

完整性检查确认原始材料哈希、JSON字段、编号唯一性、主题引用、四层存放位置和本地链接。原始网页及publisher Markdown保留网站相对链接，按证据快照读取；当前报告与索引的本地链接单独验证。

检查结果属于资料质量证据。产品缺陷复现、真实Agent运行和TaskLoom性能实验在项目实现阶段产生各自的记录。
