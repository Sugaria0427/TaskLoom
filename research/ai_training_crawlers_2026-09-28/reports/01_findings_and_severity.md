# AI 训练语料抓取对网站的损害：事实、根因与严重度

调研截止：2026-09-28。本文是本轮主结论；技术对策见 [02](02_existing_defenses.md)，OS 可解决问题见 [03](03_os_research_opportunities.md)，文献与证据审计见 [04](04_sources_and_audit.md)。

## 1. 明确回答：问题存在，但不能把所有 AI 流量都当成训练抓取

**“批量获取训练语料的爬虫会加重网站负载，甚至造成服务中断、资源费用和维护损失”有足够的一手材料支撑，可以作为课设的现实背景。** 本轮核心证据覆盖四个独立机构、三类网站：SourceHut 与 Codeberg 的代码协作服务、Wikimedia 的百科/多媒体、MetaBrainz 的音乐元数据与开放知识 API。

这里的“训练归因”主要来自机构维护者的明确说明，不等于研究者获取了爬虫运营者的训练流水线。对于用途不明的抓取，我们保留其资源损害证据，但不把它升级为训练爬虫确证。没有公开统一数据集能支持“全网多少损失都是训练抓取导致”的结论。

**问题的根因也已能进一步定位：公共页面请求可能触发远高于传输一个文件的数据库查询、历史差异计算或归档生成；广泛扫描增加首次/冷门内容回源；多来源的合计工作量又没有被单 IP 配额限制住。** 因此，单看请求次数、人机标签或网络字节会漏掉关键资源压力。

但“现有技术没有解决办法”不成立。缓存修复、访问认证、挑战、负载准入和批量数据出口已经有成功案例。剩余问题是在特定部署、负载与访问政策下，现成机制能否以可接受的开销、误伤和等待代价稳定工作。

### 1.1 证据的两个维度

本轮分别记录“损害是否有证据”和“训练用途是否有证据”，避免把身份、用途和性能因果混在一起。

| 维度 | 较强证据 | 有条件证据 | 不能推出什么 |
|---|---|---|---|
| 损害与机制 | 站方运行指标、状态页、费用、具体故障链或接口变更 | 单一维护者自述、估算、未公开原始遥测 | 大量请求不自动等于 CPU 饱和；写入失败不等于永久数据损坏 |
| 训练用途 | 机构明确描述训练采集；经验证的训练 crawler 身份可辅助归因 | 一般 LLM/AI 标签、混合用途 crawler、未知代理来源 | 请求格式、鼠标行为、IP 或 UA 无法证明数据最终进入训练 |

四个核心机构均有明确的训练/建模用途归因；不把同机构多篇后续文章算作多个独立机构。辅证和排除记录另列，不合并成“已确认训练事故数量”。

## 2. 核心案例：发生了什么，为什么发生，后来怎样

### 2.1 代码协作站：昂贵动态操作与共享后端受压

| 案例 | 实际后果与证据 | 根因支持到哪一步 | 当前解决状态 |
|---|---|---|---|
| SourceHut，2025–2026 | 官方博客和状态页记录 git web frontend 被 LLM 抓取干扰；2025-12、2026-06明确提到训练用途 | 站方确认抓取与服务性能下降；没有足够细粒度遥测将瓶颈全部归为 CPU、DB 或网络 | 2025 Anubis/go-away有效缓解；后续仍复发，2026-06事件当晚已有部分缓解，9月14日关闭 |
| Codeberg，2025–2026 | 2026-07官方明确：训练采集遍历 issue 筛选组合、Git 历史和重复文件，降低服务质量并消耗维护资源 | 原文直接指出昂贵数据库查询；2025说明分布式来源可低至单 IP 每日约2请求，单 IP 限流难以抑制合计负载 | 昂贵路由/Weblate已用Anubis，部分抓取被挡住；2026仍报告持续压力 |

SourceHut 的状态记录比泛泛新闻标题更有价值：[2025-03 状态页](https://status.sr.ht/issues/2025-03-17-git.sr.ht-llms/)明确区分受影响的 web frontend 与当时正常的 API、git、SSH；[2026-06 状态页](https://status.sr.ht/issues/2026-06-06-llms-again/)记录后续波次及缓解进展。状态系统显示的约 2381 小时是事件开放跨度，**不能解释为连续约99天全站停机**。SourceHut 另一篇 2026 Q2 网络 DDoS 记录不纳入训练抓取核心证据。

Codeberg 的 [2026-07-23 原文](https://blog.codeberg.org/protecting-our-floss-commons-from-llms.html)给出最适合建模的根因：逻辑上有限的代码内容可以通过许多筛选、历史和页面表示触发大量重复或昂贵工作。**爬取“可达 URL 空间”与获取“独特内容”不是一回事。** 该判断有站方具体访问描述支持，但没有公开每类请求的 CPU 毫秒或 SQL 执行分布，需要课设自行测量。

### 2.2 百科、多媒体与开放数据 API：回源、带宽和交互通道被批量消费

| 案例 | 实际后果与证据 | 根因支持到哪一步 | 当前解决状态 |
|---|---|---|---|
| Wikimedia，2025–2026 | 多媒体下载带宽自2024-01增长50%；正常热点事件时部分链路约一小时满载、部分用户加载变慢 | 站方将主要增量归因图片批量抓取；广泛访问冷门页面导致更多昂贵回源。bot约35%页面访问与至少65%昂贵回源是不同口径 | 2026报告约30%自动请求被阻断/限流；加强API治理、可信身份和bulk出口；仍存在匿名代理与带宽问题 |
| MetaBrainz，2025-12至2026-08 | 官方称逐页采集用于建模导致合法用户不能访问；后续增加token/登录、关闭部分端点。2026又报告约5倍通常流量的抓取突发及部分端点在抓取时使ListenBrainz站点不可达 | 抓取使用交互页面/API而不下载已有数据dump，触发共享后端工作；但正常增长、导入、刷记录与DB/Spark容量也是后续故障因素 | 多项准入和接口收缩已落地，仍调优容量；不能将所有积压、OOM或队列数归给爬虫 |

[Wikimedia 2025](https://diff.wikimedia.org/2025/04/01/how-crawlers-impact-the-operations-of-the-wikimedia-projects/)说明的直接链条是“提高常态带宽占用→降低余量→正常事件叠加时局部拥塞”。这不是“AI 请求直接让整个维基百科停机”。[2026 回访](https://diff.wikimedia.org/2026/03/26/quo-vadis-crawlers-progress-and-whats-next-on-safeguarding-our-infrastructure/)证明防护确实有作用；30%是自动请求的拦截/限流比例，不是CPU节省比例。

[MetaBrainz 2025-12](https://blog.metabrainz.org/2025/12/11/we-cant-have-nice-things-because-of-ai-scrapers/)将训练用途、逐页获取和过载联系起来，并列出实际接口变更。[2026-08-19后续](https://blog.metabrainz.org/2026/08/19/growing-pains-an-update-on-the-listenbrainz-service-status/)显示问题持续且有多重根因。需避免用单一“AI爬虫”解释正常增长或数据处理系统自身瓶颈。

### 2.3 补充机制证据：损害具体，但训练用途不能全部确认

| 网站类型与案例 | 可核验后果 | 准确的根因/限制 |
|---|---|---|
| 文档托管 Read the Docs，2024 | 一次爬虫下载73TB，带来超过5000美元费用，后获赔付；阻断AI分类来源后文件下载带宽下降75% | 重复旧ZIP下载、重定向进入未缓存路径、未用条件请求；训练用途未逐项确认，Facebook下载部分作者明确不知用途 |
| 自托管 Forgejo，Jade Ellis 2025 | 自动生成归档占满数百GB磁盘，继发内存压力、数据库写入失败和多服务离线；维护者约两小时后恢复访问处理 | 已有清理cron仍未阻止本次积累；有效总量预算不足是据此提出的机制判断。抓取归因AI是个人判断，训练用途未证；没有证据证明永久数据丢失 |
| 游戏Wiki Weird Gloop，2026 | 缓存请求通常<20ms，旧diff常1–2秒，作者估算50–100倍服务成本；短时1000+RPS，长期均值掩盖高峰 | 路径/参数组合巨大且绕过缓存，源站工作放大；作者明确不知道抓取主体或数据用途，故不是训练确证 |
| GNOME/Gentoo等协作系统 | 有访问故障、维护者说明及认证/防护调整 | GNOME原始归因用likely；Gentoo为LLM标签；不扩大成已确认所有故障都来自训练抓取 |

原文：[Read the Docs 2024](https://about.readthedocs.com/blog/2024/07/ai-crawlers-abuse/)、[Forgejo维护者记录](https://jade.ellis.link/blog/2025/05/18/actually-stopping-forgejo-ai-scraping)、[Weird Gloop 2026](https://weirdgloop.org/blog/clankers)。这些辅证可用于确定实验的资源链条，但不能借它们虚增训练爬虫的确证数量。

Read the Docs 是重要的反例：**应先修缓存和重定向路径，再谈复杂调度。** Forgejo 的最直接保护也可能首先是归档生成并发、磁盘配额和清理，而不需要准确识别人机。已有 go-away 缓解成功也必须报告。

### 2.4 网站类型的覆盖空白

代码协作、百科/多媒体、音乐知识服务已有训练用途归因较强的一手材料；文档、个人站和游戏Wiki提供更具体的机制辅证。没有找到同等强度的一手材料证明电商、博物馆、新闻站等各类网站普遍因训练抓取发生资源故障，**不以其他类型的bot问题或新闻转载补齐这一空白**。

出版与创作者权益研究可以证明控制诉求、robots部署差异等，但不能据此推导实际收入损失全部由训练阶段抓取造成。AI答案替代点击主要发生在检索/回答阶段，是另一个因果问题。

## 3. 按严重程度排序：分清已发生损害与尚未证明的推断

以下按本课设的服务运营影响排序，不是对版权、隐私或社会价值的通用轻重排序。严重度与证据强度独立呈现，不能将后果严重但归因不明的案例写成最强训练证据。

| 顺位 | 损害类别 | 已有证据与范围 | OS可干预程度 |
|---|---|---|---|
| S1 | 服务不可用、关键操作失败、资源耗尽外溢 | SourceHut/MetaBrainz有站方训练归因；Forgejo有磁盘满→写失败的具体机制辅证 | 对执行准入、进程/存储隔离、内存/产物限额可强干预；对已饱和上游链路有限 |
| S2 | 持续高延迟、热点访问被挤压、峰值容量丧失 | Wikimedia带宽余量与回源；Codeberg昂贵DB；Weird Gloop成本差异辅证 | 成本并发、缓存准入/置换、公平调度、出口带宽分配可改善 |
| S3 | 额外费用、运维工时、防护带来的访问门槛 | RTD费用且已获补偿；SourceHut数周维护；MetaBrainz要求登录/token、删除部分端点 | 可减少重复工作、自动回收/恢复和细粒度隔离；不能保证无误伤或自动追回费用 |
| S4 | 内容用途控制、授权/补偿、开放生态影响 | IMC等研究与站方政策说明支持问题存在；具体收入/训练泄露损失需另证 | 授权与审计可限制未来服务；OS不能约束内容离站后的训练、许可争议与商业替代 |

本轮没有足够材料确认由训练抓取造成的永久数据损坏、已量化的全行业损失、所有访问者隐私泄露或缓存命中下降的统一幅度。不得用“破坏”一词把性能损害自动升级为内容删除或安全入侵。

## 4. 根因定位：不是“AI”这个标签，而是具体工作如何被触发和积累

### 4.1 工作放大：访问一条URL可能创建大量后端工作

**证据支持的链条：**筛选/历史/差异/逐页API访问→数据库查询或动态计算→共享执行能力受压→正常业务延迟或失败。Codeberg与MetaBrainz直接支持这一链条；具体CPU、DB锁或I/O分量还需测量。

**解决状态：**限制昂贵端点、缓存可复用结果、提供dump、按估计成本准入均是成熟办法。剩余难点是请求成本变化大、同一资源既服务交互又服务批量、未知身份和数据新鲜度约束。不是再加一个“每秒请求数”就必然解决。

### 4.2 局部性变化：冷访问回源与缓存污染是两个不同问题

**已观测：**大范围抓取更常访问冷门内容，缓存未命中导致回源；不可缓存参数路径也会直接触发动态工作。**待测：**这些新对象是否进入缓存并挤出了正常热点，不能只凭未命中多就认定发生污染。

**解决状态：**已有缓存、single-flight合并、TinyLFU/S3-FIFO/SIEVE等策略。抗扫描准入可以保护热点，但无法使大量不同冷对象的第一次生成免费；缓存也不能免除向客户端传输内容的带宽。SoCC2025已研究AI流量与缓存：后续用户提供全文后，确认其具有原型/合成缓存实验，而完整分层架构仍是提案；详见[全文补读](05_socc2025_fulltext_reading.md)。该主题不能称为空白。

### 4.3 存量积累：队列、连接和生成文件不是请求结束就自动归零

**已观测：**Forgejo案例中生成归档占满磁盘并影响其他服务。**机制推断：**长时间等待连接、无界日志/来源状态等也可能使保护模块自身耗尽，但本轮没有证据将每一种都归到训练抓取实际事故。

**解决状态：**有界队列、产物磁盘预算、TTL/置换、并发生成限制、进程隔离和守护回收已有方法。剩余工程问题是怎样让“准入—生成—缓存/文件保留—释放”使用一致预算，避免仅限制生成并发却让累计产物仍无限增长。

### 4.4 总量与身份错配：每个IP都很少，合计仍能过载

**已观测：**Codeberg与站方记录支持分散来源导致单IP限额不足；Wiki机制辅证说明突发远高于长期均值。**不能推出：**相同SYN/TLS指纹必定属于同一训练组织，或匿名主体能被可靠合并。

**解决状态：**全局/端点容量控制不依赖识别意图，能够先保护源站；按可信身份分配配额、匿名池受总量约束可以限制身份扩张的收益。剩余难点是匿名公网中无法无条件保证“每个真实人公平”，且优先服务真人需要额外信息，不能单靠资源调度创造身份真值。

## 5. 对当前选题的直接判断

**可立项的事实基础：充分。可宣称所有训练爬虫都不守规则：不充分且有反证。可宣称现有反爬没有资源调度：错误。可以用OS方法改善源站压力：可以，而且对执行准入、存量预算和缓存管理有明确控制点。**

因此应把核心从“找到AI训练爬虫并降级”改为“对批量采集触发的昂贵工作和资源存量进行预算管理”。训练采集是有证据的应用背景；网站仍然根据可观察资源和访问政策控制服务，不需要等待完美识别训练用途。

最值得进入预实验的是代码站/开放数据API的昂贵工作准入，以及生成产物的生命周期预算；缓存与带宽为相邻但独立的资源路径。选择哪条主线取决于可复现瓶颈，不能把所有OS算法同时装进系统。具体候选方案、强基线与止损条件见 [03](03_os_research_opportunities.md)。
