# Agent / LLM 工作流调度调研与课设方案

检索日期：2026-09-26  
目标：核验“Agent 调度是否是当前真实问题”，找出已有解决方案覆盖到哪里、仍可做的课设级问题，以及完成后可以量化的现实指标。

> **2026-09-27 复核说明：**本文的“团队共享平台”是候选设想，未获选题确认；服务器证据不能直接推导个人 PC 的工具拥塞。新增调研发现 AIOS、PeakBench 等直接相关工作，并补入生产追踪中“多数会话受模型耗时主导、工具并行较少”的反证。选题判断、现有方案和证据边界以[补充重评报告](agent_resource_competition_reassessment.md)为准。下文保留原方案用于追溯，不代表已验证的现实收益。

## 结论先行

“Agent 调度”是当前真实存在的系统问题，但不能笼统地说“Agent 没有调度”或“LLM 调度还没有人做”。截至 2026 年，以下问题已经有很强的研究成果：

- LLM 请求的 token 公平性；
- prefill/decode 分离和连续批处理；
- 多实例之间的动态迁移；
- 以完整 Agent 程序为单位的 LLM 调用调度；
- 面向 SLO 的 LLM serving；
- GPU 集群上的工作流级调度。

因此，下面这些说法不能作为项目创新点：

- “我们第一次给 LLM 请求加优先级”；
- “我们第一次按照 Agent 工作流进行调度”；
- “我们第一次减少多用户 Agent 的等待时间”；
- “我们第一次解决 LLM 的吞吐—延迟权衡”。

文献同时给出了一个更适合操作系统课设的、较窄的切入点：

> **在共享 Agent 运行时中，多个动态工作流会交替产生 LLM 调用和工具调用；工具资源有限、执行时间长尾明显、工具调用会失败或重试。如何在普通操作系统资源上，对“可运行的工具步骤”进行依赖感知、资源感知和故障可恢复的调度，以降低关键任务的端到端完成时间和无效重复执行？**

这不是宣称“领域无人研究”，而是把已有的 GPU/LLM-serving 研究成果下移到一个课设能控制、能实现、能对照的层面：**工具执行资源与工作流运行时**。

## 1. 研究范围与检索方法

### 1.1 研究问题

本次调研围绕四个问题：

1. 多用户 Agent 或 Agent 工作流是否已经造成可观察的等待、尾延迟、资源浪费和公平性问题？
2. 现有论文主要优化的是哪一层：GPU 推理、LLM 请求、完整工作流，还是工具执行？
3. 已有方案留下了哪些明确限制，哪些限制适合在操作系统课设中模拟？
4. 系统完成后应该用什么业务指标，而不是只报告吞吐或模型准确率？

## 2. 文献已经确认的现实问题

### 2.1 Agent 请求不再是一个独立的“输入—输出”请求

Agent 请求会展开为多个 LLM 调用、工具调用、控制决策和中间状态。NSDI 2026 的 Agentix 将 Agent 程序描述为运行时逐步形成的动态工作流，而不是一组互相独立的 LLM 请求。论文指出，已有只按请求调度的 serving 系统会出现两层 head-of-line blocking：一个长 LLM 调用会阻塞其他调用，一个长 Agent 程序还会继续阻塞其他程序。

[Agentix 官方页面](https://www.usenix.org/conference/nsdi26/presentation/luo)报告其在评估工作负载中把程序视为一级对象后，在相同延迟下实现了相对 vLLM 的 4–15 倍程序吞吐改善。这个结果同时说明两件事：

- 平台层的工作流调度确实是现实问题；
- “做一个能识别 Agent 工作流的调度器”已经被高水平论文做过，不能直接作为你们的创新点。

### 2.2 实时聊天、完整回答和复合 Agent 任务有不同的服务目标

NSDI 2026 的 JITServe 将请求分成三类：

- 关注首 token 和 token 间隔的交互请求；
- 需要在截止时间前拿到完整回答、否则无法触发下游工具的请求；
- 由多个依赖调用组成的复合请求。

论文报告在 chat、deep research 和 agentic pipeline 上，服务 goodput 提高 1.4–6.3 倍，或在相同 goodput 下节省 28.5%–83.2% 资源。它还明确指出，负载变化、响应长度未知、依赖关系未知和分布变化会造成调度决策不确定性。

[JITServe 官方页面](https://www.usenix.org/conference/nsdi26/presentation/zhang-wei)给出的现实指标不是“平均吞吐最大”，而是**有多少请求在自己的应用级 SLO 内完成**。这对课设很重要：Agent 系统应测量任务是否按时完成，而不是只测量调用了多少 token。

### 2.3 工具执行把 Agent 工作负载变成 CPU、I/O 和外部资源混合负载

2026 年的生产规模编码 Agent 追踪研究 *Agentic Coding in the Wild* 报告了 3.2M 用户、13M 会话、761M LLM 调用和 95T tokens 的采样数据。论文摘要指出，编码 Agent 的一轮用户请求会交替产生 LLM 调用和工具执行，token 数、会话时长和工具调用数具有长尾；同一轮内 KV cache 命中率平均约 90%，跨轮次下降到约 55%。

论文全文进一步报告：

- 9.1% 的 turns 被归为 deep-loop-with-failures 类，包含约 36 次 LLM 调用，为中位数的 4 倍；其中混合了构建错误、错误假设、缺失依赖和重试，不能全部解释为可由检查点消除的重复计算；
- 读取和搜索工具通常较快且成功率高；
- `run_command`、构建和文件修改类工具耗时变化大、失败率明显更高；
- 工具执行阶段是 Agent 工作流尾延迟的重要来源。

复核补充：论文同时指出多数会话由 LLM 时间主导，工具优化主要惠及少数长外部操作工作流；93% 的工具 batch 仅有一个调用。上述长尾并不证明个人 PC 上普遍存在资源竞争。

[arXiv 页面](https://arxiv.org/abs/2608.00101)同时把“质量感知调度”和“服务器端资源指标”列为限制和后续方向。因为它是预印本，课设应把这些数字标为该研究的追踪结果，不能说成整个行业的普遍比例；但它足以说明工具执行不是可以忽略的附属步骤。

### 2.4 Agent 运行时存在 CPU/GPU 交替、突发和资源碎片

*Architectural Implications of Agentic AI Workflows* 使用 Microsoft Azure 生产研究和开源框架控制实验，指出 Agent 执行会反复跨越 CPU–GPU 边界：LLM 推理使用 GPU，编排和工具调用主要使用主机 CPU/IO。论文报告了：

- 平均利用率可能不高，但短时突发明显；
- 一个工作流的不同阶段对 CPU、GPU、内存和工具资源的需求不同；
- 统一的服务器资源配置会留下 CPU/GPU 碎片；
- 多个 Agent 共用核心会增加局部性和协调开销。

其 Agora 原型已经研究了按角色分配 CPU、回收空闲核心和保护尾延迟。因此，课设不应把“CPU/GPU 异构资源调度”作为原创算法，而应把范围缩到普通主机上可复现的**工具池、任务队列、CPU/内存预算和故障恢复**。

## 3. 已有方案覆盖到哪里

| 层次 | 代表工作 | 已解决的重点 | 你们不能再声称的新颖性 |
|---|---|---|---|
| LLM serving 请求 | Orca、Sarathi-Serve | 迭代级调度、prefill/decode 干扰、吞吐—延迟折中 | 不是“首次做 LLM 请求调度” |
| 多实例 serving | Llumnix、DistServe | 动态迁移、实例负载均衡、prefill/decode 分离 | 不是“首次做动态 LLM 资源分配” |
| 应用级 LLM 工作流 | Parrot、Agentix、Orla | 利用请求之间的语义/阶段/程序依赖 | 不是“首次知道 Agent 有工作流” |
| GPU 集群 Agent 工作流 | SAGA | 工作流级调度、KV 复用、GPU 公平性 | 不应复现 GPU 集群调度 |
| CPU/GPU Agent 服务器 | Agora 原型 | 主机 CPU 角色调度、空闲资源回收、局部性 | 不应声称首次做 Agent CPU/GPU 调度 |
| 工作流恢复 | ExoFlow | 执行与恢复分离、Exactly-once DAG | 不应声称首次做工作流检查点/恢复 |
| **工具执行运行时** | 生产追踪显示工具长尾、失败和重试，但上述多数系统的主要调度对象仍是 LLM serving 或 GPU 资源 | **适合课设做受限集成** | 不应声称“没人研究”，应说“在可控的主机工具资源和故障条件下进行系统化对比” |

OSDI 2024 的 VTC 还说明，只按请求数做公平性很粗糙，因为请求的输入/输出 token 成本不同。[官方页面](https://www.usenix.org/conference/osdi24/presentation/sheng)

这意味着，课设应至少按“预计工作量”或“已消耗服务量”计账，而不是只给每个任务一个固定优先级。

## 4. 仍然适合课设的研究空白

这里的“空白”指**适合你们在受控仿真中验证的组合问题**，不是声称学术界没有任何相关工作。

### 4.1 工具资源冲突没有被课程级系统清楚呈现

Agentix、JITServe 和 SAGA 的主要调度对象是 LLM 调用、模型 serving 或 GPU 状态；Orla 已经提出了工具/阶段编排抽象，但仍然是新的系统方向。一个具体的课设问题是：

> 多个动态工作流同时需要浏览器、代码执行沙箱、文档解析器和文件写入器时，怎样选择“当前可运行的工具步骤”，让短的、接近截止时间的任务不被长的构建或检索步骤堵住？

这里的资源不是抽象的 GPU 算力，而是可直接模拟的：

- 浏览器会话数；
- shell/代码沙箱数；
- 文档解析 worker 数；
- CPU 核数；
- 可用内存；
- 文件锁；
- 外部 API 并发额度。

### 4.2 工具失败和重试会造成可量化的无效工作

生产追踪已经指出，命令执行、构建和文件修改工具更容易失败且耗时长。一个简单重试器可能使同一工作流重复执行很多前置步骤。

可以研究：

- 哪些步骤可安全重试；
- 哪些步骤必须依赖检查点；
- 失败后重试当前步骤还是回滚到上一个检查点；
- 用户取消后如何传播到子进程；
- 守护进程重启后如何恢复而不重复产生副作用。

这能直接对应课件的守护进程、进程控制、信号、文件锁和持久化。

### 4.3 任务完成时间、公平性与资源利用率互相冲突

Agentix 的附录明确显示，知道完整运行时间的 SRPT 仍然优于非全知调度，而完整运行时间在实际中不可得；SAGA 也报告了任务完成时间改善和峰值吞吐下降之间的权衡。

因此，项目不应只追求一个指标。可定义三类目标：

- 交互/截止时间任务的按时完成率；
- 用户或工作流之间的公平性；
- CPU、工具池和模型调用额度的利用率。

## 5. 建议的课设系统方案

### 5.1 题目建议

> **ToolFlow：面向共享 Agent 运行时的工具工作流调度与故障恢复系统**

副标题可以写成：

> 在有限工具资源下保障短任务及时完成，并降低 Agent 工具失败造成的重复执行。

这个题目不声称重新发明 LLM serving，也不与 GPU 集群调度直接竞争。它研究的是**Agent 运行时的主机侧工具工作流**。

### 5.2 可验证的现实场景

设想一个团队共享的资料分析/代码辅助 Agent 平台。用户提交的不是纯聊天，而是以下几类任务：

- 快速查询：读取少量文件或网页后给出结论；
- 资料研究：检索、下载、解析多个文档并生成报告；
- 代码验证：读取仓库、修改文件、运行测试；
- 批处理任务：可以等待，但有截止时间。

这些任务都由相同的 Agent runtime 执行，并共享有限工具池。一个任务在运行时产生下一步，所以系统不能提前知道完整 DAG。

这不是假设“所有真实平台都存在同样比例的任务”。你们应当用公开工作流结构和可控的合成 trace 建立基线，并把负载参数公开。

### 5.3 系统结构

```text
任务提交进程
      |
      v
平台级用户队列 ----> 用户公平/准入调度器
      |
      v
工作流运行时：维护每个任务的状态和动态依赖图
      |
      +--> 可运行步骤队列
      |       |
      |       +--> 浏览器工具池
      |       +--> 代码/命令工具池
      |       +--> 文档解析工具池
      |       +--> 文件写入与结果持久化
      |
      +--> 失败/超时/取消处理器
      +--> 检查点与日志进程
      +--> 守护进程
```

建议第一版把“模型调用”抽象为有输入长度、输出长度和服务时间的任务；这样不需要依赖外部 API，也不会把模型质量波动误认为调度收益。后续可以接一个本地小模型或固定回放服务。

### 5.4 OS 机制的真实用途

| OS 机制 | 在系统中的实际用途 |
|---|---|
| 进程/线程 | 每类工具 worker、工作流运行时、日志和监控分离 |
| 消息队列 | 提交任务、工具结果、失败和取消事件 |
| 共享内存 | 高速传递工作流状态和统计快照 |
| 信号量 | 限制浏览器、解析器、代码沙箱等工具并发数 |
| 互斥锁/读写锁 | 保护任务状态、就绪队列、文件索引 |
| 文件 I/O/文件锁 | 保存检查点、结果和恢复日志，避免并发写坏 |
| 信号 | 超时、取消、优雅退出和故障通知 |
| 守护进程 | 监控 worker，重启崩溃组件并恢复可重放任务 |
| 进程调度 | 对交互、截止时间和后台任务进行 MLFQ/EDF/公平调度 |

### 5.5 调度策略

不要声称发明新的调度算法。建议实现三个层次进行对照：

**基线 A：FIFO。** 按任务或工具调用到达顺序执行。

**基线 B：成熟策略组合。** 例如用户级 DRR/公平轮转，加上工具级 FCFS；或者 MLFQ 处理短任务和长任务。

**方案 C：工具感知工作流调度。** 为每个可运行步骤计算：

```text
score = 截止时间紧迫度
      + 等待时间补偿
      + 用户公平补偿
      + 工作流已完成进度
      - 预计工具占用时间
      - 资源冲突惩罚
```

评分只能作为你们自己的工程策略，不要说它是新的理论算法。它的可验证贡献是：在同样资源和同样工作负载下，是否减少关键任务超时和失败重做。

### 5.6 故障与恢复模型

第一版应只支持可控的故障类型：

- 工具 worker 崩溃；
- 工具调用超时；
- 外部工具返回失败；
- 用户取消任务；
- 共享文件写入失败；
- 进程异常退出。

任务步骤分为两类：

- **经验证可重放的步骤**：输入/数据版本固定且没有不可重复副作用的读取、搜索或解析；不能仅凭工具名称认定安全重试；
- **需要保护的步骤**：写文件、修改仓库、发送外部请求，必须依赖检查点或幂等键。

不要在课设中承诺完整 exactly-once 外部副作用。ExoFlow 已经说明 exactly-once 恢复本身是复杂的系统问题。你们可以明确采用：

> 对本地、可重放的模拟工具提供至少一次执行；对写入步骤使用检查点、临时文件和幂等任务 ID，避免重复提交。

## 6. 验收指标与实验设计

### 6.1 应该展示的宏观指标

| 指标 | 现实含义 |
|---|---|
| 任务完成时间 P50/P95/P99 | 用户从提交到拿到结果要等多久 |
| 截止时间内完成率 | 有多少批任务真正按时完成 |
| 交互任务超时率 | 短任务是否被长任务堵住 |
| 工具等待时间 | 时间花在等待浏览器/解析器/代码沙箱上，还是实际执行上 |
| 重试放大倍数 | 失败导致的额外工具调用和 CPU 时间 |
| 检查点恢复时间 | worker 崩溃后多久能继续工作 |
| 用户公平性 | 是否有用户长期拿不到资源；可报告 Jain 指数或最大/最小服务量比 |
| 资源利用率 | CPU、内存、各工具池是否闲置或过载 |
| 结果质量 | 调度不能通过跳过步骤或降低任务要求获得收益 |

### 6.2 负载设计

使用 30 天压缩仿真，每天包含：

- 交互短任务；
- 长文档研究任务；
- 代码构建/测试任务；
- 截止时间任务；
- 不同用户提交强度；
- 工具执行时长的长尾；
- 随机工具故障和取消。

每天改变任务比例和资源压力，模拟工作日/夜间、考试周、项目截止日前的负载变化。保持所有算法面对相同的任务 trace、资源数量、失败种子和模型服务时间。

### 6.3 必须对比的实验组

| 实验 | 目的 |
|---|---|
| FIFO vs 工具感知策略 | 证明短任务是否减少被堵塞 |
| 无检查点重试 vs 有检查点恢复 | 量化失败造成的重复工作 |
| 无用户公平 vs 用户级公平 | 证明是否存在单一用户占用资源 |
| 固定并发度 vs 动态工具配额 | 观察工具池过载和资源闲置 |
| 无故障 vs 注入故障 | 证明守护进程和恢复机制是否真正有效 |
| 合成均匀负载 vs 长尾/突发负载 | 证明策略不是只在理想负载下有效 |

### 6.4 指标报告方式

最终不要只说“吞吐提高”。应展示：

- P95 交互等待时间下降多少；
- 按时完成率提高多少个百分点；
- 失败重试导致的额外工具调用减少多少；
- 工具 worker 崩溃后的恢复时间缩短多少；
- 最差用户的等待时间是否改善；
- 在不降低任务结果质量的前提下，CPU 和工具池利用率如何变化。

对于任何提升，都要同时报告代价。例如，短任务优先可能让长任务平均等待变长；检查点会增加磁盘 I/O；动态调度会增加状态维护和锁开销。

## 7. 创新点应如何诚实表述

不建议表述为：

> 我们提出了一种全新的 Agent 调度算法。

建议表述为：

> 现有研究已经分别优化了 LLM serving、GPU 集群和工作流级推理调度。本项目面向教学和普通主机环境，构建一个可复现的 Agent 工具工作流运行时，将动态依赖、有限工具池、用户截止时间、故障恢复和 OS 进程机制放进同一套实验框架中，并量化其对任务完成时间、按时完成率和重复执行开销的影响。

它的创新性不是“重新发明 FIFO/MLFQ/EDF”，而是：

- 把 Agent 工具步骤作为 OS 可调度对象；
- 把工具资源冲突和失败重试纳入同一实验模型；
- 用长期、长尾、故障注入的工作负载进行端到端对比；
- 明确展示 OS 机制带来的业务指标变化。

## 8. 主要风险与止损线

### 风险一：与其他 AI 调度题目重合

解决办法是把资源边界写清楚：不调度 GPU 集群作业，不做药物计算，不做模型训练；调度的是**Agent 工作流的浏览器、代码沙箱、解析器、文件和 CPU/内存资源**。正式定题前仍应向其他小组确认实际实现范围。

### 风险二：Agent 工具调度已经有论文

这个判断是正确的。Orla、Agentix、SAGA 等已经说明相关研究正在快速发展。因此不要声称领域空白，而要把目标定义为一个课程级、可复现的系统集成和实验问题。老师如果要求“创新算法”，这个方向的风险会上升；如果老师重视 OS 原理运用和长期指标，它仍然合适。

### 风险三：真实 Agent 工具过于复杂

第一版只使用模拟工具 worker 和固定回放，工具服务时间、失败概率、资源需求均可控。只要能保证同一输入下所有算法执行同一任务，就能比较调度收益。不要一开始接浏览器、代码执行和多个商业 API。

### 风险四：调度通过降低任务质量获益

将任务的步骤数量、模型配置和结果验收条件固定；任何“少调用一个工具”“少生成一些内容”都不能算调度提升。结果质量应作为约束或单独指标。

## 9. 综合判断

调研支持下面这条结论：

> **Agent 系统的调度问题是真实的，而且在 2024–2026 年已经成为系统研究热点；真正的困难来自动态工作流、异构工具、应用级 SLO、资源突发、长尾执行和失败重试，而不是简单的“给请求排队”。**

同时，调研也否定了过于宽泛的创新叙述：LLM 请求调度、工作流级调度、GPU 资源调度和公平性调度都已有强成果。

如果继续这个方向，最稳妥的系统方案是：

> **ToolFlow：共享 Agent 运行时中的工具工作流调度与故障恢复**

它的验收目标不是证明算法击败所有现有系统，而是证明在同一组资源和长尾故障负载下，工具感知、依赖感知和可恢复的 OS 运行时相比 FIFO 或固定并发策略能够：

- 减少交互任务和截止时间任务的 P95/P99 完成时间；
- 提高按时完成率；
- 降低工具失败导致的重复执行；
- 缩短 worker 故障后的恢复时间；
- 防止单个用户或长任务长期占用资源。

这些指标可以直接对应现实中的“用户等多久、任务是否按时完成、失败后浪费多少资源”，比“分类准确率或平均吞吐”更能回应老师的要求。
