# 小型代码托管站爬虫资源调度方案评估

评估日期：2026-09-28。基于用户提交的方案、前次反自动化调研，以及本次对官方事件报道、Linux/Go/Gitea 文档的核验。仅评估，没有部署、压测或修改系统代码。

## 1. 总判断

**保留场景和研究方向，修改核心论证及执行架构，再进行小规模验证。** “持续自动访问挤占小站资源、影响正常浏览”有直接公开证据，Gitea 作为可控代码托管负载也合理。但“群体识别无误伤”“连接分池即后端 CPU 分池”“不用拒绝”和“现有系统只做分类”均不成立。

| 维度 | 判断 | 理由 |
|---|---|---|
| 现实问题和展示 | 强 | 可展示同一浏览操作在不同负载/策略下的延迟与成功率 |
| OS 结合 | 强，但有条件 | 准入、同步、进程隔离、状态管理和守护恢复具有实际作用 |
| 原定 eBPF→worker→cgroup 路线 | 尚未打通 | 连接、HTTP 请求、Go goroutine 与后端 CPU 不是同一归属链 |
| 创新与实证 | 待验证 | 公平、反馈控制、成本计量都已有方案；必须增加强基线 |

当前仓库可见内容仅为课件、提取文本和 research 材料，未发现 Observer/Decision/Executor、eBPF 或 TC/HTB 实现。模块分层可以复用为设计思路，不能据此估计“大部分代码已经可用”；若实现位于其他仓库，应另行审查。

## 2. 痛点证据与已有方案的纠正

### 2.1 公开证据成立，但措辞要精确

[Wikimedia 官方文章](https://diff.wikimedia.org/2025/04/01/how-crawlers-impact-the-operations-of-the-wikimedia-projects/)确认，自 2024 年 1 月起，多媒体下载带宽增长 50%，增量主要来自自动抓取；同时报告 bot 对昂贵回源访问的占比明显高于其整体浏览量占比。这支持“自动抓取侵占峰值余量”，不代表所有流量增长都由 AI 导致，也不证明 Gitea 的 CPU 瓶颈。

[SourceHut 2025 Q1 官方更新](https://sourcehut.org/blog/2025-03-07-whats-cooking-q1-25/)明确记录 LLM 抓取导致服务被打垮的情况；[Q2 更新](https://sourcehut.org/blog/2025-05-29-whats-cooking-q2/)继续讨论应对方式。SourceHut 是独立的代码托管平台，不能写成 SourceHut 的 GitLab。GNOME/KDE 应分别有来源再写，不能把所有项目、部署软件和故障统一成一个事实。

进一步核验：[GNOME 2024 年论坛故障记录](https://discourse.gnome.org/t/login-problems-gitlab/25132)包含访问错误和对 AI 训练爬虫的疑似归因，原文使用 likely，不应改写为 2025 年已确定事故。[GNOME 2026 年 3 月运维公告](https://discourse.gnome.org/t/gnome-gitlab-bot-management-migration-to-fastly/34358)确认此前用 Anubis，并在 3 月 17 日跟帖宣布启用 Fastly WAF、停用 Anubis。KDE 对应的“2025 GitLab 因 AI 爬虫不可用”本次未找到机构原始确认，暂不作为已证实案例；未找到不等于事件不存在。

### 2.2 现有技术描述过度简化

robots.txt 依赖合作，不能强制阻止请求，这一点成立。按 IP 限速对分散来源存在局限，但对单源突发仍有价值，且 NGINX 支持其他 key 和全局/并发约束，不能概括为“没用”。

Cloudflare 的典型防护部署让 HTTP/HTTPS 流量经过其反向代理，源站可仍自托管，见[官方说明](https://developers.cloudflare.com/dns/proxy-status/)。准确的取舍是第三方流量中介依赖、可用功能/费用和部署政策，而不是必须迁移网站。Turnstile 也可单独嵌入，不要求全站流量经 Cloudflare。

此前调研已核验 Cloudflare 成本限流、Envoy 反馈准入、Kubernetes APF 公平隔离。因此“现有都先分类再拦截”错误。应用层 DoS/过载控制同样可以保障服务而非识别人机；爬虫访问的合法性也不能从流量形态判断。项目价值应来自特定约束下的可测增量，不能靠把 DDoS 定义为恶意、爬虫定义为合法来制造技术区别。

## 3. MLFQ 类比有启发，但存在两个不可省略的问题

### 3.1 群体划分仍会误伤

MLFQ 无需知道进程语义，但操作系统已经知道每个进程的身份和获得的 CPU 服务量。公网网站首先要解决“哪些请求属于同一主体”和“为它们实际消耗多少资源”。这两项比套用优先队列更困难。

IP 段可能包含运营商、校园和企业的正常用户；相同 TCP SYN 特征更多反映协议栈、系统配置和路径等特征，并非同一个操作者的唯一标识。[p0f 原始说明](https://lcamtuf.coredump.cx/p0f3/README)可以帮助理解其识别对象，不能拿 OS 指纹当跨 IP 的 bot 身份证明。代理还可能改变站点可见的网络对端。

降级虽然不是封禁，仍可能使被错误聚合的正常请求超时。低频请求也可能极昂贵，高频请求也可能是廉价正常浏览。因此应写“保护低强度交互访问”，并用真实业务标签评估对真人的效果，不应宣称调度器能够自动知道真人所在的池。

建议把会话/认证身份作为有条件的细粒度线索，将 IP/网络特征作为弱关联或辅助约束。匿名新身份不能无限领取高优先级预算；保底应受全局或类别总份额约束。必须承认在匿名、可分裂身份下无法无条件保证按真实人公平。

### 3.2 行为反馈不能替代容量约束

“不用拦截就不怕误判”应删除。若持续输入工作量大于服务能力，队列会不断增长；Aging 改变服务顺序，不产生新的 CPU/带宽，不能保证无限到达任务都及时完成。

可采用有界排队、最大等待、快速过载拒绝和适当 Retry-After，同时在有剩余容量时允许低优先级工作使用它。Aging 应作用于已接纳的任务，不能让无限积压的爬虫请求最终全部升为最高优先级。

累计服务量需要窗口、衰减或明确的服务账本策略；无限期累计会使长期正常用户越来越不利，简单重连或记录淘汰又不能将全部服务历史清零。经典 MLFQ/WFQ/老化不应全部叠加为同一层调度器：可用反馈分级决定类别、级内 DRR 类策略决定服务份额，再用受限等待补偿防饥饿，分别说明作用并做消融。

## 4. 执行链路的四个关键修正

| 原设想 | 实际边界 | 建议 |
|---|---|---|
| sk_lookup 在内核动态给访问分类 | 监听 TCP socket 查找时触发，已建立 TCP 不触发；连接不等于 HTTP 请求 | 用于连接级试验，不作为完整请求调度器 |
| 代理 worker 分 cgroup 就分离 Gitea CPU | 下游 Gitea 进程不会因收到代理请求而继承代理 cgroup | 第一版在 HTTP 入口控制真正进入后端的请求并发 |
| 根据流量统计知道客户端 CPU 用量 | 字节、连接和请求耗时都不等于请求 CPU；并发 goroutine/共享数据库使归因复杂 | 使用经校准的端点成本估计，明确误差；需要精确归因再引入应用埋点或隔离执行 |
| SYN 指纹将上千 IP 正确聚合 | 同指纹会合并无关用户；多个 netns 仍可共享同一内核栈，测试可能偏置 | 将群体混合与身份周转作为实验变量，不能把测试标签送给调度器 |

[Linux sk_lookup 文档](https://docs.kernel.org/bpf/prog_sk_lookup.html)明确区分新 socket lookup 与已建立连接，并只提供地址/端口等上下文；不能直接从这个 context 读取完整 TCP 选项算指纹。若采 SYN 特征，应选择有报文访问能力的适当 hook 并校验内核支持。SO_REUSEPORT 可选择 listener，但不自动给已被应用接管的 HTTP 长连接中每个请求重新分流；其特定 socket 迁移能力不等于任意 HTTP 状态迁移。

TLS 在普通网络 hook 处不可见明文 URL/会话；HTTP/1.1 keep-alive 与 HTTP/2 多路复用允许同一连接承载多个请求；HTTP/3 基于 QUIC/UDP，也不具有 TCP SYN。这些协议边界必须公开，不能只在每请求新建 TCP 的简化负载中得出通用结论。

[Go FAQ](https://go.dev/doc/faq#goroutines)与[net/http 文档](https://pkg.go.dev/net/http#Server)说明 goroutine 在 OS 线程上复用。Gitea 的逻辑 HTTP worker 不是天然可独立放入 cgroup 的 Linux 调度实体；threaded cgroup 的存在也不会自动将 goroutine 隔离。若运行多个完整后端进程，可设置不同 cgroup，但应处理数据库/缓存/磁盘共享与后台任务，保持所有实例总资源与基线一致。若只是多个代理进程汇入同一个 Gitea，则隔离主要针对代理 CPU。

[cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)中 `cpu.weight` 为相对份额，不能用作固定总算力或延迟保证；`cpu.max` 可限制父组总 CPU 配额，子组权重用于共享可用容量，并需确保实际执行实体都位于受控组。实验生成器应与被测服务隔离，避免抢同一份预算。

[HTB 文档](https://man7.org/linux/man-pages/man8/tc-htb.8.html)支持发送带宽分级与借用空闲容量，适用于本机出口带宽竞争；它不能回收已经到达的入站数据成本，也不能替代 CPU 请求调度。第一版可将 CPU 密集网页和带宽密集下载分开实验，避免多个控制器互相干扰后无法归因。

## 5. 建议的最小方案与立项关卡

### 5.1 首版架构

```text
客户端 → TLS/HTTP 入口 → 按已用服务与端点成本估计的有界请求队列 → Gitea
                             ↑
                 负载观测、额度与状态管理、守护进程

cgroup：固定源站总资源；eBPF：可选资源观测；TC/HTB：独立带宽扩展
```

这是 MLFQ 服务反馈思想在请求层的应用，而非直接复制 CPU 时间片。成本基于当前可用信息估计，反馈矫正；优先级改变可作用于后续请求，不要求迁移现有连接。请求墙钟时间包含 I/O 和排队，不得当作精确 CPU 时间。对代价偏大的端点还应有并发上限。

如果用户坚持以 eBPF 为核心，宜先验证“连接→独立实际执行进程→cgroup”的隔离链路，再谈性能，不宜仅为保留题目而使系统不可实现。建议题目暂改为“面向自动化抓取的小型代码托管站服务保障与资源调度”；eBPF 在证实不可替代的价值后再进入主标题。

### 5.2 最低可信基线

| 实验组 | 配置 | 目的 |
|---|---|---|
| 展示组 | 无额外保护但使用正常 Gitea 配置 | 展示真实瓶颈，不能作为唯一比较对象 |
| 基础保护 | 调参后的按 key 限速＋全局并发＋合理缓存/超时 | 不只击败易失效的纯 IP 限速 |
| 强调度基线 | 同一身份粒度上的公平/成本调度和负载准入 | 分离“聚合更聪明”与“调度更好” |
| 候选反馈方案 | 在相同资源/身份信息下增加行为反馈与有限老化 | 检验实际增量；单独做群体划分消融 |

Gitea 中 blame/diff 是否昂贵取决于仓库规模、历史、缓存和配置。官方配置已有 diff 展示行数/文件数限制；不能随意解除合理防护只为造拥塞。需固定版本、仓库快照、缓存冷热、数据库、并发与 keep-alive/H2 设置。观察 Git 子进程和后台任务是否纳入总资源限制。

### 5.3 指标与工作负载

指标分四组：正常会话按时成功率和 P50/P99；源站加保护模块总 CPU/内存与有效成功处理量；爬虫获得的有效内容/服务量及最长等待；误聚合群体、超时/429/503、恢复与控制开销。拒绝成功者不应从延迟/成功率分母消失，快速错误响应不能抬高“有效吞吐”。

network namespace 适合控制地址和网络路径，但不等于上千真实住宅客户端。需同时测试爬虫与真人同指纹、同 NAT、跨段来源、低频昂贵请求、正常热门事件及长连接。流量标签只用于事后评估，不允许按预设爬虫 IP 池给调度器直接提供答案。

“唯一变量是策略”还要求实例数、总 CPU/内存、缓存副本、生成负载与观测开销可比。固定外部到达轨迹，多次随机化配对；不要仅用完成一个请求才发下一个的客户端，让慢策略自动降低外部压力而掩盖延迟问题。真实浏览可另用含阅读间隔的闭环模型，分别报告其目的与指标。

先验证四道关卡：真实负载下存在稳定瓶颈；资源归因/控制链路有效；混合群体和身份变化时仍有可接受误伤；候选方案胜过强调度基线且额外开销可接受。若不防护已经满足目标、瓶颈不在受控资源，或成熟简单控制已经足够，应调整问题而非继续堆算法。反过来，一次过轻的测试没有拥塞，也不足以否定整个领域。

byrdocs 的公开页面不能替代其私有流量分析；本次没有该站分析权限或数据，不对其 bot 占比作判断。即使获得 Cloudflare 图表，bot 分数不是人机真值，流量占比也不是源站资源占比，需要按网站瓶颈解释。

## 6. 可用于答辩的修订表述

本项目面向自动抓取与交互浏览混合的小型代码托管站，在固定服务器资源下，研究基于服务量反馈的有界请求调度。系统不依赖完美的人机分类，而利用可获得的会话线索、请求成本估计和实时负载，限制高资源消耗流的影响，并在有剩余容量时服务低优先级任务。通过进程通信、同步计账、状态管理与守护恢复完成实现，重点验证正常会话体验、资源利用和错误聚合下的稳健性，相比成熟准入与公平调度是否具有增量收益。
