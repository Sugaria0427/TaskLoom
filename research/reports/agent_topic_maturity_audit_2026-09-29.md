Agent 调度选题现状与研究缺口审计

审计日期：2026-09-29。依据：既有两份 Agent 报告、来源记录、论文提取文本、课程课件提取文本，以及后续讨论形成的“模型额度与本地资源协同”候选描述。本轮为既有材料审计，没有新一轮联网检索，没有运行论文代码、实现系统或进行性能实验。来源的网络访问状态仍是原检索日期的记录。

**总体判断：Agent 调度已经具备选题价值和 OS 实现依据，但尚未形成“具体用户需求—可归因的瓶颈—现有方案的不足—可执行的改进—可信指标”这一完整论证链。** 最明显的进展是厘清了服务商推理、客户端请求和工具执行的边界；最明显的欠缺是，后来提出的“API 额度与本地工具联合调度”尚未获得与之匹配的真实负载、具体接入方式和对照证据。

老师更感兴趣为后续选题工作提供了方向。本报告只评估 Agent 方向，保留其作为主候选，不把尚未验证的场景或技术组合写成已经成立的创新。

1. **现状：已完成问题探索和部分证据纠偏，尚未完成场景定型与可行性验证。**

   **目前存在三种不同成熟度的内容。** 2026-09-26 的[初始报告](agent_scheduling_research.md)提出共享运行时中的工具工作流调度与恢复；2026-09-27 的[重评报告](agent_resource_competition_reassessment.md)修正多人共享场景及本地拥塞的过度推断，补入 AIOS、HiveMind、PeakBench 等直接相关工作；此后对话又进一步提出“按完整任务协调模型请求与工具执行”。最后这一层仍主要是候选问题描述，还没有统一的配额模型、任务接口或实验设计。

   | 维度 | 已有基础 | 当前成熟度及主要欠缺 |
   |---|---|---|
   | 问题与文献 | 已确认工作流依赖、API 访问协调、工具资源约束具有研究价值。 | 方向成立，但三类问题的证据来自不同环境，不能直接拼成同一场景的收益证据。 |
   | 场景与控制边界 | 已区分云端推理、客户端请求、主机工具三个边界。 | 具体用户任务、运行时、额度归属、部署位置与瓶颈尚未固定。 |
   | OS 方法与系统 | 已提出准入、就绪队列、公平调度、信号量、IPC、持久化和守护机制。 | 有机制映射，尚无可执行状态机、算法定义与接入验证。 |
   | 实验与交付 | 已提出端到端延迟、按时完成率、资源压力和恢复指标。 | 当前目录未见 Agent 实现、可运行基线、真实任务轨迹或测量结果；30 天仿真尚无校准数据。 |

   **当前最稳妥的问题表述仍是一项待验证假设：**在同一运行时管理的多个 Agent 任务中，如果它们确实共享模型 API 限额和受限工具资源，利用当时可见的依赖与资源状态进行协调，能否比合理配置的独立限流、重试和工具并发控制，完成更多满足时限及质量要求的任务？其中“是否有这样的负载”和“联合控制是否有增量价值”都尚未验证。

   **“平台级”需要进一步消歧。** 在自建 Agent 应用的统一入口安排请求，属于应用平台层控制；它可以服务一个人的多个任务，也可以部署在应用服务器上。服务商内部如何分配 GPU 则属于另一种控制范围。部署位置与是否多用户不是同一个问题。当前不能用“平台级”一词在这两种含义之间切换。

   **OS 适配是已有优势。** 上层运行时可以在工作启动前管理任务依赖、额度和资源占用，内核继续负责实际线程/进程调度；两者掌握的信息不同。课程材料要求真实守护进程，并重视可运行性、功能、体验、性能、可靠性和创新。现有设想能够对应这些要求，但机制名称清单尚不能证明实现质量。[课件依据](../materials/extracted/course_verified.txt)：72–95 行、249–287 行。

2. **证据：核心材料已经有价值，但现实适用性、竞争方案覆盖和数字口径仍有缺口。**

   **第一类缺口是“领域问题存在”与“我们的目标用户确实遇到”之间的距离。** Agentix、JITServe、Parrot 等支持工作流上下文会影响推理服务表现，但它们控制或利用的推理条件不能直接搬到黑盒 API 客户端。Architectural Implications 的服务器资源证据也不能直接等同于个人 PC 的资源竞争。现有文献为方向提供依据，尚未替代具体场景的需求验证。

   最重要的反向证据来自[生产编码追踪](../materials/extracted/coding.txt)：包含模型与工具的单轮会话中，模型耗时占比中位数为 87.7%（1103 行附近）；93% 的工具 batch 仅有一个调用（1811 行附近）。这表明不能默认典型单会话存在重工具并发拥塞。它仍不能证明多个会话没有累计竞争，也不能将模型阶段耗时归因为 API 限额：客户端观测缺少服务端视角，响应时间可能混合网络、排队和推理服务等因素（2506 行附近）。

   我们需要测量的是目标任务的可控等待，而不是笼统收集“Agent 很慢”的案例。首先区分本地准入等待、请求发出后的外部耗时、工具就绪等待和工具实际执行；对并行分支应分析关键路径及重叠，不能把所有跨度简单相加。CPU 争用、内存压力、外部网页等待、工具内部串行和程序逻辑错误的解决方法不同。

   **第二类缺口是当前方案与成熟系统的逐项对照不足。** 已有材料明确说明，AIOS 有调度和工具并发管理，LLMCompiler 有依赖感知并行，LangGraph 有持久化与恢复，HiveMind 有 API 准入、额度跟踪、重试预算和优先级/DAG。因此，首次加队列、首次工具并发、首次工作流感知或首次检查点都不成立。

   但目前仍缺少面向一个具体运行时版本的能力核查，以及对成熟 API 网关、限流库、任务队列与通用工作流系统的有针对性比较。未调研到某个功能，不能写成该产品没有该功能。下一轮应沿着候选痛点检查能力和默认配置，避免只围绕带有 Agent 关键词的新论文检索。尚未完成此项调研时，“现有方案没有联合优化”只能作为待查问题。

   | 最相关材料 | 已支持的判断 | 不能据此推出的结论 |
   |---|---|---|
   | AIOS | 集中调度、工具实例并发管理确实已有实现。 | 普通个人设备上少量任务调用云端模型时也能取得论文的性能增益。 |
   | HiveMind | 共享端点下可以协调准入、限额和重试；论文声明未协调工具/文件操作。 | 其主要模拟实验的高失败率是商业 API 的普遍现象，或全部改善来自排序。 |
   | PeakBench | 工具依赖允许并行与资源允许并行是不同问题。 | 模拟容量违反就是真实 OOM；完整依赖已知的成绩可直接迁移到动态工作流。 |
   | Agentic Coding in the Wild | 生产任务存在模型/工具交替、长尾和不同失败类型。 | 所有长尾源于调度不足，或者多次调用均可通过检查点消除。 |

   **第三类缺口是部分核心数字仍需收紧，本轮发现了新的修正点。**

   - AIOS 的[正文](../materials/extracted/2026-09-27/aios.txt)456 行说明质量实验用 GPT-4o-mini；484 行附近说明效率实验用本地 Llama/Mistral。旧重评第 41 行笼统概括为本地 A5000 实验不够准确。2.1 倍是该设置下的 AIOS syscall 吞吐指标，不能写为完整个人任务加速 2.1 倍。扩展性评估复制 HumanEval 任务形成 250–2000 个 Agent，同样不等同于个人典型并发。
   - PeakBench 的[正文](../materials/extracted/2026-09-27/peakbench.txt)表 9 列出可行比例 74.9%→87.6% 及 Viol. red. 48.5%；但表 4 中同一 Flash 模型的 CVA 增加 0.034，正文明确说明违反面积略变差。可行比例、违反面积和附录另一违反指标不能混用。未澄清口径前，48.5% 不应作为核心收益证据；也不能据此判定论文内部必然矛盾。
   - [早期来源记录](../materials/metadata/agent_scheduling_sources.json)78 行仍保留约 9% 会话产生四倍 retry-driven 开销的概括，正文已经收窄。生产论文中的深循环类别混合调试、错误假设、缺依赖等，不代表四倍调用都能靠故障恢复消除。后续引用应使用修正后的解释。

   **第四类缺口是复现材料和阅读深度不齐。** 本地已有全文提取、官方页面与来源记录，但并非每篇都逐表复核；部分扩展线索只有摘要。HiveMind 代码在原检查时可访问但未运行；PeakBench 仓库在 9 月 27 日返回 404，仅代表当时未取得，不能断言目前仍不可用；生产追踪论文的公开数据计划不能当作已经拿到可回放轨迹。原检索是针对性补查，不是穷尽综述。[复核清单](../materials/metadata/agent_resource_reassessment_2026-09-27.json)记录了这些边界。

3. **设计：资源模型、观察接口与在线决策仍未闭合，会直接影响方案能否成立。**

   **首先，模型额度与本地资源不能使用同一种“申请—释放”语义。** 下表是必须明确的资源类型，而不是已经选定的提供商协议。

   | 资源类别 | 需要回答的问题 | 对调度的影响 |
   |---|---|---|
   | 时间窗口限额 | RPM/TPM 按什么身份、模型与窗口共享？允许多少突发？输入、输出与预留如何计数？ | 已消耗份额通常按服务契约随时间恢复，不能在请求结束时像信号量一样返还。 |
   | 总量或费用预算 | 总 token/金额是否为硬约束？失败、重试和取消怎样计费？ | 消耗后不随并发槽释放自动恢复；排序不能增加总预算。 |
   | 占用型资源 | 工具实例、内存、浏览器会话何时分配及释放？子进程是否仍存活？ | 可以做并发许可与容量预留，但释放必须对应真实资源回收。 |
   | 执行速率与共享资源 | CPU、磁盘 I/O、远端响应速率如何观测？工具内部是否已有多线程？ | 增加并发可能减慢每个步骤；生成 tokens/s 不等同于 API 的 TPM 限额。 |

   还需核查额度是否在其他客户端间共享。我们的运行时只能精确记账经过自身入口的活动；同账号其他程序的请求可能使账本不完整。客户端自主设定的并发上限也不能直接称为提供商的硬限制。当前材料尚未选定并核验这些契约。

   **其次，完整工作流信息的获取途径尚未确定。** HTTP 代理可以看到模型请求，但不天然知道它属于哪个完整任务、哪个工具已经就绪、是否修改共享文件、用户是否取消任务。要真正联合调度，需要可接入的运行时、事件接口或明确的工具包装层。支持一个受控运行时，与透明接管任意商业 Agent 产品，是完全不同的工程范围；目前没有证据证明后者可实现。

   动态依赖也限制算法可见信息。当前可见步骤不等于完整 DAG；已执行十步不意味着完成了 80%。原报告的评分包含“工作流已完成进度、预计占用时间、紧迫度”等，但尚无可靠定义、估计来源、量纲处理或权重依据。未知未来关键路径与剩余步骤不能作为在线真实值。预测方案需要说明冷启动、误差和失准后的保守处理；全知信息只能用于标注清楚的参照上界。

   **再次，已有算法名称必须落到实际可执行的控制点。** 当前最明确的控制点是模型请求发送前和工具启动前的准入及排序。DRR/公平轮转需要定义按用户、完整任务还是子 Agent 计账以及服务单位；否则一个任务拆成更多子 Agent 就可能获得更多份额。EDF 需要有实际意义的截止时间；MLFQ 的反馈降级必须说明发生在哪个步骤边界，不能默认远端推理可以按时间片暂停后无损恢复。资源受限列表调度可以约束已就绪步骤，但无法凭顺序修复单个工具自身超出内存容量的问题。

   OS 方法成立的关键是利用任务级信息管理启动和资源占用。CPU 已有内核调度，额外系统需证明依赖信息、预算或任务级目标带来了什么增量。CPU 使用率更高也不必然更好：如果同机还有前台工作，适当留有余量可能更符合用户目标。

   **最后，联合调度与恢复的作用仍是有条件假设。** 一个值得验证的机制是：模型请求的发送顺序改变后续工具就绪时间，工具阻塞又影响后续请求，因此两个独立控制器可能无法优化完整任务。但两个资源不必在每一时刻同时饱和；需要证明它们沿工作流存在有意义的交互。若只有一个瓶颈，另一层可能只需简单控制。为下游长期预占资源还可能破坏流水并行、浪费会过期的额度机会，或造成占有等待。

   已有 HiveMind 包含优先级和 DAG，[Readiness/Release 论文](../materials/extracted/2026-09-27/readiness_release.txt)已经研究就绪请求的排序和释放预算。它们不能直接代替本候选方案，但足以说明“将这些机制组合”本身不是学术创新的证明。需要找到在明确约束下，独立策略作出何种具体次优决策，候选策略又使用何种额外信息改变了它。

   恢复方面，需区分 Agent 推理/代码逻辑错误、可重试工具失败和基础设施崩溃。日志和检查点不能保证任意执行中的工具可恢复；超时也不证明远端操作未完成。效果已产生但完成记录未落盘、流式结果已部分交付、取消后子进程仍运行，均需要明确状态与处理规则。文件锁只保证规定范围内的互斥，不能自动解决两个 Agent 的语义修改冲突。守护进程的价值应体现在可验证的存活监测、回收与恢复行为中。

4. **验证：需要先取得能区分假设真假的证据，再扩展算法与长期仿真。**

   **目标函数目前仍过宽。** “有限额度转化为更多及时、正确完成的任务”可以作为叙事目标，但必须选一个主要评价口径，其他作为约束。调度器不能凭空增加额度或提高模型推理能力；它可以减少等待、可避免的失败重做和有限窗口中的未完成工作。优先短任务可能提高完成数却推迟长任务，因此正确性、长任务等待和费用需同时核验。

   可将“在固定时间、额度和硬件条件下，通过验收并满足时限的任务数/比例”作为候选主要指标，明确分母包括所有提交任务，并交代拒绝、超时、取消和未完成任务。还需记录按任务类型划分的等待或 P95、实际 token/费用、资源峰值与调度开销。P99 需要足够样本，不宜在极少量任务上制造精确感。若声称保护桌面流畅度，应另测前台响应，不能用工具 CPU 使用率代替。

   **最关键对照应是合理独立控制与联合控制，而不只是无保护或 FIFO。** 两边应有一致的依赖正确性、合理调参后的并发上限、服务契约限流、指数退避和抖动、重试预算及必要的恢复能力。联合方案的改进必须能在消融中归因于其协同决策，不能来自只有它拥有重试或检查点。通用成熟策略还应按具体问题纳入，例如资源受限列表调度与公平准入。

   | 优先阶段 | 需要补齐的材料或验证 | 通过后才能支持的主张 |
   |---|---|---|
   | P0：确定可观察、可控制的场景 | 选一类有独立验收条件的任务、一种可接入运行时、一份可核查额度契约，画出任务与资源边界。 | 我们确实可以做出该调度器，而非只能画架构图。 |
   | P0：定位真实损失 | 在单任务与少量并发任务下获取分阶段时间、资源压力、限额/失败事件，核查现成合理配置。 | 目标用户确有可由本系统影响的瓶颈，且问题未被简单配置充分解决。 |
   | P1：验证协同增量 | 比较两边宽松、仅 API 受限、仅工具受限、两边受限四种条件；用相同可见信息比较独立与联合控制。 | 额外工作流协调在明确负载区间有价值，并知道其无收益或有代价的条件。 |
   | P1：建立验收与长期外推 | 先固定语义回放验证机制，再小规模真实 Agent 检验质量与接入；用测量校准仿真，加入恢复和取消实验。 | 指标可解释、机制可运行，30 天结果有依据且标明仿真假设。 |

   **仿真并不需要等待完整产品，但必须与现实参数相连。** 纯固定时长的模型可能抹掉并发造成的 CPU/内存干扰，恰好删掉待研究机制。应根据实测说明时长如何随并发与资源压力变化；若使用简化假设，应单独做敏感性分析。动态步骤必须按原本可知的时间逐步揭示，不能让候选算法偷看未来。

   30 天压缩回放也必须保持因果与配额语义：若任务到达被压缩而服务时长、窗口恢复等未作一致处理，得到的会是人为过载。用户到达、故障和其他应用负载应按明确模型引入，多种子报告波动。固定随机种子并不自动保证故障影响相同，需说明按任务步骤还是墙钟注入。真实 Agent 验证则要保留质量评估，因为时序、外部内容和模型随机性可能改变后续工作量。

   **下一步最优先补的是场景与因果证据。** 当前应保留的判断是：该方向可以合理使用 OS 管理机制，并且有足够相关研究支持继续探索。必须暂缓的判断是：个人 Agent 普遍受本地拥塞拖累、联合调度必然优于成熟独立控制、已有论文数字就是我们的预期收益、或者已经找到了学术空白。先完成上述 P0 验证，才能决定主线应偏向 API 配额、工具资源，还是确有必要的跨阶段协调。
